## §0 阅读约定

### 0.1 任务粒度五条判据

1. 一个任务 = 一次可独立提交、可独立验证的改动。
2. 提交后构建退出码 0，且不依赖同批次里尚未提交的任务。
3. 每个任务自带至少一条可观察断言，断言里必须出现具体数值、键名、路径或日志片段。
4. 回滚该提交不会让其它已完成任务失效。
5. 不跨 Phase 边界。

### 0.2 复杂度换算

| 档 | 人日 | 判据 |
|---|---|---|
| **S** | 0.5 | 单文件，或纯数据 / 纯资源 |
| **M** | 1.5 | 2 ~ 4 个文件，或新增一个完整行为 |
| **L** | 3.0 | ≥ 5 个文件，或含状态机 / 序列化 / 渲染管线 |

本版对「序列化」的边界见 **A-112**：单一方块实体的两三个 NBT 键**不算** L 档的序列化，协议结构、跨版本存档格式才算。

### 0.3 中间态窗口

本版有**两个**互不重叠的窗口。窗口内某些断言**期望红**——那不是 bug。

| 窗口 | 开窗任务 | 关窗任务 | 跨几个任务 | 窗口内期望红的断言 | 窗口内禁止改动的文件 |
|---|---|---|---|---|---|
| **W1 注册面** | F-331（第一个把 blocks / items 从 28 抬到 29 的任务） | F-348（把 `EXPECTED_COUNTS` 改到 96） | 18 个（F-331 ~ F-348） | 检查器 §2 的「92 / 96」计数断言与 4 项新 ID 的存在性断言 | `tools/verify_project.py` 一行都不许动 |
| **W2 语言键表头** | F-331（第一次让语言键从 321 变 323） | F-339（最后一次让语言键到 328，并同步表头口径段） | 9 个（F-331 ~ F-339） | `ModLangProvider` 类注释里 `321` 那组数与实际键数的**人读一致性**（检查器不校验这一条） | `datagen/ModLangProvider.java:10-16` 的表头口径段 |

两条窗口纪律：

1. **W1 的关窗只有一个任务**：F-348 把 `EXPECTED_COUNTS` 四类同改 + ID 清单加 4 项 + `:453-457` 的算式注释同步，三项必须同一提交（D-289）。
2. **W2 期间不许改表头**：`ModLangProvider.java:10-16` 那段注释写死了 `321`（= 28 + 28 + 32 + 178 + 13 + 42），中途改它会让「注释说 323、下一任务又变 328」的两头对不上；只在 F-339 改一次，落到 `328`（= 29 + 29 + 32 + 178 + 13 + 47）。

> **〔v0.3.0 实施期更正 · Phase 74 · 依据实测〕**

> 现口径（C10）：**窗口内不出现期望红**。`tools/verify_project.py:609-623` 的 §2 只核对检查器自带的期望清单（`total += len(ids)`、`expected_total = sum(EXPECTED_COUNTS.values())`），**不数源码注册面**；新增注册项在 F-348 改清单前完全不可见，所以 W1 全程 `92 / 92` 绿 —— F-348 的作用是「让读数承认 96」，不是「把红变绿」。
> 另（C9）：F-331 的「语言键 321 → 323」在本次拆分下不可独立达成（`runData` 在 F-331 窗口必失败），顺延 F-332。

### 0.4 六条读数纪律

1. **数字只从 64 号 D-258 取**：注册面 96、server config 175、client config 3、语言键 328、Java 文件 156、网络包 2、协议版本 `"4"`、Mixin 0、方块战利品表 29、转换配方 21、合成配方 5、进度 16、方块模型 79、贴图 PNG 88、mcmeta 8。
2. **每个数给算式**（92 + 4 = 96、321 + 7 = 328、151 + 5 = 156、84 + 4 = 88、5 + 3 = 8）。
3. **行号按 UTF-8 实读**；`read` 整读超过 480 行会静默截断，用 `offset` / `limit` 分段。
4. **验收断言只写可观察项**：计数 / 日志行 / `/data get` 读数 / grep 命中 / 像素比对。不写「正常」「手感」。
5. **构建退出码 0 是每个任务的入场券**，不是某个 Phase 的收尾项。
6. **不写英文**：本版不做英译，七条新语言键的 `en_us` 只写值不写进任何验收之外的判据。

## §4 裁决 A-112 ~ A-118（写作期新立，共 7 条）

#### A-112 · 「序列化」在复杂度换算里的边界

- **结论**：单一方块实体的两三个 NBT 键**不算** L 档的「序列化」；协议结构、跨版本存档格式、多字段 payload 才算。
- **理由**：F-333 只存 2 个标量键（模式序号 + 一个 `BlockPos`），若按「含序列化」判 L，本版会出现 2 个 L 档、人日虚高 3.0。
- **影响**：F-333、F-343 定为 M；F-340（含状态机）定为 L。

#### A-113 · 中间态窗口拆成两个

- **结论**：本版拆 W1（注册面，F-331 开 → F-348 关）与 W2（语言键表头，F-331 开 → F-339 关）两个窗口，不合并成一个。
- **理由**：两个窗口的关窗任务不同、禁写文件不同（`tools/verify_project.py` 对 `ModLangProvider.java:10-16`）。合并会逼出「改检查器」或「改表头」二选一的错误顺序。
- **影响**：§0.3 的两行表格。

#### A-114 · 语言键 7 键的分组

- **结论**：`container.*` 记在表头的「其余」组，与 `item.` / `block.` 两组分开算；因此目标算式是 `29 + 29 + 32 + 178 + 13 + 47 = 328`，不是「把 container 记进 item 组」。
- **理由**：`ModLangProvider.java:15-16` 现有的「其余 42」枚举里明确含「1 container」，照既有分组走，表头其余组的写法不用改。
- **影响**：F-339 的表头同步、66 号 §7 的四张子表。

#### A-115 · 终端配方取四角玻璃，而不是换材料

- **结论**：终端配方定 `GIG` / `IRI` / `GIG`（四角玻璃、四边铁锭、正中红石），与培养器 `IGI` / `GRG` / `IGI`、转换器 `III` / `GRG` / `III` 三者两两不同。
- **理由**：原定「四角铁、四边玻璃」与培养器逐格相同，同料同图样的两条 `crafting_shaped` 只会稳定命中一条。换排布比换材料代价小——不用新造「石英是屏幕」的设定。
- **影响**：F-346；64 号 D-268 已同步。

#### A-116 · 贴图计数口径

- **结论**：`textures/block` 下三个数分开数：`.png` **84 → 88**、`.mcmeta` **5 → 8**、文件总数 **89 → 96**。三者不许互借。
- **理由**：`Get-ChildItem -File` 会把 mcmeta 一起数进去，得到 89；拿 89 当 PNG 数会让冻结值从 88 错成 93。RT-96 记的就是这个坑。
- **影响**：F-330、F-348、§0.4 第 1 条。

#### A-117 · 金镐进验收但不写断言

- **结论**：金镐挖三个处理方块的操作写进验收第 19 条，**只记录结果、不断言掉不掉**。
- **理由**：D-280 已定口径；断言可能与原版 `incorrect_for_gold_tool` 的真值相反，变成必红条目（RT-98）。
- **影响**：F-341 的验收断言、66 号 §8 第 19 条。

#### A-118 · 掉落监听放进既有事件类

- **结论**：`BlockDropsEvent` 的监听写在既有的 `event/FarmstormGameEvents.java` 里，**不新建** `event/PuffedHayDropHandler.java`。
- **理由**：`Java 文件 151 → 156` 的 +5 已经把这 5 个新类定死（D-258）；再开一个文件就变 157，与六份文档的数字打架。类注释的「九件事」同步改「十件事」。
- **影响**：F-345。

#### A-119 · 注册面断言有两处，必须同批改

- **结论**：注册面 92 → 96 的断言有**两处**——`tools/verify_project.py:459-470`（脚本）与 `Farmstorm.java:180-183`（运行时启动自检），两处必须与四处注册改动同批收口。
- **理由**：只改脚本会让启动日志末段打 `FAIL` 而检查器全绿；只改日志会让检查器红。`Farmstorm.java:193` 的注释还写着「总数 92 的断言」，漏改会让注释与代码分叉。
- **影响**：F-348 的交付物与验收断言、64 号 D-289 的落地位置。
