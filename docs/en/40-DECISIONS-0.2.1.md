### 0.2 Glossary

This section gives each term its **decision boundary**, not a circle of synonyms. When the five downstream documents meet these words, they are used by the boundary of this section.

**Auto-rebind**
: the periodic **write action** by which the core, **at run time**, folds a cultivator that is "inside its influence range (the 3×3 chunks), in a loaded chunk, not taken in by any core" into its own 16-entry binding list. Decision boundary: a rebind **adds one binding** (`addCultivator`); it is not "re-binding", not "drifting to the nearest", not "choosing the core again"; it **adds unbound ones only**, and removes, changes and moves no bound entry; it **does not force-load chunks** (ruling #2); it **does not change** the core-selection criterion of 0.2.0 (nearest + one's own + not full, `OutpostCoreBlockEntity:276-317`). A rebind is the **third binding write point**, the first two being cultivator placement (`CultivatorBlock:86-102`) and rebinding on core dismantling (`OutpostCoreBlockEntity:685-691`). Per ruling #12 it **partially supersedes** the two sentences "no 'drift to the nearest / periodic rebinding' at run time" and "do not quietly rebind at run time" of the D-165 Notes (the rest of D-165 is kept in full, see §5).

**Unbound**
: the state of a cultivator that is **not** taken into any core's 16-entry list. Decision boundary: the only truth is the list **on the core side** (D-165 of 0.2.0); the copy in the cultivator's BE, "whom I am bound to", is a **reference cache**, and usability has to be validated against the core-side `hasCultivator` (`CultivatorBlockEntity:116-125`). "Unbound" **does not equal** "dismantled", **does not equal** "invisible", **does not equal** "any core may grab it" — it is only a **candidate** for rebinding and still has to pass the three criteria "coverage + one's own + a free slot"; a rebind write goes to **both sides** (core side `addCultivator` + cultivator side `setCore`).

**mount mode**
: one of the two presentation branches of Qbounce, selected by the **server-side** config `qbounce.poseMode`; in this branch an entity carrying Qbounce is given an invisible `ArmorStand` mount (`QbounceMountController:242-272`). Decision boundary: mount is a **global config branch**, not a property of some entity, not player input, not a client state; the other branch `render` **is not** mount. Suspending AI has to skip mount (ruling #7), so "is it mount right now" may only be asked of `QbounceMountController`, and the config **must not** be parsed a second time inside the effect class (otherwise the same thing has two truths).

**Suspend AI**
: calling `Mob#setNoAi(true)` on a `Mob`, so that the target selection and the movement of the vanilla AI stop. Decision boundary: suspending AI is **not** a generic name for "make the mob stop moving" (item 4 of the hard prohibitions of §6 of `BRIEF`) — it changes no damage, health, drops, collision, knockback or pushing, and no state other than `isNoAi`; it **has restore semantics** (see "the original AI flag", ruling #8); the target is **`Mob`**, not `LivingEntity` (a ready-made predicate form is `WildHunterAura:88`); a player is **never** in scope (a player is not a `Mob`).

**The original AI flag**
: the `isNoAi()` reading (`true` / `false`) of a `Mob` **before its AI was suspended**. Decision boundary: restore writes **this reading**, not the constant `false` (ruling #8); the original value is **recorded on the entity** (a NeoForge entity attachment, **which holds across save reloads**, ruling #15), and **must be deleted promptly once used**, leaving no residue; the attachment **stores no timestamp** — the expiry tick lives in memory only (ruling #16); an entity that "was already `noAi` on entry" **must still be `noAi`** on exit, and must not be "helpfully restored to having AI" by this release. The ready-made precedent `AI_RESTORE_AT` of `WildHunterAura` (`:52`) **does not meet** this definition: it stores an "expiry instant" and hard-codes `setNoAi(false)` on restore (`:119`) — exactly the convention ruling #8 changes.

**Hostile mob**
: a `LivingEntity` that is "an instance of `net.minecraft.world.entity.monster.Enemy`" **or** "of `MobCategory.MONSTER`" (union, ruling #9). Decision boundary: this is a **criterion new in this release** (0 hits of `Enemy` / `MobCategory.MONSTER` / `isHostile` across the whole repository, §1.5 of `BRIEF`); it is **wider than** the 5 existing `Monster` filters, so it is **used only for the ×3 gate** and does not change the trigger surface; a player is **never** a hostile mob; "non-player mob" and "hostile mob" **are not synonyms** (the object of the Vibration Bean is the former, the object of ×3 the latter).

**Multiplier**
: `trap.damageMultiplier` — the **1** global config key added to the `trap` group (type double, default **3.0**). Decision boundary: the multiplier is **not** a change to each crop's default values (`blast_carrot.maxDamage` 7, `zangief_cane.slamDamage` 7.5, not one of them moves); **not** a uniform multiply at the damage-event layer (§6 item 2); **not** "every trap takes part" — of the 4 `TRAP` crops only **2** really take part (ruling #11, see D-184); what it multiplies is the **final damage**, not the power, not the cap, not the blast radius; it takes effect **against hostile mobs only**, and does nothing to players or non-hostile mobs.

### 1.2 Core rebinding (D-176 ~ D-177)

#### D-176 · Auto-rebind: every 100 ticks, staggered by the position hash, loaded chunks only, only while not full

- **ID**: D-176
- **Conclusion**: in its own server tick the core tries a rebind once every **100 ticks**; the phase is staggered to **0 ~ 99** ticks by a hash of the core position; **it scans loaded chunks only** and force-loads none; it rebinds only while the core's binding count is **< 16**.
- **Basis**: ruling #2 (**phase staggering** (offset 0~99 ticks by the position hash) + **loaded chunks only**, no force-loading), #12 (**partial supersession** of the two sentences of the D-165 Notes, see §5), #13 (an ownerless core does not rebind), #14 (the order of preference when there are more candidates than free slots); `plan0.2.1.txt:9` ("every 100 ticks", "when less than 16"); row 3 of §3.4 of `BRIEF`; the ready-made phase form `OutpostCoreBlockEntity:507-525` (`floorMod(now + floorMod(pos.hashCode(), interval), interval)`, the decision at `:516-518`); periodic precedents `CoreListBroadcaster:34` (100-tick reconciliation), `CultivatorLinkBroadcaster:60` (20-tick rescan); the only source of 16, `FarmstormConfig:949-951`, and its only read point `OutpostCoreBlockEntity:344`; the ownerless-core early return `OutpostCoreBlockEntity:535-537`; the tie-break keys `OutpostCoreBlockEntity:310-315`.
- **Landing site**: `blockentity/OutpostCoreBlockEntity#serverTick` (`src/main/java/com/dashpig/farmstorm/blockentity/OutpostCoreBlockEntity.java:507-525`).
- **Notes**: ⚠️ **the two phase gates must stay independent**: the existing particle phase gate of `serverTick` does a `return` at `:516-518`; if the rebind is attached after it, the effective period is filtered down to `LCM(40, 100) = 200` ticks (40 is the default of `outpost_core.boundaryParticleIntervalTicks`, `FarmstormConfig:941`, and config can change it to 20~1200), which means "every 100 ticks" fails on the spot and drifts with the config — the ordering is 42's call, but "the 100 ticks do not depend on the particle interval" is a hard constraint (the "independent phase gate" of row 3 of §3.4 of `BRIEF`). The names of the period and phase constants are fixed by 42 within the framework of D-176 (item 1 of §7 of `BRIEF` authorises the derivation). The **capacity check** of a rebind must not go through `cultivators()`: it calls `pruneCultivators()` first (`:328-331`, `:380-391`) and may `setChanged`; use `cultivatorCount()` / `isCultivatorListFull()` (`:334-345`, which triggers no cleanup). Rejected: "reuse the 100-tick reconciliation scan of `CoreListBroadcaster` for rebinding" (§6 item 3), and rejected: "scan every tick": `OutpostCoreBlockEntity:326` has already recorded for such a check that "every tick × 16 entries × number of cores is out of proportion to the benefit". **An ownerless core does not rebind** (ruling #13): a core whose `ownerUuid` is empty (placed by `/setblock`) **takes no part in periodic rebinding at all** — consistent with the "one's own core" convention, the ready-made form being the ownerless-core early return of `emitBoundaryRing:535-537`; with no owner there is no "one's own", and no way to decide whose 16 slots they are. **The order of preference when one round has more candidates than free slots** (ruling #14): ascending `distSqr`, ties broken by coordinate lexicographic order — isomorphic to the tie-break key of `selectCore:310-315` at placement time in 0.2.0, so the behaviour is reproducible; it must not become "chunk iteration order" or "random".

#### D-177 · The scan surface and the write boundary of a rebind: unbound ones only, no taking over, stop when full

- **ID**: D-177
- **Conclusion**: a rebind binds into **its own** free slots only the cultivators "inside the 3×3 chunks, in a loaded chunk, not taken in by any core"; it **removes, changes and moves** no bound entry; it stops at 16; every candidate passes the three criteria "coverage + one's own + a free slot".
- **Basis**: rulings #2, #12; `plan0.2.1.txt:9` ("the unbound Crop Cultivators inside its influence range"); D-165 of 0.2.0 (the core-selection criterion and the 16 cap); `OutpostCoreBlockEntity:276-317` (`selectCore`'s three criteria and the tie-break keys `distSqr` → `placedGameTime` → `x` → `y` → `z`, `:310-315`), `:343-345`, `:351-364`; the range `RANGE_CHUNKS = 1` (`:75`), `inRange` (`:454-465`); the two-sided write precedents `CultivatorBlock:86-102` (`:99` `addCultivator` + `:100` `setCore`) and `OutpostCoreBlockEntity:685-691`; how "unbound" is read, `CultivatorBlockEntity:116-125`.
- **Landing site**: `blockentity/OutpostCoreBlockEntity` (the rebind entry point and the utility "enumerate the block entities in the loaded chunks of the 3×3"; the method and utility-class names are fixed by 42); row 4 of §3.4 of `BRIEF` (0 ready-made implementations: 0 `ChunkMap`; `LevelChunk#getBlockEntities` only in `DeployedCropBlockEntity:227-236`; `getAllEntities` only in `QbounceMountController:220` and `QbounceObserverSync:164`).
- **Notes**: **candidate test = "the cultivator-side cache is empty ∧ the target core has not bound it itself"**, and the cultivator-side cache is written **immediately after the write**, so that cores processed later in the same tick see "already bound" — otherwise two cores in the same tick would each write their own copy for the same block, breaking the one-to-one invariant of D-165 of 0.2.0 (RT-51, **[author's supplement]**). **When the two sides disagree, the rebinding side must skip**: D-165 handles "a disagreement at the pre-use validation" by treating the cultivator as unbound (not usable), whereas a rebind doing the same would create a second owner; the same test handled in opposite directions is one point this release must spell out (**[author's supplement]**). **Writing both sides** is a hard requirement: core side only, and the cultivator-side cache stays empty (`CultivatorBlockEntity:125` passes the core-side validation, but the lie the cache tells stays for good); cultivator side only, and the core's list is one entry short, and neither the capacity nor the migration ever sees it. **No chunk is force-loaded**: only `getChunkNow` is used, and a missing chunk skips the round (ready-made forms `selectCore:296-300`, `pruneCultivators:384-387`), so "the unloaded part of the 3×3" is not rebound this round and waits for the next — this is not an omission (RT-52). **Stop when full**: `addCultivator` returns `false` by itself when full (`:352`), so the rebind loop need not test again, but it **must** stop enumerating at 16 (RT-53). Rejected: "run `pruneCultivators` along with the rebind" — it changes `cultivators` and calls `setChanged` (`:384-389`), and interleaving it with the rebind in the same loop would make "the coordinates bound this round" be counted twice or missed in later tests, whereas all the rebind needs is the single fact "is there a free slot". ⚠️ The class comment at `CultivatorBlock:73-84` currently says "when no core is available ... **does not claim automatically** ... adding a core next to it afterwards **will not bind either**" (`:81-83`), **exactly the opposite** of this entry, and must change with it (row 11 of §3.4 of `BRIEF`, that row already synchronised to `:73-84`).

### 1.4 AI intervention (D-179 ~ D-181)

#### D-179 · Recording the original AI flag: record it before entry, restore it on exit

- **ID**: D-179
- **Conclusion**: record the original `isNoAi()` value of a mob **before** its AI suspension **on the entity** (a NeoForge entity attachment, **which holds across save reloads**); on entry read the original value first and then `setNoAi(true)`; on exit restore by the original value (one that was `true` stays `noAi`); **delete the record immediately** once used.
- **Basis**: ruling #8 (**remember the original value from before entry**, and restore **the original value** on exit (not uniformly "has AI")), #15 (the original value **goes to disk**, recorded on the entity, deleted promptly once used), #16 (the 80-tick window of the Vibration Bean **does not cross a save reload**); §1.5 of `BRIEF` (the only "temporarily disable → restore" precedent `WildHunterAura:87-95` + `:98-123`, `AI_RESTORE_AT:52`, duration 2 ticks, call site `WildHunterDamage:56`; `setNoAi` has only 3 hits across the whole repository, all in that class); §3.1 of `BRIEF` (registry surface +0); RT-54.
- **Landing site**: a new original-AI-flag attachment (`ATTACHMENT_TYPES` registration + serialisation; the class name and package fixed by 42 within the framework of D-179); the entry points `behavior/impl/VibrationBeanTrap#trigger` (D-180) and `effect/QbounceEffect` (D-181).
- **Notes**: **this record must differ from the ready-made precedent**: `AI_RESTORE_AT` of `WildHunterAura` stores an "expiry instant" (`:52`) and **hard-codes** `setNoAi(false)` on restore (`:119`), so it **wrongly lets out** an entity that "was already `noAi` on entry"; this release cannot follow that semantics (ruling #8 exists precisely because of it). **The record lands on the entity** (ruling #15: DataAttachment), so it **holds across save reloads as well** — the cost "a server stop / re-login loses the original value ⇒ the entity permanently has no AI" **does not hold** (the cross-save half of RT-54 dissolves with it); **once used it must be deleted promptly**, leaving no residue. **The expiry tick lives in memory only** (ruling #16): the attachment **stores no timestamp** (42 has confirmed the shape as `Suspend(boolean originalNoAi, int sources)`); the 80-tick window of the Vibration Bean **does not cross a save reload** — on chunk unload / server stop it simply "restores by the original value + deletes the record", at the cost of possibly standing still for only 2 seconds instead of 4 (rare, and **an early restore does no harm**). **When the same entity has its AI suspended in two places at once** (hit by the Vibration Bean first, then by Qbounce), the original value records only the one **from before the first entry**: a later entrant overwriting the original value would take the reading "already changed to `true` by this release" as the original and lock the entity out for good on restore; the reference-count bit in the attachment (`sources`) carries "how many places are still holding it down", and only at 0 is the entity restored and the record deleted (**[author's supplement]**). **No player may appear in the record** (a player is not a `Mob`; the predicate form of `WildHunterAura:88` already gives the correct spelling). Rejected: "restore uniformly to having AI" (§6 item 4); rejected: "derive the original value backwards from `Mob#setNoAi` instead of recording it" — `isNoAi()` only tells you "whether there is no AI right now", and on restore it reads the value this release has already changed, so it cannot be reversed; rejected: "store the expiry instant" (§6 item 8, ruling #16).

#### D-180 · The Vibration Bean: every non-player mob inside the radius loses its AI for 80 ticks

- **ID**: D-180
- **Conclusion**: **at the moment the Vibration Bean triggers**, suspend the AI of **every non-player mob** inside the trigger radius for **80 ticks (4 seconds)**, recording the original value per D-179; "who triggered it" plays no part in the filtering.
- **Basis**: ruling #4 (**every non-player mob inside the radius** (not "the one that triggered the trap")), #5 (**4 seconds (80 ticks)**), #8; `plan0.2.1.txt:14`; §1.3 of `BRIEF` (`VibrationBeanTrap` is 106 lines; its only effect on mobs is being triggered by `Monster`, `:59-64`; `trigger` applies `CONFUSION` to `ServerPlayer` only, `:83-91`; `consume` at `:97`); row 6 of §3.4 of `BRIEF`.
- **Landing site**: `behavior/impl/VibrationBeanTrap#trigger` (`src/main/java/com/dashpig/farmstorm/behavior/impl/VibrationBeanTrap.java:74-105`).
- **Notes**: **the radius introduces no second number**: it reuses the one key shared by the trigger end and the confusion end, `vibration_bean.triggerRadius` (`FarmstormConfig:900-902`, the sharing convention in the comment at `VibrationBeanTrap:41-42`); this release does not change that key's value — the worry "the two radii, for the player and for mobs, disagree" does not exist at the source level (both ends already share one key and the same strict less-than), and RT-56 has now been rewritten as the repeated application of Qbounce (see D-181, **[author's supplement]**). **The 80 ticks are "how long the AI is suspended", not "how long the confusion lasts"**: the latter is `vibration_bean.confusionTicks` (`:903-905`, also defaulting to 80 ticks); the two **share a value but not a meaning**, and must not be merged into one key, nor may "change the confusion duration" be taken for "change the AI duration". **"Inside the radius" is a one-off snapshot at the moment of the trigger**: the trap is `consume`d at `:97`, so a mob entering the radius later is not additionally suspended, and one leaving early is not restored early — the necessary consequence of "one trigger, one settlement" (§7 ⑥), not a defect. **The object is "non-player mob", not "hostile mob"**: ruling #4 says the former, and neutral / passive mobs other than `Monster` are in scope as long as they are not players; the player's exemption stands as before (a player is not a `Mob`). Rejected: "suspend only the one that triggered it" (§6 item 7); rejected: "write the 80 ticks as a new config key" (ruling #5 has given the fixed number; one more key would take 175 to 177 and conflict with §3.2).

#### D-181 · Qbounce: keep the AI suspended for as long as the effect is in force, skip in mount mode

- **ID**: D-181

- **Basis**: ruling #6 (**keep the AI suspended for as long as the effect is in force** (no separate fixed number of seconds)), #7 (**suspend AI only when not in mount mode**; one already in mount mode is left alone), #8, #15 (the original value goes to disk and holds across save reloads), #17 (the attachment type is registered separately, 97 unchanged); `plan0.2.1.txt:18`; §1.4 of `BRIEF` (`QbounceEffect` is 20 lines, 0 overrides; the effect is actually applied at `FriendChivesProjectile:164-169` to **all** `LivingEntity` inside the sphere; the mount is attached at `QbounceMountController:242-272`, the attribute at `:280-287`); row 7 of §3.4 of `BRIEF`; RT-55, RT-56.

Restore must be judged by "**is the effect still on the entity**" (all three paths must be covered: expiry, `/effect clear`, milk; RT-55), and **must not** pair a fixed timer with the first application — otherwise the every-tick rescan resets the timer, or conversely restores early while the effect is still there (RT-56 is exactly that risk, **[author's supplement]**). **There is only one truth of mount**: the check at `QbounceMountController:199`; the effect class (or the record of D-179) **must not** parse `qbounce.poseMode` a second time. Rejected: "count N ticks in `applyEffectTick` inside the effect class and then restore" (ruling #6 explicitly sets no fixed seconds); rejected: "suspend the AI in mount mode as well" (§6 item 6).
