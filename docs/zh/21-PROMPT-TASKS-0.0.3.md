## 0. 使用说明

### 0.1 与 20-PROMPT-MAIN-0.0.3.md 的分工

| 文件 | 管什么 | 投喂频率 |

三条规矩：

1. 本文件不重写硬约束，只引用编号。看到 `D-xx`（决策）回 `16`、`RT-xx`（风险）与 `§11 #n`（验收自检）回 `18`、`§12.x`（异常与边界）与数值表回 `17`、`A-10 ~ A-18`（裁决）与 `F-xxx`（任务）回 `19`、`HC-29` 起与 `N-29` 起回 `20`，不要凭记忆理解。
2. 冲突时的裁决顺序：`16-DECISIONS-0.0.3.md`（v0.0.3 唯一真相源）> `17` / `18` > `19` > 本文件。`19` §0.4 已把本轮的口径分歧裁完（A-10 ~ A-18），本文件按裁决写，不重开讨论。
3. 本文件的验收判据只在 `20` 的完成定义之内收紧，不额外发明新的交付物；`19` 里没有的任务、编号与数值，本文件一个都不加。

### 0.2 怎么投喂

1. 打开本文件，找到当前 Phase 的小节（标题形如 `## 2. Phase 16 · 基线与工具修复（F-100 ~ F-105）`），从标题开始整段复制。
2. 与 `20-PROMPT-MAIN-0.0.3.md` **全文**一起投给编码代理，**一次只投一个 Phase**。
3. 等它按 `20` 的回报格式交回，再对照本节 §x.4 的出口判据逐条验收。
4. 验收通过后，用 §7 的交接语开下一阶段。

三条禁令：

- 不要把 §1 总览表一起投——代理会试图一次做完五个阶段。
- 不要跳过 Phase 16 的 F-100 / F-101 直接做 F-103：0.0.2 的 **77** 是工具修好之后才可复算的实测值，跳过去就回到「拿 +13 宣布 90」的老路（RT-23 风险④；A-14 不许降级成人工签字）。
- 不要按编号顺序硬排这三处（`19` §1.2 的补充前置）：Phase 19 内先 `F-123` 后 `F-122`（`F-122` 的依赖是 `F-105` 与 `F-123`）；`F-126` 要等 Phase 16 的 `F-104`（两个 `fang_trap_cactus` 新键）；`F-132` 要等 `F-128`（`damage_type` 的 data json 与它同一批）。

### 0.3 怎么判断一个阶段完成

三道闸全绿才算过，缺一条都按「未完成」处理：

1. **出口判据**：§x.4 的每一条都能指到 `logs/latest.log` 的断言输出、游戏内 `/execute` / `/data get` / `/damage` / `/advancement` / `/playsound` 的返回值、F3 / F3+B 的界面读数、`src/generated/resources` 或 `run/config/farmstorm-server.toml` 的文件内容、`build/libs` / `dist` 的产物。结构性证据（`grep` 命中 0、`git diff` 为空、`ffprobe` 的编码输出、`jar tf` 的条目列表）只在 `19` §0.3 第 4 条允许的场合使用。说「实现了但没验」不算过。
2. **任务覆盖**：§x.3 的每个 F-xx 都有一份可指认的证据；代理漏做时按 `20` 的完成定义要求回补，不要自己补。
3. **仓库状态**：`.tools\gw.cmd build` 退出码 0；`git status` 只出现本阶段边界内的文件；`docs/zh` 的 00 – 20 与 `docs/en/` 全部、既有 19 条 `CropProfile` 档案的字段、既有 139 个 config 键的默认值（除 F-104 授权的 3 条）、既有 15 条进度、既有 21 条转换配方未被触碰（D-80；`16` §5.7）。

阶段失败时的处理顺序：先让它按 `20` 的自查节自查 → 仍不过就把未通过的验收项抄回任务书重派一次 → 两次不过才换新会话重做，并在交接语里点名卡在哪一条。

### 3.5 常见翻车点

1. **三个镜像常量与 config 不同步**（F-107 第 1 条；A-15）：客户端常量是编译期的另一份数，抄错了不会编译失败，只会「看起来转得慢」或「压缩周期偏长」。表现：旋转约 240 度/秒、或 10 刻一个压缩周期——正是 A-15 判错的那组旧读数。提前发现：三个常量逐值与 `farmstorm-server.toml` 的 `qbounce.*` 比对，差一处即判失败。
2. **`pushPose` 与 `popPose` 不成对**（RT-17 风险②）：`Post` 里因异常提前返回、或只在某些条件下 `pop`，表现是连续渲染 30 秒后整个画面累积位移——越看越歪，退出重进就好，很容易被误判成「显卡问题」。提前发现：RT-17 验法③的「连续渲染 30 秒看是否漂移」必须在真机上做一次。
3. **用「总时长 − 剩余时长」反推 `t`**（F-107 第 2 条）：写法更省事，但 `/effect` 改剩余时长时相位会跳。表现：给效果续时后旋转角度突然跳一大截。提前发现：F-107 第 2 条就是这条对照实验，把剩余时长改成 100 看 `t` 跳不跳。
4. **给混乱新写第二套锁**（RT-19；D-79）：表现是 Q弹 + 混乱同时存在时按 W 反而反向移动——两套逻辑互相覆盖，锁被执行顺序打败。提前发现：`grep -rn "isLocked"` 的命中必须全部指向 `InputLockHandler`；`ConfusionInputHandler` 的第一句必须是 `if (InputLockHandler.isLocked()) return;`。
5. **`mount` 分支漏一条退出路径**（RT-18 风险②）：死亡 / 掉线 / 换维度 / 服务器停止四条任漏一条，隐形 ArmorStand 就会留在世界里，把玩家钉在原地。表现：重进服务器后人物动不了、又找不到是什么挡住了。提前发现：三条路径各做一次 + `poseMode` 切两次看记账表是否清空；重挂超过 20 次会打一行 warn，看到这行就是没走对退出路径。
6. **为坐骑新增 `entity_type`**（A-12；D-102）：一旦新增，注册自检从 90 变 91、`entity_types` 从 13 变 14，A-12 与 D-102 同时被违反。提前发现：本阶段每次 build 后核对注册自检行的 `entity_types` 小计。

### 3.6 完成后应向用户回报

- `18` §11 的 #3 ~ #7 逐条读数（坐姿 / 压低 0.35 / 480 度每秒 / 6 刻周期 / AI 仍在走 / 碰撞箱不变；七段按键各一次的结果；混乱的 W 与 A 位移；叠加时位移为 0）。
- 两条坐姿分支的真机对照记录：观感、AI 表现、碰撞差异、第三方自定义模型是否认 `riding`、最终保留哪条、落选那条是怎么关掉的（默认值 vs 配置）。
- 三个镜像常量的值与 TOML 的对应读数（24.0 / 0.15 / 6）。
- 锁定日志的原文（应当只有一行）与它被打印的时机。
- 四条 grep 的 0 命中证据：`CustomPacketPayload`、`Mixin`、`effect/` 目录里的 `FarmstormConfig`、`QbounceClientState` 里的 `setYRot`。
- 注册自检行（仍是 90、`entity_types` 13、`block_entities` 6）与 `build/libs` 的产物。
- 未关闭的问题（尤其是 RT-17 的 4 个待验证 API 各自的结论、`setMarker(true)` 的实际语义、两分支里哪条更适合将来做默认）。

1. **把 AABB 当判定**（RT-20 风险①）：8 格 AABB 是立方粗筛，角点距中心 13.86 格，直接拿它当命中判定就变成切比雪夫。表现：对角 8.4 格被拦、7.9 格反而不拦。提前发现：`distanceTo(...) <= 8.0` 的欧氏复核必须在 predicate 里；对角 7.9 必拦、8.1 必不拦这两个点各测一次。
2. **漏写「非己方」那一筛**（RT-20 风险⑤；D-98）：表现是自己人和队友的投掷物被自己的菌吃掉——计数照样 +1、粒子照放，玩家还以为是 bug。提前发现：`18` §11 #8 的第三段就是这条；投一次己方，看 `interceptCount` 有没有动、有没有粒子。
3. **拦截后没真 `discard()`**（RT-20 风险⑥；D-99）：表现是被拦的韭照常结算落点，6 次上限形同虚设，还给对面白白上了 Q弹。提前发现：被拦的投掷物落点必须「不爆炸 / 不写方块 / 不施加效果 / 无掉落」四无；`grep -c "new Explosion"` 与 `grep -c "hurt("` 都是 0。
4. **去重标记放错对象**（RT-20 的缓释②）：标记放在方块上而不是投掷物上时，3 个菌围同一投掷物会各自扣一次。表现：`interceptCount` 一次 +3。提前发现：`lastInterceptTick` 必须写在 `ThrownCropEntity` 上，且不进 `addAdditionalSaveData`；三菌同投的读数只允许 +1。
5. **播音次数与命中数挂钩**（F-116 第 3 条；D-85）：写成「每个被施加的生物播一次」时，一次命中 3 个会响 3 次，空投还可能因为「范围里有生物」而响。提前发现：`n ≥ 1` 是唯一判据，一次投掷只播一次，空投完全不播。
6. **`soundRange` 与音量 2.0 两处写法对不上**（F-116 第 2 条）：把 `soundRange` 改成 16.0 却忘了音量、或把音量写死成 1.0，都会让「32 格可闻」这条验收凭手感而不是凭读数。提前发现：改 `soundRange` 为 16.0 后 16 格可闻、改回 32.0 后 32 格可闻，两次都要在 16 / 32 格上各站一次。
7. **给近防菌补了 `sound_event`**（A-13；D-100）：一旦新增，`sound_events` 从 3 变 4、`sounds.json` 从 2 变 3，A-13 被违反且 F-131 的验收错位。提前发现：本阶段 `sounds.json` 的事件数必须仍是 2，拦截音必须写 `SoundEvents.SHIELD_BLOCK` 常量而不是 `minecraft:` 字符串。
