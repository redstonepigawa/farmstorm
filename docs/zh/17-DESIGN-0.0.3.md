### 0.3 单位与取整

1. 时间：秒 / 游戏刻（tick），1 秒 = 20 刻。
2. 长度：格（block）。
3. 生命与伤害：点。原版 2 点 = 半颗心，因此 7.5 点 = 3.75 颗心。
4. 等级与 amplifier：等级 N 落库时 `amplifier = N − 1`。所以「缓慢 V」= `amplifier 4`（这条换算 v0.0.2 已在 `10-DECISIONS-0.0.2.md` 的 D-69 定过）。
5. 角度：度（°）。转速单位写作「度/刻」。
6. 百分比：一律写带 `%` 的数值，不做隐式四舍五入。

### 0.4 距离度量

沿用 16 号 §7.3 对 D-20 的细化：「陷阱与炮台用切比雪夫」的主规则不变，**光环 / 效果半径用欧氏**。本版三个新增判定与一处改值全部走欧氏：朋友的韭 6.0 格（§4.5）、近防菌 8.0 格（§5.3）、震动豆严格小于 4.0 格（§6.5）、刺球 2.5 格（§7.3）。逐条理由写在各节。

### 0.5 权威与同步

1. **服务端权威**：落点结算、方块写入、效果施加、伤害、方块移除全部在服务端（D-23 口径不变）。
2. **0 个自定义网络包**（D-50，本版仍全额有效）：Q弹 与混乱都是 `MobEffect`，用「效果是否存在 + amplifier + 剩余时长」表达完整状态，走原版 `ClientboundUpdateMobEffectPacket` 免费同步。Q弹 的三件套表现（乘坐姿势、旋转、压缩拉伸）全部由「效果存在」派生，客户端自算，不新增任何同步字段。
3. **渲染层不写回**：Q弹 的旋转与压缩只作用于渲染层的 `PoseStack`，不写 `entity.setYRot()` / `entity.setXRot()`，也不改 `Pose` 与碰撞箱（与 11 号 §0.5 第 3 条同一口径）。

## 2. 状态效果：Q弹

### 2.1 一句话定位

一个把受效果生物摆成**乘坐姿势**、绕着竖直轴**持续旋转**、并在旋转中**反复压缩拉伸**的状态效果；效果存续期间受效果玩家的**全部操作被锁死**。时长不由效果自己定，由施加方写入（本版唯一的施加方是朋友的韭，写 200 刻）。

### 2.2 类型与类别

| 项 | 值 | 依据 |
|---|---|---|
| 注册 id | `farmstorm:q_bounce` | D-81 |
| 载体 | 状态效果（`MobEffect`），本版 `mob_effects` +2 之一 | D-81、施工事实卡 §3.1 |
| 可见性 | **可见**：HUD 图标栏里显示这一条 | D-81 |
| 图标 | `assets/farmstorm/textures/mob_effect/q_bounce.png`，18×18 PNG | D-81、D-53 |
| 图标素材 | Steam 工坊的 `preview.jpg`（1024×1024 RGB，622 KB）转 18×18；转换走既有的 `tools/convert_media.ps1`，不另写脚本 | D-81、D-53、施工事实卡 §1.3 |
| 时长 | **效果自身不设时长键**，由施加方写入（朋友的韭 写 200 刻） | D-81、D-85、16 号 §6 第 6 条 |
| 施加对象 | 生物（`LivingEntity`）：玩家与非玩家生物都算 | D-85 的「球体内的生物」 |
| config 组 | `qbounce.*`，4 个键（`poseMode` / `rotateDegreesPerTick` / `squashAmplitude` / `squashPeriodTicks`） | D-81、D-82；施工事实卡 §3.3；§11 |
| 同步 | 原版效果包，0 个自定义网络包 | D-50 |

**对非玩家生物的说明**（本文补充）：三件套对生物照演（坐姿、旋转、压缩都走渲染层，与实体是不是玩家无关）；「不可进行任何操作」这一段对生物不可观测——非玩家生物没有客户端输入，D-81 的锁本来就只落在玩家的输入上。

### 2.3 数值表

| 参数 | 数值 | 单位 | 依据 |
|---|---|---|---|
| 效果时长（由施加方写入） | 200（= 10 秒） | 刻 | D-81、D-85；config `friend_chives.effectTicks` |
| 旋转速度 | 24.0（= 480 度/秒） | 度/刻 | D-81；config `qbounce.rotateDegreesPerTick`。【本文补充】：480 = 24 × 20；一圈 = 360 ÷ 24 = 15 刻 = 0.75 秒 |

| 坐姿分支 | `render`（默认）/ `mount` | 枚举 | D-82；config `qbounce.poseMode`；§2.4 |
| 图标尺寸 | 18×18 | 像素 | D-81、D-53 |

### 2.4 两条坐姿实现分支（两条都要实现）

D-82 要求 **`render` 与 `mount` 两条都实现**，由 `qbounce.poseMode` 切换，默认 `render`；作者在真机上比对后**保留其一**，落选的那条靠配置关掉、**不删代码**（16 号 §6 第 8 条）。本文不预判哪一条胜出——取舍只能在真机上做（D-82 的依据）。

#### 2.4.1 分支 A：`render`（默认）

| 项 | 内容 |
|---|---|
| 表现 | 客户端在 `RenderLivingEvent` 里拿到渲染器与模型实例，把模型的 `riding` 标志置真、并对 `PoseStack` 施加向下的平移（压低模型），让模型呈现原版乘坐姿态。每个客户端渲染自己看到的实体，因此「别人看我坐着」与「我看别人坐着」是同一段逻辑 |
| 改什么 | 只改**渲染期**的模型实例与姿态矩阵 |
| 不改什么 | 不碰实体本身：不改 ``vehicle`` 关系、不改碰撞箱、不改 `Pose`、不影响 AI 与寻路 |
| 代价 | ① 只对继承原版 `HumanoidModel` / `EntityModel` 的自定义模型有效，别的模组自建的渲染器可能不认 `riding` 标志（RT-17）；降级路径是「**只旋转不压坐**」——三件套里的旋转与压缩照演，坐姿退化为原姿势；② 姿势是**近似**：模型是坐着的样子，实体实际上没有载具 |
| 实现层次 | 纯客户端渲染层，服务端零参与 |
| 依据 | D-82；RT-17 |

#### 2.4.2 分支 B：`mount`

| 项 | 内容 |
|---|---|
| 表现 | 服务端给每个受效果生物挂一个**隐形坐骑**（`startRiding`），姿势由原版自己算，拿到的是原版真实的乘坐姿态 |
| 改什么 | 服务端实体关系：生物的载具字段被占用，客户端的 `rideTick` / 渲染姿态随之改变 |
| 代价 | ① 生物 `isPassenger()` 为真，多数 AI goal（近战、寻路、跳跃）在乘客状态下不再跑；② 一个实体只有一个载具，玩家被挂上坐骑后不能再上船、不能再骑马；③ 碰撞箱随载具改变；④ 坐骑实体本身要 tick、要随生物死亡一起移除，漏清就是一个永远漂在世界里的隐形实体（RT-18） |
| 实现层次 | 服务端实体关系层；客户端零改动 |
| 默认 | **关闭** |
| 依据 | D-82；RT-18 |

**一条硬边界**（D-102）：`mount` 分支**不许新增 `entity_type`**——坐骑用原版既有实体类型承载，本版 `entity_types` 的增量保持 +2（两个投掷物，施工事实卡 §3.1），具体用哪个原版类型由 `18-TECH-0.0.3.md` §4 的实体表定死（RT-18）。这条边界的用处是：本分支即使胜出，也不改本版的注册增量表（§1.3）。

#### 2.4.3 两分支对照与切换方式

| 维度 | `render`（默认） | `mount` |
|---|---|---|
| 姿势来源 | 客户端改模型实例的 `riding` 标志 + 压低模型 | 原版载具关系（原版自己算姿势） |
| 谁改 | 客户端 `RenderLivingEvent` | 服务端挂载隐形坐骑 |
| 影响 AI / 碰撞箱 | 否 | 是 |
| 第三方自定义模型 | 可能不认标志 → 降级「只旋转不压坐」（RT-17） | 不受影响（原版姿势） |
| 出错时的影响面 | 画面 | 实体状态 |
| 切换方式 | config `qbounce.poseMode = render`（默认值） | config `qbounce.poseMode = mount` |
| 生效时机 | 启动期读入，改配置后重启生效（本文补充：与既有 config 的读入口径一致，不做热切换） | 同左 |
| 是否允许删除 | 不允许，落选也要留代码（16 号 §6 第 8 条） | 同左 |

两条分支共用同一套「三件套」参数（§2.5）：`poseMode` 只决定**坐姿那一段**怎么来，旋转与压缩与分支无关。

### 2.5 效果期间的三件套

| 表现 | 参数 | 实现层次 | 依据 |
|---|---|---|---|
| ① 乘坐姿势 | `qbounce.poseMode`：`render` = 模型 `riding` 标志 + 压低模型；`mount` = 服务端挂隐形坐骑 | `render` 在**客户端渲染层**；`mount` 在**服务端实体关系层** | D-82 |
| ② 持续旋转 | 24.0 度/刻，绕竖直轴（yaw 方向），方向与累计角度只影响观感 | **客户端渲染层**：在 `PoseStack` 上绕 y 轴旋转，按刻累加 | D-81、施工事实卡 §3.3 |
| ③ 反复压缩拉伸 | 幅度 0.15、周期 6 刻 | **客户端渲染层**：在同一个 `PoseStack` 上做三轴缩放 | D-81、施工事实卡 §3.3 |

三者的计算式（本文补充，参数值全部来自上表）：

```
t   = 该实体在该客户端上「连续带效果」的刻数（首次看到置 0，逐刻 +1，效果消失归零）
θ   = (24.0 × t) 对 360 取模                                  // 单位：度
s   = 0.15 × sin(2π × t / 6)                                  // 幅度由 squashAmplitude 给
scale = (1 − s ÷ 2,  1 + s,  1 − s ÷ 2)                       // y 轴拉开、xz 收窄，体积近似守恒
```

三条实现约束：

1. **顺序固定**：先旋转、后缩放。反过来的后果是缩放轴跟着一起转，观感从「上下弹跳」变成「沿身体斜向挤压」（本文补充）。
2. **时间基准在客户端本地累加**，不用「总时长 − 剩余时长」反推。状态仍由 `MobEffect` 表达（D-50），客户端只拿它做存在性判定；反推会在「重连」与「被另一个来源以不同时长施加」两种情况下跳相位（本文补充）。
3. **一律不写回实体**：不 `setYRot`、不 `setPose`、不改碰撞箱、不发包（D-50、§0.5 第 3 条）。效果消失的那一刻，三件套的累加值同时归零，下一 tick 再看到效果才重新起算（本文补充）。

### 2.6 「不可进行任何操作」= 复用既有的七段输入锁

D-81 明写锁操作**复用 0.0.2 的七段输入锁（D-79），不另写一套**。本文照此落地：七段一段不改，只扩判据。

| # | 段 | 挂在哪个事件 | 锁法 | 覆盖的输入 | 依据 |
|---|---|---|---|---|---|
| 1 | 移动 | `MovementInputUpdateEvent` | `forwardImpulse` / `leftImpulse` 清零，`jumping` / `shiftKeyDown` 置 false | 前后左右、跳跃、潜行 | D-79 |
| 2 | 鼠标按下 | `InputEvent.MouseButton.Pre` | 取消事件（可取消、且是最早的入口） | 左键攻击、右键使用的最前一道 | D-79 |
| 3 | 交互第二道网 | `InputEvent.InteractionKeyMappingTriggered` | 取消事件 | `startAttack` / `startUseItem` / `continueAttack`（含「按住左键持续挖掘」） | D-79 |
| 4 | 键盘动作 | `InputEvent.Key` | **抽干** `consumeClick()`（该事件不可取消，只能抽干） | 快捷栏 1–9、丢弃 Q、背包 E、副手交换 F、切换视角 F5 | D-79 |
| 5 | 滚轮 | `InputEvent.MouseScrollingEvent` | 取消事件 | 滚轮切栏 | D-79 |
| 6 | 视角 | `CalculatePlayerTurnEvent` | `setMouseSensitivity(0)` + 关电影镜头 | 鼠标转向（残留 `0 × 0.6 + 0.2` 的固定系数，即极慢但可微动） | D-79 |
| 7 | GUI | `ScreenEvent.Opening` | 取消，只放行暂停菜单与死亡屏 | 背包、聊天、容器、任何第三方界面 | D-79、源码 `client/InputLockHandler.java` |

三条配套口径：

- **放行两条**：暂停菜单（ESC）与死亡屏。死亡屏是刻意的例外——`/kill` 与坠落伤害都可能在锁定期内发生，拦掉死亡屏会让玩家在没有任何 UI 的状态下卡住（源码注释与 D-79 的「只留 ESC」一致）。
- **拦不住三项**（无 Mixin 够不着，验收时不算缺陷）：F11 全屏、F2 截图、F3 调试。
- **进入锁定的那一 tick 要复位按键状态**：若锁定瞬间左键正被按住，`keyAttack` 会一直 `isDown`，挖掘停不下来；因此进入锁定的一刻主动把 `keyAttack` / `keyUse` 的按下状态清零（D-79 的状态复位条）。

**复用方式（本文补充，这是 D-81 的「复用」在这份代码里的唯一落点）**：`client/InputLockHandler.java` 的七段实现一段不改，只把锁定判据从「桑吉尔蔗相位效果存在」扩成「桑吉尔蔗相位效果存在 **或** `farmstorm:q_bounce` 存在」。

- 由此 D-81 的「不可进行任何操作」= 上表七段的并集；本文不再另列一张操作清单，操作口径以上表为准。
- Q弹 与桑吉尔蔗的相位锁同时存在时，七段都锁；解锁以「两个效果都不在」为准（本文补充）。
- 混乱不参与这套判据（§3.5）。

### 2.7 边界与异常

| 场景 | 规则 |
|---|---|
| 效果期间玩家死亡 | 死亡屏照常放行（第 7 段的例外）；效果随实体移除而消失，锁同时解除，三件套累加值归零（详条见 §12.2） |
| 效果期间玩家退出游戏 | 效果随玩家存档保存，回线按剩余时长继续；客户端刻数从头累加，相位重排——旋转与压缩都是周期函数，观感无副作用（本文补充，详条见 §12.2） |

| 同一生物被多个来源反复施加 | 同 id 同 amplifier 的效果按原版合并规则取剩余时长较长的那一个，不叠加、不翻倍（本文补充） |
| 第三方模组的自定义模型不认 `riding` 标志 | 降级「只旋转不压坐」，不报错、不崩溃（RT-17） |

### 3.5 与 Q弹 的叠加规则：输入锁优先

**规则**（D-83 原文）：与 Q弹 同时存在时**输入锁优先**——被锁定时「反方向」没有意义，按锁处理。

落地三条（本文补充）：

1. **显式早退**：混乱那一段与七段锁的第 1 段挂在同一个事件（`MovementInputUpdateEvent`），两个监听器的执行顺序不由本模组保证。因此混乱那一段先判「锁是否生效」，生效就 `return`，不做取反——不依赖「取反 0 仍然是 0」这个巧合。
2. **每刻现判，不缓存**：锁一解除、混乱还在，下一 tick 立刻恢复反转。
3. **视角永远不反转**（D-83），所以「锁优先」不影响七段的第 6 段；混乱根本不碰那一段。

### 3.6 边界与异常

| 场景 | 规则 |
|---|---|
| 同时带 Q弹 与桑吉尔蔗的相位锁 | 三道来源都锁，锁的判断仍只有一条（第 1 段）；混乱照 §3.5 早退（详条见 §12.1、§12.13） |
| 其它模组也在改移动输入 | 本模组只做「取反」一件事，不重算、不覆盖（详条见 §12.11、RT-19） |
| 旁观者 / 创造玩家被施加 | 施加端只筛 `Player`，两种都在内；但旁观者没有位移、被锁也无可锁（§12.12） |
| 效果被 `/effect clear` 提前移除 | 立刻停止反转，方向分量在下一 tick 回到玩家自己的输入 |

### 4.6 命中判定与音效

**判定顺序（同一刻完成，不排队）**：

1. 投掷物到点，取落点为球心、半径 6.0 格的**欧氏球**；
2. 球内所有生物逐个写入 200 刻的 `farmstorm:q_bounce`；
3. 累计本次**实际施加成功**的生物个数，记作 n；
4. `n ≥ 1` → 在落点播**一次**音效；`n = 0` → 不播（D-85）。

四条口径：

- **判据只有一条**：n 就是施加成功计数，不另做一次「附近有没有生物」的查询——两条判据会打架（本文补充）。
- **只播一次**：一次投掷一次音效，与命中几个生物无关（D-85「播放一次音效」）。
- **32 格怎么来**：原版 `playSound` 的广播半径 = 16 格 × 音量，因此音量取 **2.0** 让半径到 32.0 格（本文补充：换算；32.0 这个数字的唯一来源是 `friend_chives.soundRange`，不改键值）。
- **音源分类**：`SoundSource.PLAYERS`，与 D-76 的循环音同一分类选择口径——不占用 MUSIC、不打断背景音乐。

音效素材的文件名保留 `pengyoudejiu.mp3` 不改，事件 id 用 `friend_chives`（16 号 §4.1 第 3 点）；视频素材的出处与非商业自用声明按 D-66 写进 README 与 Release。

### 5.4 拦截判定：「只拦非己方的本模组投掷物」的判定依据

**什么算**：判定面只有一条基类——`entity/ThrownCropEntity.java`。落地的代码就一句 `instanceof ThrownCropEntity`（D-87 的依据：一个 `instanceof` 就能覆盖全部，不需要逐件登记）。再叠一条**敌我筛选**：投掷物的归属者与该近防菌的放置者不同盟时才算拦截目标（D-98），己方投掷物穿过不拦、**也不扣次数**。

家族规模（D-98 的逐件清单；本节已逐条核对 `registry/FarmstormEntityTypes.java`）：

| 组 | 条数 | 明细 |
|---|---|---|
| 0.0.2 已在 | **10** | `puffed_wheat`、`ubi_server`、`toxic_ubi_server`、`melon_slice_bomb`、`melon_grenade`、`bamboo_firecracker`、`red_mushroom_puff`、`brown_mushroom_puff`、`molotov`、`compressed_puffed_wheat` |
| 0.0.3 新增 | **2** | `friend_chives`、`vibration_bean` |
| 合计 | **12** | 走 `ThrownCropEntity` 的 `entity_type` 总数 |

**「9 还是 10」的账已由 D-98 结清**：D-87 依据里的「v0.0.2 已有 9 个 `entity_type` 走它」是笔误——9 是 **v0.0.1 的 `entity_types` 总数**（8 个投掷物 + 1 个 `turret_bullet`，与 11 号 §1.3 的「9 → 11」对得上），不是走该基类的数目。D-98 已按源码逐件订正为 0.0.2 的 10 个 + 0.0.3 的 2 个 = **12**，本文 §5.4 按 12 写。**判定口径不受影响**：仍是先 `instanceof`、再判敌我。

**原版箭矢为什么不算**：三条产品线彼此平行，`instanceof` 天然排除，因此不需要「排除清单」：

| 原版射弹 | 它的基类链 | 与 `ThrownCropEntity` 的关系 |
|---|---|---|
| 箭 `Arrow`、三叉戟 `ThrownTrident` | `AbstractArrow` → `Entity` | 与 `ThrownCropEntity`（→ `ThrowableItemProjectile` → `ThrowableProjectile`）不同支 |
| 雪球 `Snowball`、末影珍珠 `EnderPearl`、鸡蛋、药水 | `ThrowableProjectile` → `Entity` | 比 `ThrownCropEntity` 更高一层，但**不是**它的子类，`instanceof` 判否 |
| 其它模组的射弹 | 各自的基类 | 同上；本模组不枚举、不登记、不做白名单 |

拦原版箭会改变原版战斗与其它模组的射弹手感，收益远小于风险（D-87 的依据）；这一条比 C-3（man瓜 拦投掷物）更窄，属于本模组内部的自保机制。

**敌我筛选**（D-98）：只拦**非己方**投掷物——投掷物的归属者与该菌的放置者不同盟时才算目标；判定沿用 `TeamResolver`（`00-DECISIONS.md` 的 D-06 原版计分板队伍口径），与陷阱类、炮台类同一套，不另写判据。己方（放置者本人、同队玩家）的投掷物穿过时**不拦、也不扣次数**，6 次寿命不受影响。plan 第 3 条原文里的「非己方投掷物」由此补齐，订正登记在附录 A 第 3 行。

**拦下之后投掷物去哪**（D-99）：拦截成立时投掷物立即 `discard()`，**不触发它的 `onImpact`**——不爆炸、不写入方块、不施加效果、不掉落，也就是不结算落点。否则一个既被「拦下」又照常结算落点的投掷物等于没被拦，D-88 的 6 次上限也失去意义。注意这是**实体移除**，与 D-72 的「触发后方块静默移除」不是同一条路径：方块移除仍走 D-72（D-88），实体移除由 D-99 给。

### 5.5 6 次消耗与「同刻只扣一次」的判定方法

两个计数放在两个不同的对象上（D-88 的依据：方块实体只知道自己被扣了几次，无法知道同刻还有谁在扣；投掷物是这条判定里唯一的共享对象）：

| 数据 | 放在哪 | 类型 | 作用 |
|---|---|---|---|
| 拦截计数 | 方块实体 `DeployedCropBlockEntity` 的 `interceptCount` | 整数，0 起算 | 每次成功拦截 +1；到 6 就静默移除（D-88） |
| 「本 tick 已被拦截」标记 | 投掷物实体上的 `lastInterceptTick` | 游戏刻号，初始为 -1 | 同刻去重（D-88） |

每刻一次的判定四步（扫描间隔 10 刻，RT-20）：

1. 方块实体自己每 10 刻扫一次欧氏 8.0 格内的 `ThrownCropEntity`（只覆盖已加载区块）；
2. 对每个候选先判 `instanceof ThrownCropEntity`，再判**敌我**——归属者与本菌的放置者同队（或就是放置者本人）则跳过，**不扣次数**（D-98）；
3. 对通过前两步的候选看 `lastInterceptTick == level.getGameTime()`：相等 → 本刻已被别的菌扣过，跳过；不等 → 扣自己 1 次，并把投掷物的 `lastInterceptTick` 置成当前刻号；
4. 扣完立刻播粒子与音效、把投掷物 `discard()`（D-99）；若这次扣减让 `interceptCount` 到 6，先完成本次拦截，再 `level.removeBlock` 静默移除自己（D-72 的路径，不走战利品表）。

三条实现约束：

- **「后续菌跳过后清除」的落法**：标记存刻号而不是布尔，下一 tick 刻号不同即自然失效，不需要额外的清除代码（本文补充）。
- **顺序**：「扣次数 → 置标记 → 播图效 → 丢弃投掷物」在同 tick 内完成；把置标记放在扣次数之后，保证同刻不会有第二个菌扣到（本文补充）。
- **不回滚**：任何一步失败都不回滚已扣的次数——「已拦截」是既成事实，回滚会让同一发投掷物被扣两次（本文补充）。

### 5.6 拦截图效是纯视觉

D-89 的三条禁令逐条落地：

| 禁令 | 落地 | 依据 |
|---|---|---|
| 不造成伤害 | 不调 `hurt`：拦截不产生任何伤害事件，玩家不掉血、不加无敌帧、不产生死亡消息 | D-89 |
| 不破坏方块 | 不动任何方块状态；自己用完后的移除走 `level.removeBlock`，是「移除自己」而不是「破坏别人」 | D-89、D-88 |
| 不构造 `Explosion` | 连 D-58 的「威力 0 触发器」都不用——这里连触发器都不需要，落点就是投掷物自己的位置 | D-89 |

只留下的两样：`interceptParticles`（8）个粒子 + 一次音效。音效**不新增** `sound_events`（本版 `sound_events` 的增量只有 +1，是朋友的韭的命中音，施工事实卡 §3.1），改用原版既有音效事件（D-100）；具体复用哪个事件、音量与音高，由 `18-TECH-0.0.3.md` 的音效表定死一次。

### 5.7 边界与异常

| 场景 | 规则 |
|---|---|
| 球内没有本模组的非己方投掷物 | 什么都不发生，不扣次数，方块保持待机 |
| 同一刻被 N 个近防菌够到 | 只扣其中 **1** 个的次数（§5.5 的第 2 步），其余菌下 tick 才可能扣到别的投掷物 |

### 6.4 「不依附」模式与既有 `supportsFloating` 的区别

D-91 明写**不许**复用 `supportsFloating`——那是「依附丢失后容忍」，语义不同。两者的差别逐条列出：

| 维度 | 既有的 `supportsFloating`（0.0.2） | 震动豆的「不依附」模式（0.0.3 新加） |
|---|---|---|
| 前提 | 方块先**合法依附**在一个支撑面上 | 从落点那一刻起**就没有**支撑面 |
| `canSurvive` | 仍做支撑检查；依附丢了才转 `FLOATING` | 恒真：不查支撑、不查 FACE 方向 |
| `updateShape` | 依附方消失 → 置 `FLOATING` 并 `markDetached()` | 恒返回自身：任何方向的邻居变化都不改状态 |
| FACE 支撑检查 | 参与（`supportPos` / `supportDirection`） | 不参与——没有「依附面」这个概念 |
| 移除条件 | 依附丢失且未开 `supportsFloating` → 移除，并按 `deploy.dropOnSupportLost` 决定是否掉落 | 只有被玩家挖掉、被触发结算、或被 `/setblock` 覆盖 |
| 语义 | 「依附丢失后**容忍**」 | 「从一开始就**不依附**」 |
| 依据 | 0.0.2 的 `block/DeployedCropBlock.java`；16 号 §5.7 | D-91、RT-21 |

三条落地约束：

1. **不许合并**（D-91、16 号 §6 第 9 条）：合并的后果是既有 5 个部署方块的依附语义被一起改掉，而 16 号 §5.7 明写「既有部署方块的行为与外观不动」。
2. **三处分支**（D-91）：`canSurvive` 恒真、`updateShape` 返回自身、FACE 支撑检查短路。三处以一个「模式旗标」开关，**只作用于 `farmstorm:vibration_bean` 这一个方块**。
3. **方块实体复用**：不新增 `block_entities`，仍用既有的 `DeployedCropBlockEntity`（施工事实卡 §3.1）。

### 6.5 触发与结算

**触发条件**：非己方玩家与陷阱方块中心的**欧氏距离严格小于 4.0 格**（D-92）。「严格小于」是硬口径——恰好 4.0 格不触发（plan 第 50 行原文也是「小于 4」）。

**两端的分工**：

| 端 | 认谁 | 依据 |
|---|---|---|
| 触发端 | 只认**非己方玩家**（照 D-07 的敌我口径）；创造与旁观沿用既有陷阱的豁免、不触发 | D-92；【本文补充】创造/旁观豁免（D-92 未逐条重述，按 D-71 的既有口径处理） |
| 效果端 | 半径 4.0 格内的**所有玩家**，**不筛敌我**——己方踩到也会被混乱。这是 D-101 所管的效果端（照 D-27 的一次性 AoE 口径），与近防菌的拦截筛选（D-98）是两回事 | D-92、D-101 |

**端点口径**（D-101）：效果端与触发端共用同一个 4.0 的尺子（D-92 的依据原话是「同一把尺子的两个用法」），两端都用**严格小于 4.0**，不许一端写「< 4」另一端写「≤ 4」。若两端的端点不一致，会出现「站在 4.0 格处没触发，却被混乱」这种自相矛盾的结果。配置上只有一个键 `vibration_bean.triggerRadius`（4.0），两端共用它。

**同一刻内的四步**（不排队、不分帧）：

1. 判触发（非己方玩家、欧氏距离 < 4.0）；
2. 对半径 4.0 内的所有玩家施加 80 刻 `farmstorm:confusion`；
3. 在陷阱处播**一次**爆炸音效（复用原版既有音效事件，D-100；只用音效，不构造 `Explosion`，避免与 D-58 的威力 0 触发器混淆）；
4. `level.removeBlock` 静默移除方块，不产生掉落物、不触战利品表（D-72）。

**一次性**：方块移除后不可能二次触发；同刻多个玩家同时满足条件时只结算一次（方块已经没了）（本文补充）。

### 6.6 边界与异常

### 7.5 「击中」的定义（D-95）

## 9. 幸运浆果随机池的扩充

### 9.1 结论

| 项 | 值 | 依据 |
|---|---|---|
| v0.0.2 的池 | 19 条档案 − 3 = **16** | D-55、11 号 §11.11 |
| v0.0.3 的池 | 22 条档案 − 3 = **19** | D-97 |
| 本次增加 | **+3**：`friend_chives`、`point_defense_fungus`、`vibration_bean` **全部纳入** | D-97 |
| 排除项 | 仍是 `lucky_berry`、`wild_apple`、`compressed_puffed_wheat` **三件，一件不加** | D-97、16 号 §6 第 11 条 |
| 推导式 | **不动**：池 = `CropProfile.ALL` 减去那三件（流式推导，不是清单） | D-97、D-55 |
| 代码 | `util/CropProfile.java` 的池常量不改；`util/LuckyBerryRoller.java` 不改 | D-97 |
| config | **无新增键**（池内容不进 config） | D-97、D-55 |

### 9.2 池成员是怎么来的

- 池的实现是「`CropProfile.ALL` 减去三件」的**推导式**，不是一份手写清单。档案从 19 增到 22，池就自然从 16 变成 19——这是当初选推导式的必然结果，也正是它的用处（D-97 的依据）。
- 三条新档案都不具备狂野苹果的强度地位：朋友的韭是投射 + 增益、近防菌是防守方块、震动豆是一次性陷阱。进池不会造成「1 颗浆果换到本版最强道具」的失衡（D-97 的依据）。
- 反过来说，若为它们逐个加排除项，推导式就退化成需要逐版维护的清单，与 D-55 的原意相反（D-97）。

### 9.3 后果：池里现在含朋友韭（有意为之，不是漏洞）

**这一节是本节的正文，不是脚注。**

1. **能开出朋友韭**：吃一颗幸运浆果，有概率直接得到 1 个 `friend_chives` 投掷物。
2. **再扔出去就是 10 秒全锁**：落点球内（含投掷者自己）的生物拿到 200 刻 Q弹，同时**全部操作被七段锁锁住**（§2.6）。因此存在一条完整可复现的路径：**吃一颗浆果 → 把自己扔进去 → 被锁 10 秒**。
3. **这是 D-97 明确要求写出来的后果**，属**有意为之**，不是漏洞：作者本次要求三条新档案全部纳入；D-97 的落地位置原文就是「必须写出后果：幸运浆果可开出朋友韭，落地后是 10 秒 Q弹并锁住全部操作」。
4. **另外两条后果**（本文补充）：开出近防菌 = 得到 1 个防守方块，没有副作用；开出震动豆 = 得到 1 个一次性陷阱，要自己踩才会中招。

**不做的三件补救**：不给「玩家自己被锁」加豁免、不给池加新的排除项、不改 Q弹 的时长（16 号 §6 第 6、11 条；D-81、D-97）。要改其中任何一条，都必须先改 16 号，再改代码。

### 9.4 一个易错点

池是 **19**，不是 22（22 是档案表行数），也不是 16（16 是 0.0.2 的池）。三个数分别属于三个不同的对象：档案条数、池成员数、上一版的池成员数。`18-TECH-0.0.3.md` 的启动自检文案按池的实测成员数写（D-97 的落地位置）。

## 12. 异常与边界处理清单

编号沿用 11 号 §11 的风格，共 **14 条**。每条只写规则与依据，数值回到各节查。

### 12.1 Q弹 与混乱 叠加

- **规则**：**输入锁优先**（D-83）。两者同时在时移动分量为 0，不结算反转；混乱那一段先判锁、锁生效就 `return`（§3.5）。
- **不靠巧合**：「取反 0 仍然是 0」只是数学上的巧合，实现必须显式早退——两个监听器挂在同一个事件上，执行顺序不由本模组保证（本文补充）。
- **解除即恢复**：锁一解除、混乱还在，下一 tick 立刻恢复反转（每刻现判，不缓存）。
- **视角不受影响**：混乱永远不碰第 6 段，所以「锁优先」不影响视角锁（D-83）。
- **依据**：D-81、D-83、RT-19。

### 12.2 Q弹 生效中玩家死亡 / 退出

- **死亡**：死亡屏是七段第 7 段的**刻意例外**，照常打开（否则玩家在没有 UI 的状态下卡住）；效果随实体移除而消失 → 七段锁立刻解除、三件套累加值归零；重生后的新实体不继承任何状态（D-79、D-81）。
- **退出**：效果随玩家存档保存，回线按剩余时长继续（原版 `MobEffectInstance` 行为）；客户端刻数从 0 重新累加，旋转与压缩的相位重排——两者都是周期函数，观感无副作用（本文补充）。
- **快速重连**：若在 200 刻内回线，玩家带着剩余时长的效果回来，锁照旧生效、三件套照旧；不补发任何阶段（与 11 号 §11.4 的桑吉尔蔗同类处理同构）。
- **依据**：D-81、D-79、D-50。

### 12.3 mount 分支下生物被骑乘 / 被拴绳

- **跳过挂载**：受效果生物若已有载具（`isPassenger()` 为真）或正拉着拴绳（`isLeashed()` 为真），**不挂隐形坐骑**，退化为 `render` 分支的表现（本文补充）。
- **为什么**：一个实体只有一个载具。强挂会把玩家从船上、马上踢下来，或把生物从驮着它的实体上摘下来——这正是 D-82 明列的「改实体关系与碰撞」代价（RT-18）。
- **拴绳不抢**：拴绳是另一套实体关系，`mount` 分支不去解、不去覆盖；效果结束后拴绳原样有效。
- **清理**：效果结束时把坐骑一并移除；若坐骑已不存在（区块卸载、被 `/kill`），按空操作处理，不报错。
- **依据**：D-82、RT-18。

### 12.4 近防菌 拦截到一半区块卸载

- **计数在方块实体里**：随区块卸载与重载保存、恢复；**已扣的次数不回滚**——「已拦截」是既成事实，回滚会让同一发投掷物被扣两次（本文补充）。
- **标记不进存档**：「本 tick 已被拦截」是投掷物实体上的运行期字段（刻号），不参与区块存档；投掷物在未加载区块里本来就不 tick，因此不会出现「跨 tick 的半个拦截」（本文补充）。
- **扫描只覆盖已加载区块**：菌所在区块加载、投掷物所在区块未加载时这一发扫不到；投掷物的寿命是 100 刻（§6.3），等它重新加载通常已经过期，实际结果是「不拦」。
- **粒度回滚**：若扣次数之后、播粒子之前发生区块卸载，粒子丢失、计数已扣，按「已拦截」算（本文补充）。
- **依据**：D-88、RT-20、D-72。

### 12.5 震动豆 悬空方块遇活塞 / 水 / 方块更新

- **方块更新**：`updateShape` 恒返回自身，任何方向的邻居变化都不改状态、不移除（D-91 的「不被方块更新移除」）。
- **水**：既有部署方块的 `pistonPushReaction` 没有被覆盖（默认 `NORMAL`，`block/DeployedCropBlock.java` 未声明该属性），水流不会冲掉它（本文补充）。
- **活塞**：判为可推 → 方块与方块实体一起平移，陷阱跟着换坐标、仍可被触发；判为不可推 → 原地不动。两种结果都**不经过**「依附丢失 → 移除」这条路径，因为这个模式从一开始就没有依附（D-91 的依据）。
- **只有两条路能移除它**：玩家挖掉，或被 `/setblock` 覆盖（§6.4 的表）。
- **依据**：D-91、RT-21。

### 12.6 震动豆 与其它陷阱同时触发

- **各自独立**：每个陷阱都是一次性方块，只看自己与玩家的距离，互不查询、互不排队（D-92）。
- **同刻都结算**：两个陷阱同刻都满足条件时，两句 `removeBlock` 各删各的方块；两段 80 刻混乱是同 id 同 amplifier，按原版合并规则取剩余时长较长的那一个，**不叠加、不翻倍**（本文补充）。
- **与既有一次性陷阱同构**：与桑吉尔蔗、刺球一样走「一次性 + 静默移除」，谁先结算谁先消失，不回滚（D-72）。
- **依据**：D-92、D-72。

### 12.7 刺球 尖牙落在无地面处

- **不检查地面**：尖牙坐标由部署点 + 两圈分布半径算出后直接生成，不因目标位置没有支撑而跳过任何一颗（本文补充）。
- **为什么不能检查**：个数与两个分布半径是 D-94 的决策边界（§7.4）。加一条「没地面就少生成一颗」的判据，等于偷偷改了这两项，而 16 号 §5.3 明写这两项不在授权内。
- **落在不该有实体的位置**：处置以原版实体自身行为为准（原版尖牙不在生成时做支撑检查），本模组不做额外清除、不做兜底（本文补充）。
- **依据**：D-94、D-30。

### 12.8 桑吉尔蔗 目标在相位 2 死亡

- **取消随之失效**：效果随实体移除而消失，自然坠落伤害的取消也跟着没了（它靠效果存在性判定，§8.4 第 1 条）。
- **结算不执行**：人已经死了，落地 7.5 点不施加；不产生 `farmstorm:zangief_slam` 的伤害记录，也不产生第二段击杀归属（D-96、D-72）。
- **同刻先后**：若死亡与落地落在同一刻，以服务端结算顺序为准——先落地则结算一次 7.5，先死亡则只走死亡路径。两种都只结算一次（本文补充）。
- **不二次触发**：方块已在触发刻静默移除（D-72）。
- **依据**：D-96、D-72。

### 12.9 桑吉尔蔗 与其它模组的坠落免疫冲突

- **只取消自己这一段**（RT-22）：只用效果存在性判定，只取消「本陷阱相位 2 期间」的坠落伤害；缓降、免疫、飞行由它们自己决定，本模组不读取、不覆盖、不检测。
- **叠加后的结果**：若其它模组在相位 2 期间也取消了坠落伤害，结果是「它们取消 + 本模组结算 7.5」，7.5 仍只结算一次——它由落地事件施加，不走坠落伤害通道（本文补充）。
- **永不落地**：目标在相位 2 期间获得飞行或漂浮时走 `MAX_FALL_TICKS`（100 刻）结束，不结算 7.5（§8.4 第 4 条）。
- **不做运行时检测**：与 RT-16 的同类处理一致，不做兼容分支。
- **依据**：D-96、RT-22。

### 12.10 幸运浆果开出朋友韭

- **会发生**：池含朋友韭（D-97）。吃到浆果得 1 个投掷物，扔出去落点球内的生物（含自己）拿 200 刻 Q弹并**锁住全部操作**（D-81）。**有意为之，不是漏洞**（§9.3）。
- **不加补救**：不给「玩家自己被锁」加豁免、不给池加排除项、不改 Q弹 的时长（16 号 §6 第 6、11 条）。
- **锁定期间死亡**：走 §12.2 的死亡路径，死亡屏放行，不卡 UI。
- **依据**：D-97、D-81、D-55。

### 12.11 混乱 与其它模组的移动修改

- **只做取反**（RT-19）：在 `MovementInputUpdateEvent` 里对两个分量取反，不重算、不覆盖、不读其它模组的中间值。
- **与锁同时存在**：锁优先（§3.5、§12.1）。
- **顺序无实义**：若其它模组在同一事件里做归一化或限速，取反发生在它之前还是之后由事件注册顺序决定；两种顺序的结果都只是「方向相反、力度不变」，不影响可玩性（本文补充）。
- **不检测不降级**：不做运行时检测、不加兼容分支。
- **依据**：D-83、RT-19。

### 12.12 创造 / 旁观玩家的豁免

三处分开写（D-81、D-83、D-92 都没有逐条重述豁免，以下是本文补充的推导；近防菌那一行由 D-98 给了敌我口径）：

| 处 | 规则 | 依据 |
|---|---|---|
| 陷阱触发端（震动豆、刺球、桑吉尔蔗） | 创造与旁观**不触发**，沿用 D-71 与 v0.0.1 三处陷阱的既有豁免 | D-71、D-92 |
| 效果施加端（朋友的韭 的 Q弹、震动豆 的混乱、刺球的缓慢） | **不设豁免**——D-81 与 D-83 都没有这一条。创造玩家被朋友的韭命中就锁 200 刻；旁观者拿不到 `EvokerFangs` 的伤害，因此也拿不到刺球的缓慢 | D-81、D-83、D-95 |
| 近防菌 | 只拦**非己方**投掷物（D-98）；它拦的是投掷物不是玩家，因此创造/旁观玩家的身份在这里不参与判定 | D-87、D-98 |

### 12.13 Q弹 与桑吉尔蔗的相位锁并存

- **同一套锁**：两个效果都打开七段锁（第 1 段判据看「任一效果存在」），解锁以「两个效果都不在」为准（§2.6）。
- **互不读取**：桑吉尔蔗的相位机在相位切换时重发同 id 不同 amplifier 的效果；Q弹 的存在不改变相位推进，反之亦然（D-50）。
- **先后结束**：Q弹 先结束 → 锁保持到相位 2 结束；桑吉尔蔗先结束 → 锁保持到 Q弹 结束。两种都不出现「半解锁」（本文补充）。
- **依据**：D-79、D-81、D-50。

### 12.14 己方触发的陷阱与己方投出的投掷物

- **震动豆**：效果端对半径内所有玩家一视同仁，己方玩家踩到同样拿 80 刻混乱（D-92、D-101）。不筛敌我的是**效果端**，与近防菌的拦截筛选（D-98）是两回事。
- **近防菌**：只拦**非己方**投掷物（D-98）；己方玩家投出的作物穿过时**不拦、也不扣次数**，与 plan 第 3 条的原文一致。
- **刺球 / 桑吉尔蔗**：触发端只认非己方玩家（D-71 与既有口径），己方踩上不触发。
- **这三处不是同一把尺子**：触发端与拦截端管「谁踩进来 / 谁扔过来」（D-07 的敌我口径，D-98 同源），效果端管「谁被波及」（D-27 的一次性 AoE 口径）——分工不同，别把效果端的不筛读成拦截端也不筛（D-92 的依据）。
- **依据**：D-92、D-98、D-101、D-71。
