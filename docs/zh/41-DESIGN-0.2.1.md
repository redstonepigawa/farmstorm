## 0. 阅读约定

### 0.1 本文与 40 号的分工

40 号定**口径**（一句话结论 + 依据 + 落地位置 + 连带），本文写**长什么样**（触发条件、周期与相位、时序、范围、参与面、玩家侧观感、边界）。四条分工纪律：

1. **口径不在这里发明**。本文每一个结论后面都挂决策号（`D-17x`）；读者若发现某句追不到决策号、也不是标了「本文补充」的推导，那就是本文的缺陷，不是可以自行解释的空白。
2. **40 号的正文不复述**。本文引编号，不抄结论句；需要读者「先读 40 号第几条」的地方直接写编号。
3. **哪些东西不在这里**：config 全表与键名清单（42 号）、类设计与方法签名（42 号）、**NBT 结构**（42 号）、任务编号与排期（43 号）、验收表本身（42 号）。本文只在「依据」一列点出 config 键名与默认值。
4. **与源码冲突时报给作者**。写作期发现 40 号或事实卡与源码对不上的地方，逐条列在交稿说明里，**不改上游**；本文按 40 号写，并在对应小节留一句「按 40 号口径」的说明。

### 0.2 「本文补充」的判定标准

| 类型 | 允许标「本文补充」 | 说明 |
|---|---|---|
| 算术 | 是 | 由两个已给数值算出的第三个数，必须写出算式（例：`100 ÷ 20 = 5 秒`、`7 × 3 = 21`、`16 × 3 = 48`） |
| 40 号明确授权 | 是 | 40 号写了「由 42 号在框架内定」的条目，本文可以先把**观察面**钉住，实现形态仍留给 42 号 |
| 上游没覆盖的读法 | 是 | 必须同时给出「为什么只能这么读」，并登记进 §9 的边界清单 |
| 事实卡已给、作者未拍板 | 标「卡补充（可否决）」 | 例：`friend_chives.effectTicks` 默认 200 刻、`qbounce.poseMode` 默认 `render` |
| 与 40 号或事实卡冲突 | **不许** | 冲突只能回报，不能自己选一个写进去 |
| 审美偏好 | **不许** | 「我觉得好看」不是理由，必须给可判定的判据 |

本文里一个数只有四种合法来源：40 号写着的、事实卡的、带算式的算术、或标了「本文补充」并给了理由的。四种都不是，就是文档缺陷。

### 0.4 单位与计数口径

1. **时间**用游戏刻（tick），**1 秒 = 20 刻**。本文有两个词必须分开：**周期**（多久尝试一次，100 刻）与**窗口**（状态持续多久，80 刻 / 效果存续期）。两者不换算、不互相推导。
2. **范围**用区块：核的影响范围 = 以核所在区块为中心的 **3 × 3 区块**（切比雪夫距离 ≤ 1，`RANGE_CHUNKS = 1`，【`OutpostCoreBlockEntity:75,454-465`】），边长 `16 × 3 = 48` 格，共 **9** 个区块。
3. **「16」是名额**（`outpost_core.cultivatorCapacity` 默认 16），**「54」是格子**（`outpost_core.storageSlots` 默认 54）；两个数本版都不改，混读会把「补绑」写成「往箱子里塞东西」。
4. **「非玩家生物」与「敌对生物」不是同义词**：前者 = `Mob` ∧ ¬`Player`（R3 / R4 的对象），后者 = `Enemy` ∪ `MobCategory.MONSTER`（R5 的对象，D-182）。任何一处把两个词对调，都是错的。
5. **「AI 被删」= `Mob#setNoAi(true)`**，不是「让生物停止移动」的泛称；它不改伤害、血量、掉落、碰撞与击退，**有恢复语义**（D-179、裁定 #8）。

## 2. R1 核心自动补绑

**本节依据：D-176、D-177（裁定 #2、#12）。**

### 2.1 一句话定位

核在**运行期**每 **100 刻**在自己 3 × 3 已加载区块里找一个「没人要」的培养器，把它补进自己的 16 个名额——这是绑定的**第三个写入时点**（前两个：培养器放置 `CultivatorBlock:85-102`、拆核迁移 `OutpostCoreBlockEntity:686-690`）。补绑**只加不摘**：不摘、不改、不搬任何已绑条目，也不重新选核。

### 2.2 触发条件：绑定数 < 16 才补

| 项 | 规则 | 依据 |
|---|---|---|
| 名额来源 | `outpost_core.cultivatorCapacity`，默认 **16**、范围 1 ~ 64；唯一读取点 `OutpostCoreBlockEntity:344` | 【`FarmstormConfig:949-951`】；D-177 |
| 触发条件 | 当前绑定数 **< 名额** 才进入扫描；已满 ⇒ 本轮**直接返回**，一条都不补 | D-176、D-177 |
| 容量判定的读法 | 用 `cultivatorCount()`（`:334`）或 `isCultivatorListFull()`（`:343`）；**不用** `cultivators()`（`:328`）——它会先调 `pruneCultivators()`（`:380-391`）并可能 `setChanged`，把「只想问还有没有空位」变成一次写操作 | D-176 补充 |
| 「16」怎么写 | 正文写「默认 16」，实现读 config；**不写死 16**，否则 config 改成 8 或 64 时补绑会与放置判定分叉 | D-177；【`FarmstormConfig:951`】 |
| 一轮最多补几条 | 从 0 条补到名额为止，**不设每轮条数上限**：`16 − 0 = 16` 是本版单轮的理论最大增量【本文补充：算术】 | D-177 |

### 2.3 周期与相位：100 刻、**独立相位门**

| 项 | 规则 | 依据 |
|---|---|---|
| 周期 | **100 刻**（= 5 秒，`100 ÷ 20`）【本文补充：算术】 | `plan0.2.1.txt:9`；D-176 |
| 相位 | 按**核坐标 hash** 错开到 **0 ~ 99** 刻（`100 − 1 = 0~99`）【本文补充：算术】 | 裁定 #2；D-176 |
| 参考形态 | 与既有粒子门**同形**：`floorMod(now + floorMod(pos.hashCode(), 100), 100) == 0`（【`OutpostCoreBlockEntity:516-518`】的算式，模数换成 100）；常量名、是否复用 `pos.hashCode()` 由 42 号定 | D-176；【卡 §7 第 1 条】 |
| 周期来源 | **常量 100**，不是 config 键。本版 config 只 +1 键（`trap.damageMultiplier`，D-183），若再给补绑周期开键就变 **177**，与 D-185 的 176 直接冲突 | D-183、D-185；【卡 §3.2】【本文补充：不新增键的理由】 |

**⚠️ 这一条的实现陷阱，也是本节最重要的一句话**：`serverTick`（`:507-525`）现在只做三件事——非 `ServerLevel` 返回 → `interval <= 0` 返回（`:511-513`）→ **粒子相位门 `:516-518` 不满足就 `return`** → 边界粒子 + 每 30 轮一条日志。补绑若接在那个 `return` **之后**，实际周期会被筛成 `LCM(40, 100) = 200` 刻（40 是 `outpost_core.boundaryParticleIntervalTicks` 的默认值，【`FarmstormConfig:939-941`】，且可被 config 改成 20 ~ 1200），等于「每 100 刻」当场失效并随配置漂移。

⇒ **两套相位门必须各自独立求值**（顺序由 42 号排，但「100 刻不依赖粒子间隔」是硬约束，D-176 补充）。

| 项 | 粒子门（既有，不改） | 补绑门（本版） |
|---|---|---|
| 位置 | `OutpostCoreBlockEntity:516-518` | `serverTick` 内，与本门**并列**，不得在其 `return` 之后 |
| 周期来源 | `outpost_core.boundaryParticleIntervalTicks`，默认 40，可配 20 ~ 1200（`:939-941`） | **常量 100 刻** |
| 模数 | `interval`（可配） | **100**（固定） |
| 相位 | 坐标 hash 对 `interval` 取模 | 坐标 hash 对 **100** 取模 |
| 结果 | 每 40 刻刷一圈边界粒子 | 每 100 刻尝试补绑一次 |

**玩家侧的时间感**（三个数都是算术，不另设数值）：核放下后在**最坏 100 刻（5 秒）**内就会尝试第一次补绑（相位偏移 0 ~ 99 ⇒ 首次触发落在放置后的 1 ~ 100 刻内）；之后每 100 刻一次。

### 2.4 范围与扫描面：3 × 3、只扫已加载

| 项 | 规则 | 依据 |
|---|---|---|
| 范围 | 与核所在区块的切比雪夫距离 ≤ 1 ⇒ **3 × 3 区块**、边长 48 格、共 **9** 个区块 | 【`OutpostCoreBlockEntity:75,454-465`】；D-176 |
| 只扫已加载 | 区块用 `getChunkNow` 取；取不到 ⇒ **本轮跳过该区块**，不加载、不报错、不计失败 | 裁定 #2；D-177 补充；现成形态 `selectCore:296-300`、`pruneCultivators:384-387` |
| 枚举方式 | 遍历 `LevelChunk#getBlockEntities()`，只认 `CultivatorBlockEntity` | 【卡 §1.1】；现成唯一先例 `DeployedCropBlockEntity:230-234` |
| 先例只能抄一半 | 那一处用 `level.getChunk(...)`（`:228`，**会加载**）；补绑要求不加载 ⇒ 只抄 `:230-234` 的遍历，不抄 `:228` 的取区块 | 【`DeployedCropBlockEntity:227-236`】；裁定 #2 |
| 无先例 | 「按区域枚举方块实体」全仓 **0 处**：`ChunkMap` 0 处，`getBlockEntities()` 仅上表 1 处；`getAllEntities()` 仅 2 处且都不是方块实体 | 【卡 §1.1】 |

**「只扫已加载」在常态下其实很少真的跳过**（【本文补充】，依据是源码，不是新口径）：核自己所在的那 1 个区块有一张自有票，`distance = 1` ⇒ **中心区块 tick、紧邻 8 个区块已加载到 FULL**（【`outpost/CoreChunkTickets:17-30,43-44`】）。也就是说 3 × 3 与票的覆盖范围**恰好重合**，所以「跳过未加载」是**防御分支**，真实来源只有三种：

1. 核刚放下 / 刚重启，票还没生效（`setOwner:418` 才申请票，重启后由 `restoreAll` 补）；
2. 方块实体自己在 tick、但某个邻区块因为内存压力被降级；
3. `/setblock` 出来的核（没有 `setOwner`、没有票）。

**结论**：补绑的扫描面是「3 × 3 减去本轮读不到的区块」，**不是**「3 × 3 减去 8 个永远读不到的区块」。

### 2.5 候选判据与两侧写入

**「未绑定」在本版的可执行判据**（D-177 补充给了唯一的形态，本文照抄，不另立第二个）：

| 形态 | 判定方式 | 本版是否采用 |
|---|---|---|
| 严格形态（核侧全局） | 遍历**所有**己方核的 16 条列表，确认没有任何一条指向它 | **否**：全仓没有「培养器 → 核」的全局索引；按核数 × 16 逐轮全扫的代价，`OutpostCoreBlockEntity:326` 已经为同类判定记过「每刻 × 16 条 × 核数，代价不成比例」 |
| **本版形态** | 培养器侧缓存**为空**（`corePos == null`，NBT 缺 `Core` 键就是未绑定，【`CultivatorBlockEntity:41,53,318`】、【`CultivatorBlock:97`】）**∧** 目标核自己没绑过（`hasCultivator`，`:338`） | **是**（D-177 补充） |
| 不一致形态 | 缓存指向某个核、但那个核的列表里没有它 | **跳过，不补**（D-177 补充） |

三道判据**全部通过**才写：

|---|---|---|---|
| 1 | 覆盖它 | `inRange`（`:454-465`，区块切比雪夫 ≤ 1） | 不在候选集内，永不补 |
| 2 | 未绑定 | 培养器侧缓存为空 ∧ 本核没绑过 | 跳过（已绑的**不夺**） |
| 3 | 还有空位 | `count < capacity` | 立即停止枚举（§2.6） |

**写入顺序与「两侧都写」**：先 `addCultivator`（`:351`，满员自己返回 `false`）→ 成功后才 `setCore`（【`CultivatorBlockEntity:79`】）→ **先核侧再培养器侧**，顺序与放置时（`CultivatorBlock:99-100`）和迁移时（`OutpostCoreBlockEntity:686-690`）逐字一致。只写核侧则培养器侧的引用缓存长期为空（下一轮会因 `hasCultivator` 拒绝重复写，于是**永远补不上缓存**）；只写培养器侧则核侧列表少一条，容量、迁移、连线三处都看不到它。

**无归属者的核不补绑**（**裁定 #13**）：`ownerUuid == null` 的核（`/setblock` 出来的）**不补绑**。理由与现成形态一致：`emitBoundaryRing:535-537` 对无主核就是「直接返回」；没有主人就谈不上「己方」，也无从判定这 16 个名额归谁。它也不在 `OutpostCoreIndex` 里（索引只在 `setOwner:410-423` 写入）。

**空位不够时的取舍**（**裁定 #14**）：一轮扫到的未绑定培养器多于剩余空位时，按「到本核的 `distSqr` 升序 → 坐标字典序」取前 N 个，与 `selectCore:310-315` 的平手键同构——同一份存档两次运行给出同一个绑定结果，而不是取决于区块与方块实体的枚举顺序。

**缓存指向一个已经不存在的核**（【本文补充】）：这种「陈旧缓存」按 §2.5 的不一致形态**跳过**——补绑不得把它当未绑定重绑，因为它可能正指向一个本轮读不到（区块未加载）的核；代价是该培养器维持不可用，直到那次拆核走完迁移出口②（清缓存）或人工处理。

### 2.6 一对一：同一培养器不得被两个核同时认领

这是 0.2.0 D-165 的不变量，本版**保留**（RT-51）。补绑引入第二个写入者之后，守它的机制有三层：

| 层 | 机制 | 说明 |
|---|---|---|
| 1 | **候选面**：只有「缓存为空」的培养器才进候选 | 已被任何核写过的培养器，缓存都非空 ⇒ 天然排除 |
| 2 | **写入即占位**：核侧写入成功后**立刻**写培养器侧缓存 | 同一刻内后处理的那个核读到的是已更新的缓存 ⇒ 跳过（D-177 补充） |
| 3 | **串行**：同刻的多个核在主线程上**依次**跑 `serverTick` | 因此「先收集候选、跨刻再统一写」是不允许的：那会让两个核在同一时刻都看到「缓存为空」【本文补充：由层 2 推出的写法约束】 |

**满则停**：`addCultivator` 满员自己返回 `false`（`:352`），补绑循环不必再判一次，但**必须在到达名额时停止枚举**（RT-53）——否则「扫到 16 之后还继续 read 每个方块实体」会白烧 CPU，且给「刚绑上又被摘」留出窗口。

**补绑不调 `pruneCultivators`**（D-177 否决）：它会改列表并 `setChanged`（`:384-389`），与补绑在同一循环里交错会让「本次已绑的坐标」在后续判定中被重复或漏计。代价是：核的列表里若存在**死条目**（方块已被拆），它仍然占名额，补绑仍按「满」处理，直到别处调用 `cultivators()` 触发惰性清理（§9 B-10）。

### 2.7 与「放置时绑定」的关系：**部分取代** D-165，不是追加

裁定 #12 的原文是「**部分取代**」，plan `:5` 的「除非**本文档明确要求**，否则不能修改 0.2.0 原有内容」与 plan `:9` 的「每100刻会尝试绑定……」合起来就是那个明确要求。逐句点明：

| D-165（0.2.0）的条款 | 状态 | 本版 |
|---|---|---|
| 「运行期不做『就近漂移 / 定期重绑』」 | **被取代** | 每 100 刻的定期**补绑**是本版明确要求的（D-176） |
| 「**不要在运行期偷偷补绑**」（D-165 补充） | **被取代** | 同上；且补绑不是「偷偷」——它有显式需求（本文 §2 全节），并由 42 号写进验收表 |
| 选核判据（覆盖 + 己方 + 未满，最近优先，平手键 `distSqr` → `placedGameTime` → 坐标） | **保留** | 补绑复用同一判据（`selectCore:276-317`），**不新立第二套排序**；补绑也不改变「放置时」的判定 |
| 16 上限（`outpost_core.cultivatorCapacity`） | **保留** | 补绑的边界就是「到 16 即停」（§2.2、§2.6） |
| 一对一（一个培养器 0 或 1 个核） | **保留** | §2.6 的三层机制守的就是它 |
| 「绑定的唯一真相在核侧」 | **保留** | 补绑仍然先写核侧、再写缓存；缓存**不是**真相（D-165 补充，40 号 §5 读表要点） |

**「补位」不是「漂移」**：漂移是「把已绑的搬到更近的核」，补绑是「把没绑的补上」。本版一条已绑记录都不会被搬家。

**一句注释必须改**（【卡 §3.4 第 11 行】）：`CultivatorBlock:81-83` 现在写着「没有可用核时……**永久**处于未绑定态……**不自动认领**——事后在旁边补一个核也**不会**绑上」。这与本版正好相反，不改就是「注释说不行、代码照做」。

### 2.8 边界与异常

| 场景 | 规则 | 依据 |
|---|---|---|
| 补到 16 | 立即停止枚举；已绑的 16 条**一条不动**，第 17 个仍未被绑 | D-177；RT-53 |
| 3 × 3 里某个区块本轮读不到 | 跳过该区块，本轮不补它里面的培养器；下一轮（100 刻后）再试，不加载区块 | 裁定 #2；D-177 补充 |
| 补绑与拆核迁移同时发生 | **不会双认领**：被迁移的培养器缓存指向正在被拆的核（非空）⇒ 不在补绑候选内；迁移出口②清空缓存后，由**下一轮**补绑接管（≤ 100 刻） | D-177 补充；D-168 |
| 培养器侧缓存为空、核侧其实有记录（异常态） | 补绑**跳过**（D-177：两侧不一致一律跳过）。不得「按未绑定处理」——那会造出第二个主 | D-177 补充 |
| 写入核侧成功、写入培养器侧时 BE 已不在 | 只写核侧；下一轮因 `hasCultivator` 返回 `false` 而不会重复计数（幂等），缓存仍空 | 【本文补充】 |
| 核没有归属者（`/setblock`） | 不补绑，直接返回 | 【本文补充】；现成形态 `emitBoundaryRing:535-537` |
| 两个己方核都覆盖同一批未绑定培养器 | 各补各的空位；同一格只会落到一个核（先写者占缓存，见 §2.6 层 2） | D-177 补充 |
| 核的列表里有已拆方块的死条目 | 仍按「满」处理，本轮不补；死条目由下一次 `cultivators()` 的惰性清理摘除，**补绑不主动 prune** | D-176 补充、D-177 否决 |

## 3. R2 核心储物悬停显示物品详情

**本节依据：D-178（裁定 #3）。**

### 3.1 一句话定位

在据点核心的 54 格界面里，把鼠标移到任何一格物品上，就能看到**物品名称 + 附魔 / 效果行**，与打开普通箱子时完全一致。**这不是「从零做一套 tooltip」**：默认链路本来就该显示，本版把它写成本版的**显式需求 + 显式验收**，实现面**优先一行不改**。

### 3.2 事实前提：默认链路没有被绕过

| # | 证据 | 出处 |
|---|---|---|
| 1 | `OutpostCoreScreen` 共 **42 行**，**只覆写 `renderBg`**（`:37-41`）；`render` / `renderTooltip` / `renderLabels` / `init` 覆写**均为 0** | 【卡 §1.2】；【`client/OutpostCoreScreen:21-42`】 |
| 2 | 54 个槽位全是原版 `net.minecraft.world.inventory.Slot` 实例（`:68`、`:79`、`:84`），没有自定义 `Slot` 子类去改悬停行为 | 【卡 §1.2】；【`menu/OutpostCoreMenu:66-86`】 |
| 3 | 全仓 `renderTooltip` 命中 **0 处** | 【卡 §1.2】（本文复核一致） |

⇒ 原版 `AbstractContainerScreen#render` 自己会调 `renderTooltip`，**没有人拦它**。所以本版要交付的是「需求 + 验收」，不是「一段新渲染代码」。

### 3.3 「保证」意味着什么

「保证」是**可验收的行为承诺**，不是「大概没问题」。四条不许、两条必须：

| # | 不许 / 必须 | 为什么 |
|---|---|---|
| 1 | **不许**覆写 `render` 之后不调 `super` | 那是唯一会让整条 tooltip 链路消失的改法（0.2.0 里不存在，本版也不许引入） |
| 2 | **不许**自绘槽位绕过 `renderSlot` | 自绘槽位不会走原版的悬停判定，等于把「有没有 tooltip」变成手写逻辑 |
| 3 | **不许**加自定义 `Slot` 子类来「提供 tooltip」 | 原版 `Slot` 不负责 tooltip，加子类解决不了任何问题，只多一层没人读的代码（D-178 否决） |
| 4 | **不许**自己接管 tooltip 的定位 / 缩放 / 背景 / 延迟显示 | 那是原版的处理面；接管一处就要接管全部，42 行的类会变成自绘界面（D-178 否决） |
| 5 | **必须**让 54 格与玩家背包格的行为**一致** | 两类槽位都在同一个 `AbstractContainerScreen` 里，原版一视同仁 |
| 6 | **必须**覆盖本模组自己的 tooltip 行 | 本模组有 `tooltip.farmstorm` **20 条**语言键（【卡 §0】），它们本来就是物品 tooltip 的一部分；「显示物品详情」包含它们，不是只显示名字 |

### 3.4 验收怎么观察（画面上看，不看代码）

| 步 | 操作 | 必须看到 |
|---|---|---|
| 1 | 己方玩家空手右键核心，打开 54 格界面 | 界面正常打开，版式与普通双箱同形（54 格 + 玩家背包） |
| 2 | 鼠标移到**有物品**的格子上，停住 | 出现 tooltip：**第一行是物品名称** |
| 3 | 换一个**带附魔 / 带本模组效果**的物品（例如带临时附魔组件的作物） | tooltip 里多出**附魔行 / 效果行**，样式与普通箱子一致 |
| 4 | 鼠标移到**空格子**上 | **没有** tooltip（不是空框、不是一条空白） |
| 5 | 鼠标移到**玩家背包格**的物品上 | 与第 2 步完全一致 |
| 6 | 把鼠标移到界面最右侧一列 | tooltip 仍完整可见（原版会翻到左侧；位置由原版算，本版不接管） |

**验收只能写成「悬停可见」**：原版 `renderTooltip` 的调用点行号在本机不可核（【卡 §1.2】只给本仓证据），所以验收**不许**写成「`render` 里第 N 行调用了它」。

### 3.5 不改变什么 + 边界

| 项 | 结论 | 依据 |
|---|---|---|
| 54 格 | **不变**（`outpost_core.storageSlots` 默认 54，【`FarmstormConfig:944-946`】） | D-166 保留；40 号 §5 |
| 两道访问闸 | **不变**（己方 ∧ 原版触及范围） | D-166；40 号 §5 |
| 菜单结构 / 三处 `addSlot` | **不变**（`:68`、`:79`、`:84`） | 【卡 §1.2】 |
| 背景贴图 | **不变**（`generic_54.png`，256 × 256，`:22-28`） | 【卡 §1.2】 |
| 注册面 | **不变**：不新增 `Slot`、不新增 Screen、`menu_types` 仍 2 | D-175 |

**边界**：悬停空格无提示；tooltip 超出窗口右侧时由原版翻到左侧；非己方玩家根本打不开界面（D-166 补充），所以「非己方看不到 tooltip」不是 tooltip 的问题；界面关闭后 tooltip 状态不残留。验收通过了而代码一行没改，是**正确结果**，不是「没做」（RT-59、40 号 §7 第 4 条）。

## 4. R3 震动豆对非玩家生物删 AI

**本节依据：D-179、D-180（裁定 #4、#5、#8）。**

### 4.1 一句话定位

震动豆**触发的那一刻**，给触发半径内**所有非玩家生物**删 AI **80 刻（4 秒）**，到时按进入前的**原值**恢复。谁触发的**不参与筛选**：踩到它的那只怪、旁边站着的牛、路过的村民，只要在半径内且不是玩家，都被停手。

0.2.0 里对生物的作用是 **0**（生物只是触发器，【`behavior/impl/VibrationBeanTrap:59-64`】），所以这是**全新行为**，不是「改了个时长」。

### 4.2 对象与半径

| 项 | 规则 | 依据 |
|---|---|---|
| 对象 | **范围内所有非玩家生物** = `Mob` ∧ ¬`Player`；**不是**「触发陷阱的那一个」，也**不是**「敌对生物」 | 裁定 #4；D-180；现成谓词形态 `combat/WildHunterAura:88` |
| 半径 | 沿用触发端与混乱端**共用的同一个键** `vibration_bean.triggerRadius`（默认 **4.0** 格，严格小于），**不新设第二个数** | 【`FarmstormConfig:900-902`】；D-180 补充；【`VibrationBeanTrap:41-42`】的注释 |
| 玩家 | **恒不在对象内**（玩家不是 `Mob`），玩家的处置**一字不改**：半径内所有玩家照旧拿 `CONFUSION` | D-180；【`VibrationBeanTrap:83-91`】 |
| 快照 | 「范围内」是**触发那一刻的一次性快照**：之后进入半径的生物不补删，提前离开的也不提前恢复 | 40 号 §7 ⑥；D-180 补充 |
| 计量 | 半径内**有几个**生物、删了几个，只进日志，不影响结果 | 【本文补充】 |

### 4.3 时长与恢复：80 刻、记原值

| 项 | 规则 | 依据 |
|---|---|---|
| 时长 | **80 刻** = `80 ÷ 20 = 4 秒`【本文补充：算术】 | 裁定 #5；`plan0.2.1.txt:14`（「4秒」） |
| 窗口 | 半开区间 `[t0, t0 + 80)`；第 `t0 + 80` 刻起恢复（与 `trap/TrapImmunity:16` 的窗口写法同形） | 【本文补充】；D-180 |

| 原值 | 进入前先读 `mob.isNoAi()`，把这个读数记进该实体的**落盘**原值记录（裁定 #15，见 §5.5）；结束时写回**那个读数**（原值是 `true` 的仍留 `noAi`） | 裁定 #8、#15；D-179 |

### 4.4 与「只对玩家施混乱」并存：一次触发，两类结果

| 步 | 时刻 | 发生什么 | 谁受影响 |
|---|---|---|---|
| 1 | `t0` | `findTrigger` 命中（非己方玩家 **或** `Monster`，`:45-66`） | — |

### 4.5 边界与异常

| 场景 | 规则 | 依据 |

## 5. R4 Q弹 对非玩家生物删 AI

**本节依据：D-179、D-181（裁定 #6、#7、#8）。**

### 5.1 一句话定位

带 Q弹 效果的**非玩家生物**，在**效果存续期间**一直处于 `noAi`；效果一结束，立刻按进入前的原值恢复。**不设固定秒数**（裁定 #6）——「多久」由施加方写进效果的时长决定。当前处于 **mount 模式**时**不删**，已挂坐骑的**不动**（裁定 #7）。

### 5.2 「持续期」= 效果存续期间

| 项 | 规则 | 依据 |
|---|---|---|
| 持续期 | **效果还在身上就一直在停手**：不是 80 刻、不是 10 秒，也不读任何「停手时长」键 | 裁定 #6；D-181 |
| 效果时长从哪来 | 施加方 `FriendChivesProjectile` 读 `friend_chives.effectTicks`（**默认 200 刻 = 10 秒**，【`FarmstormConfig:879-881`】）当场长，写进效果 | 【卡 §1.4】；D-181 补充 |
| 本版新增的数值 | **0 个**：不新增时长键、不新增注册对象、不改 `friend_chives.effectTicks` | 裁定 #6；D-174；D-183 |
| 恢复判据 | **「效果是否还在身上」**（`hasEffect(Q_BOUNCE)`），不是「进入后过了多少刻」 | D-181 补充；RT-56 |
| 对象 | `Mob` ∧ ¬`Player`：玩家带 Q弹 **不受影响**（玩家不是 `Mob`），mount / render 两种表现照旧 | D-181；§0.4 第 4 条 |

### 5.3 「反复施加」这个事实必须写清

| 事实 | 出处 | 对需求的后果 |
|---|---|---|
| 场每刻重扫落点球体，对球内**所有** `LivingEntity` 重写一次效果 | 【`entity/thrown/FriendChivesProjectile:155-171`】 | 「进入删 AI」的判定点**可能每刻都被再次碰到** |
| 写入的时长是「场长 − 已过刻数」 | 【`FriendChivesProjectile:156`】 | 效果的剩余时长逐刻递减，**不是一个固定值** |
| 原版只在「新时长更长」时更新（已在场者逐刻刷新时 `addEffect` 返回 `false`） | 【`FriendChivesProjectile:176-177`】 | 同一个效果实例会从第一次施加的时长自然走完 |
| 因此：**不能**在第一次施加时配一个一次性计时器 | — | 每刻重扫会把计时器重置（→ 永远不恢复），或反过来在效果还在时提前恢复 |

**两条硬要求**（都由上表推出，标【本文补充】）：

1. **进入点必须幂等**：已有原值记录的实体，不重复记原值、不重置窗口。重复记原值会把「已被本版改成 `true`」的读数当成原值，恢复时把生物**永久锁死**（这正是 40 号 D-179 补充点名的那条坑）。
2. **恢复必须由「效果还在不在」驱动**，且**每刻**都能判：效果没了就恢复，不管它是因为到期、被 `/effect clear`、还是被牛奶清掉。

### 5.4 mount 状态跳过

| 层 | 规则 | 依据 |
|---|---|---|
| 进入时 | 当前是 mount 模式 ⇒ **不删 AI**、已挂坐骑的不动 | 裁定 #7；D-181 |
| 删了之后切到 mount | **先按原值恢复，再挂坐骑**；不得让坐骑带着一个 `noAi` 的实体跑 0 移动 | D-181 补充（第二层由 42 号在「模式切换」这一层落） |
| 判定入口 | 「当前是不是 mount」**只能问** `QbounceMountController`（`isMountMode()` 现为 `private`，【`behavior/QbounceMountController:199`】）；效果类**不得**自己再解析一遍 `qbounce.poseMode` | 裁定 #7；D-181 补充；【卡 §3.4 第 12 行】 |
| 默认值 | `qbounce.poseMode` 默认 **`render`**（【`FarmstormConfig:861-863`】）⇒ **默认配置下 mount 分支不生效**，带 Q弹 的生物**恒停手**；只有把配置改成 `mount` 时才有「跳过」这件事 | 【卡补充】；D-181 |

### 5.5 五条清理路径 + 原值落盘

| 路径 | 期望结果 | 依据 |
|---|---|---|
| 效果**到期** | 到期的同一刻起按原值恢复，**并删除该实体的原值记录** | RT-55；D-181；裁定 #15 |
| `/effect clear` | 手动清除的那一刻起按原值恢复，并删记录 | RT-55；裁定 #15 |
| **喝牛奶**（`MilkBucket`） | 同上 | RT-55；裁定 #15 |
| **实体死亡 / 被移除** | 原值记录随该实体一起删除，不留可被下次读到的残留 | 裁定 #15 |
| **区块卸载** | **保留附件、载入时结算**：卸载时实体不在世界里、改不了 `noAi`，所以不能当场恢复；载入时按附件里的原值恢复并删记录——保留附件**不是**「留在存档里不管」 | 裁定 #15；**A-80** |
| 五种之外：效果被**重新施加**（场还在扫） | 效果还在 ⇒ **不恢复**；只是进入点幂等，不重复记原值 | §5.3；D-179 补充 |
| 效果剩 1 刻时场把时长写更长 | 效果还在 ⇒ 继续停手，不误恢复 | §5.3；RT-56 |
| **读档前后**（RT-54） | 见下（原值随实体落盘，不再依赖内存表） | 裁定 #15；RT-54 |

**原值落盘的口径**（**裁定 #15**）：

1. AI 原值**写在实体上**（`DataAttachment` 一类的持久化面），随实体落盘 ⇒ **跨读档保留**。本版不再需要「内存表」，也不再需要「换服务器实例就整表清空」这类兜底（`trap/TrapImmunity:27-31` 那种形态只适用于不跨档的状态）。
2. 因此裁定 #8「记住进入前的原值、结束恢复原值」**跨读档同样成立**：读档后效果还在就继续停手，效果一没就按**落盘的原值**恢复——「进入前本来就 `noAi`」的实体照样回到 `noAi`，不需要任何「缺失记录时恢复成有 AI」的兜底。
3. **不变量**：「原值记录存在」⇔「本版正持有该实体的 AI」。记录还在、效果却已结束 ⇒ 脏数据（漏清理）；记录没了、`noAi` 还在且无外部原因 ⇒ 丢恢复。两个方向都不允许。
4. **新的风险形态是「落盘残留」**：落盘的东西不会自己消失，**漏掉上表任何一条清理路径**，存档里就留下一份脏记录；该实体下次进入停手时会读到这份旧记录，恢复就写错值。⇒ 五条路径必须穷举，且「按原值恢复 + 删记录」是**同一步**，不许拆成两步。
5. 计数不变：不新增 `data_components`（仍 1 个）、注册对象仍 **97**（附件不属于本版 12 类计数之一，最终由 42 号逐类复核）；落盘载体的具体形态由 42 号定。

### 5.6 边界与异常

| 场景 | 规则 | 依据 |
|---|---|---|
| 效果到期 / `/effect clear` / 牛奶 | 三条都走「按原值恢复 + 删记录」 | RT-55；裁定 #15 |
| 效果每刻被重写 | 进入点幂等：不重复记原值、不重置窗口；**不因「又被施加一次」提前恢复** | §5.3；D-179 补充 |
| 生物在停手期间死亡 / 被移除 | 原值记录随实体删除（第 4 条清理路径） | 裁定 #15 |
| 区块卸载 | **保留附件、载入时结算**（第 5 条清理路径） | 裁定 #15；**A-80** |
| 进入前本来就 `noAi` | 恢复写回 `true`，不放出 | 裁定 #8；裁定 #15 |
| `poseMode=mount` 且生物带效果 | 不删 AI（不动） | 裁定 #7 |
| 生物已被删 AI，配置切到 `mount` | 先恢复、再挂坐骑（§5.4 第 2 层） | D-181 补充 |
| 玩家带 Q弹 | AI 不动；mount / render 表现照旧 | §5.2 |
| 读档后仍带效果 | 原值随实体落盘 ⇒ 继续停手，结束时按**落盘的原值**恢复并删记录；不存在「写 `false`」的兜底 | 裁定 #15；§5.5 |

## 6. R5 陷阱类对敌对生物伤害 ×3

**本节依据：D-182、D-183、D-184（裁定 #9、#10、#11）。**

### 6.1 一句话定位

`trap` 组新增一个**全局倍率键** `trap.damageMultiplier`（double，默认 **3.0**）：**陷阱类作物自己结算的那一次伤害**、**目标属于敌对生物**时，乘上这个倍率。4 个陷阱作物里**只有 2 个真的参与**；玩家与非敌对生物**一律按原值**；各作物段的伤害默认值**一个都不改**。

### 6.2 倍率键

| 项 | 值 | 依据 |
|---|---|---|
| 键名 | `trap.damageMultiplier` | D-183 |
| 组 | `trap`（现有 3 键，【`FarmstormConfig:917-927`】）⇒ **4 键** | D-183；【卡 §3.2】 |
| 类型 | double | D-183 |
| 默认 | **3.0** | D-183；【卡 §3.2】 |
| 范围 | **由 42 号在 D-183 框架内定**（本文不写具体上下界） | D-183；【卡 §7 第 5 条】 |
| 生效面 | 只乘「陷阱自身结算的那一次伤害」× 「目标为敌对生物」这一个组合 | D-184 |
| 不生效的面 | 玩家、非敌对生物、非陷阱爆炸（投掷物的小爆炸、幸运浆果）、尖牙、震动豆 | D-184；裁定 #11 |
| 连带计数 | config **175 → 176** 键、组数仍 **60**；语言键 **337 → 338**（新键的翻译，中英同键同数） | D-183、D-185；【卡 §3.2、§3.3】 |
| 文档义务 | 本键**必须真的写进文档**：`tools/verify_project.py` 的期望键集从 `docs/zh/*` 抽取，文档里没有它就等于没加（A-66 的假绿） | RT-60b；D-185；40 号 §7 ⑦ |

**倍率不是「改默认值」**：`blast_carrot.maxDamage` 仍是 **7**（【`FarmstormConfig:375-377`】）、`zangief_cane.slamDamage` 仍是 **7.5**（【`FarmstormConfig:851-853`】）。玩家在 config 里看到的仍是原值，倍率在结算处乘（裁定 #10 否决「改各作物默认值」）。

**倍率也不是「伤害事件层统一乘」**：那一层拿不到可靠的「这一击是否来自陷阱」身份——`blast_carrot` 与 5 个投掷物用的是**同一个** `farmstorm:crop_blast` 伤害源（`registry/FarmstormDamageTypes:36`），按源判会把瓜！、莫洛托夫等一起乘（D-184 补充；40 号 §6 第 2 条）。

### 6.3 敌对判据

| 项 | 规则 | 依据 |
|---|---|---|
| 判据 | **`net.minecraft.world.entity.monster.Enemy` 实例 ∪ `MobCategory.MONSTER`**（并集） | 裁定 #9；D-182 |
| 为什么是并集 | 原版 `Monster` 已实现 `Enemy`，并集的**实际增量**是两类：「类别是 `MONSTER` 但没实现 `Enemy` 的模组生物」与「实现了 `Enemy` 但在 `MONSTER` 类之外的生物」 | D-182 补充 |
| 已知漏网 | 既不是 `Enemy`、类别也不是 `MONSTER` 的「伪敌对」不吃倍率；本版**不扩判据、不加白名单** | 40 号 §7 ③ |
| 只用在一处 | 只服务 ×3 的闸；**不回改**既有 5 处 `Monster` 过滤（`BlastCarrotTrap:59`、`FangTrapCactusTrap:54`、`VibrationBeanTrap:59`、`ZangiefCaneTrap:174`、`PumpkinTurret:109`）——改它们改的是**触发面** | D-182；RT-57；【卡 §1.5】 |

### 6.4 参与面：4 个陷阱作物，2 个参与

| 作物 | 伤害实现 | 参与 ×3 | 原因 |

| `blast_carrot` | 走 `explosion/FarmstormExplosion`，`entity.hurt` 在 **`:179`**，伤害 = `min(raw, cap)`（公式 `:178`，cap = `blast_carrot.maxDamage` 默认 7） | **参与** | 伤害在本仓结算，目标侧已是 `LivingEntity` 全量遍历（`:159`），只需加一道敌对闸 |
