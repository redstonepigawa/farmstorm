### 0.2 术语表

本节给每个词**判定边界**，不是同义词循环。下游五份文档遇到这些词，一律按本节边界用。

**控制终端**
：本版新增的方块 `farmstorm:control_terminal`，中文名「控制终端」。判定边界：它**不是**「据点核心」——核心是存储与归属的载体（`OutpostCoreBlockEntity`），终端不存物品、不存归属；它也**不是**「农作物培养器 / 农作物转换器」——那两台是执行机器，终端只负责把核里的东西搬给它们。

**控制面板**
：控制终端右键打开的界面（0 槽界面 + 1 个新 `MenuType`）。判定边界：它**不是**「据点核心的 54 格存储界面」（`OutpostCoreScreen`，那个只从核心右键打开）；面板里**没有任何槽位**，不显示、也不能搬动核里的物品。

**模式（Mode）**
：控制终端自己的三态 `OFF / CULTIVATOR / CONVERTER`，只存终端方块实体的 NBT。判定边界：它**不是**核的属性（裁定 #1 否决存核侧）；`OFF` 是一个真实状态，不是「两个都为假」的推导结果——枚举里就是三个值。

**投料**
：终端每一轮从核的 54 格里取出**恰好 1 个**物品放进某台空槽机器。判定边界：它**不是**「搬运整摞」、**不是**「把机器产出送回核」（那是机器自己的 `deliver()`）、也**不是**「填充任意槽位」（机器只有 1 个投入槽）。

**核储存空间**
：`OutpostCoreBlockEntity.java:138-139` 的 54 格 `NonNullList`，类本身实现 `Container`（`:62`）。判定边界：它**不是** 24 个绑定名额（`cultivators` 是名额，54 是格子数，两者不同义）；也**不是**玩家背包的延伸。

**名额**
：核侧 `cultivators` / `cultivatorKinds` 两条平行列表的长度上限，读 `outpost_core.cultivatorCapacity`（默认 24）。判定边界：控制终端**占一个名额**（裁定 #5），与培养器、转换器同一份名单；名额满时终端既不能绑定、也不投料。

**处理方块（processing_block）**
：`farmstorm:processing_block` 标签的成员，本版 2 → 3。判定边界：标签只承担**发现**（`OutpostCoreBlockEntity.java:887-892` 的 `state.is(...)`）；「这台机器是哪一个类型」仍由 `:123-125` 的 `KIND_BY_BLOCK` 单独决定——按标签发现**不等于**标签里存了类型。

**可挖门槛**
：本版起 `processing_block` 的三个成员都必须「石镐及以上」才能挖出掉落物，由 `#minecraft:mineable/pickaxe`（管挖速）+ `#minecraft:needs_stone_tool`（管是否正确工具）两条标签共同表达。判定边界：**金镐算不算「以上」由原版 `incorrect_for_gold_tool` 决定，本版不改那条标签**，因此本文不写金镐的断言（§8 第 1 条）。

**位置记录**
：`PuffedHayData` 里的 `BlockPos.asLong` 集合，记的是「膨胀麦写进去的那一格干草块」。判定边界：它**不是**「所有干草块」、**不是**「压缩干草块」（那是我方方块，由 `CompressedPuffedWheatProjectile.java:33-36` 写入），也**不是**方块实体（原版干草块没有我们的方块实体）。

**绿色连线**
：控制终端与核心之间那条线，`Kind.TERMINAL` 的渲染后果。判定边界：线**只由 payload 的一个字节决定**，渲染层不按坐标反查方块（`CultivatorLinkRenderer.java:39-41`）；绿色**不是**「培养器的青色」（那是 `(0.30, 0.85, 0.90)`）。

### 0.3 四字段写法

每条决策固定四项，**缺一不可**，顺序固定：

| 字段 | 写什么 | 不许写什么 |
|---|---|---|
| **结论** | 一句话、祈使句、可直接执行 | 条件句、备选句、「可以考虑」 |
| **依据** | `BRIEF` §2 的裁定编号，或 `文件:行号`；两者都给最好 | 「因为合理」「符合直觉」 |
| **落地位置** | 要改的 `路径` 或 `类#方法` | 代码片段、算法步骤 |
| **补充** | 连带影响 + 否决掉了哪些替代方案 | 实现细节（那是 66 号的事）、任务排期（那是 67 号的事） |

九条写作纪律：

1. **「本文补充，作者可否决」标记**：凡由本文推导、而非 `BRIEF` 直接给出的口径，在该句前标出。带标记的条目可被作者否决；不标的等于转写裁定，否决它等于否决作者。
2. **数字纪律**：所有数值只能追到 `BRIEF` §0 / §2 / §3，或两个已给数值的算术（92 + 4 = 96、321 + 7 = 328、151 + 5 = 156、28 + 1 = 29、89 + 4 = 93）。需要新数值的写「由 66 号定」，本文不自己编。
3. **禁用词**：不出现「您」、TODO、待定、待办、TBD；不写「正常」「手感」「合理」。
4. **表格纪律**：每张表首尾有 `|`，逐行列数一致。
5. **行号纪律**：本文引用的行号一律按 UTF-8 实读源码核过；子代理报告而本文未复核的，在 §8 点名。
6. **只引上游，不改上游**：发现 `BRIEF` 或既有文档有错，写进 §8 并报给作者，不去改别人的文件。
7. **plan 原文不得直接当行为描述用**；差异逐条登记在 §7。
8. **已知影响必须成文**：玩家能感知的变化写成「不是缺陷，是裁定的后果」（D-280、D-282、D-285、D-267）。
9. **中文名为基准**（裁定 #12）：首次出现写「中文名（英文 id）」，之后只用中文名。
