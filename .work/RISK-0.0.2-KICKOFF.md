# v0.0.2 开工前风险清单

> 依据：对 `docs/{zh,en}/10~15-*.0.0.2.md` 的逐项核验（编号连续性、跨文档数字、中英对称、素材实体、0 包/Mixin 约束），
> 加上 v0.0.1 实施期间真实踩过的坑。**本文只列风险与验证动作，不含实现方案**——方案在 `12-TECH-0.0.2.md`。
>
> 每条写四段：**危险在哪 / 早期信号 / 缓解动作 / 归属任务**。

## 0. 先说结论

文档本身没有硬伤（30 条决策连续、40 个任务闭合、77/139/261 全链自洽、零自定义包与无 Mixin 都有实际维持机制）。
真正会咬人的是**三个客户端子系统**和**两个"文档自己标了未验证"的技术点**。按 §9 的顺序开工，能把返工压到最小。

## A. 客户端三件套（最高风险，全部是 0.0.1 完全没碰过的面）

### A-1 · 整屏灰度（D-61 / RT-10）
- **危险**：要求"真灰度且**含 GUI**"，但 GUI 是分帧批处理的。挂错阶段会出现：只灰了世界没灰 HUD、或灰度被后续 GUI 绘制盖掉；与光影/其它 UI 模组叠加顺序不定；窗口 resize 或 GUI 缩放变化时全屏 quad 尺寸错位，露边。
- **早期信号**：文字变灰但图标不变色；打开背包后灰度消失；GUI 缩放 200% 时屏幕边缘出现未覆盖细条。
- **缓解**：在 `RenderGuiEvent.Post` 的最后阶段提交全屏 quad；尺寸按 GUI scale 计算而非硬编码；验收用**截图**，覆盖 {GUI scale 2/3/自动} × {光影关/开}。
- **归属**：F-8x（灰度簇）

### A-2 · 红色剪影（D-62 / RT-11）
- **危险**：在 `RenderLivingEvent.Post` 重绘模型等于**同帧二次提交几何**。`PoseStack` 若未严格 push/pop 会污染后续实体渲染；深度/透明处理错会出现剪影闪烁或穿墙可见；"≤64 格"需要自己剔除，否则远处怪也变红。
- **早期信号**：无关实体跟着发红；剪影忽隐忽现；F3 帧时间明显上升。
- **缓解**：严格 `pushPose`/`popPose`；复用主渲染的变换矩阵；先距离剔除再提交；验收看截图 + 帧时间对比（同一场景开/关对比）。
- **归属**：F-7x（剪影簇）

### A-3 · 输入锁（D-60 / RT-13）—— **文档自己标了未验证**
- **危险**：`InputEvent.Key` 与 `KeyMapping` 的**先后顺序在 1.21.1 未实测**，快捷栏 1–9 可能拦不住；攻击/使用走 `InteractionKeyMappingTriggered`，但鼠标左键**长按持续挖掘**是另一条路径；"只留 ESC"必须真的留（否则玩家以为游戏卡死）。
- **早期信号**：锁定期间还能换物品 / 还能挖方块 / 按 ESC 无反应。
- **缓解**：开工时**第一件事**写最小复现——锁定状态下逐键手测 WASD / 空格 / shift / 1–9 / 滚轮 / 左键点按 / 左键长按 / 右键 / E / Q / ESC，并把结果写成一张表存档。拦不住的那一路改挂更靠前的钩子（`ScreenEvent.KeyPressed`）。
- **归属**：F-92。**建议按 `13-TASKS` §11 的优化把它的前置从 F-88 改成 F-64 + F-87**，这样它不必等三相位状态机，可以提前验证。

## B. 相位同步（D-50 / RT-15）—— **文档自己标了未验证**
- **机制**：不许自定义网络包 → 用隐藏 `MobEffect` 的 amplifier 充当相位号。
- **危险**：`MobEffectInstance#update` 的合并规则未验证，文档用"**先移除再加**"绕开，代价是每次切换多 2 个原版包，且**客户端可能出现一帧效果短暂消失**。若客户端 tick 恰好在"移除"与"添加"之间读状态，会漏掉该相位——桑吉尔蔗有 3 个相位，漏一个就是动画断档。
- **早期信号**：相位切换瞬间屏幕闪一下；循环音重启；相机姿态卡住一帧。
- **缓解**：客户端读状态时**保持上一相位直到读到新值**（迟滞），不要读到空就清状态；把相位切换打日志（相位号 + 刻数），出问题能一眼看出漏了哪一段。
- **归属**：F-88 / F-93

## C. 客户端预测 vs 服务端权威的橡皮筋
- **机制**：狂野猎人位移由客户端先动，服务端独立再算一遍；文档明确**不下发** `ClientboundSetEntityMotionPacket` 去纠正。
- **危险**：两边判定不一致时（高延迟 / 视线 / 目标已死），客户端已经冲出去而服务端认为没冲 → 要么被原版逻辑自行拉回（体验断裂），要么长期位置偏离（更糟：服务端视角可能穿墙）。
- **早期信号**：高延迟下冲刺后突然回弹；客户端命中但服务端没结算；目标在服务端已死仍被冲。
- **缓解**：预测必须有**服务端回执**（哪怕只是一个 effect 状态变化）；不一致时兜底是"客户端接受服务端最终位置"，而不是强行抑制原版纠正；回归用高延迟模拟（`/tick rate` 或人为丢包）而不是只在本机跑。
- **归属**：F-76 ~ F-85

## D. 冻结面与白名单的边界（**最容易翻车，且最容易误判**）
- **事实**：D-49 冻结的是 **v0.0.1 的文档**（`docs/*/00~09`）；BRIEF §3.3 的白名单是**允许修改的既有代码文件**。两者管的对象不同，但字面都写着"冻结/不许动"。
- **危险**：混淆会导致两种相反的错——① 不敢改白名单内的文件（比如不敢给 `PuffedWheatProjectile` 抽 `fillBlock()` 扩展点），绕路写成复制粘贴；② 顺手改了白名单外的文件。
- **早期信号**：`git diff --stat` 里出现 `docs/*/00~09`，或出现白名单外的既有文件。
- **缓解**：每次提交前跑一次 `git diff --name-only HEAD` 自查，只允许「白名单内既有文件 + 新增文件」；建议把这条规则做进 `verify_project.py`。
- **归属**：F-60

## E. 校验脚本必须先升级，否则每次构建都红
- **事实**：`tools/verify_project.py` 目前硬编码 **117** 个 config 键、**222** 语言键、**64** 注册 ID、**261** 资源。
- **危险**：0.0.2 一变（139 / 261 / 77），校验脚本立刻全红。**这是"验收工具坏掉"类风险**，最容易被当成"改动有 bug"而浪费几轮排查。
- **缓解**：F-60 的第一件事就是把这些数字从硬编码改成**从文档现算**（或集中成一个常量块并注明出处），然后再动任何业务代码。
- **归属**：F-60（前置）/ F-99（最终核对）

## F. 压缩干草块 6.0 抗性的连锁矩阵（HC-21）
- **危险**：压缩干草块抗性 6.0 与瓜片子/瓜！的阈值 6.0 **正好相等** → "≥6.0 不破"意味着**两件破障类打不破压缩干草块**；膨胀麦系列则走 3.6e6 底线。矩阵写反的直接后果是"破障类打不破自家方块"或反之。
- **早期信号**：拿瓜！炸压缩干草块，块碎了（若预期是不碎就写反了）。
- **缓解**：把它做成一张明确的矩阵表并配一条**运行时验证**：摆一块压缩干草块，分别丢瓜！和育碧服务器，记录方块存活与否；结果与表逐格比对。
- **归属**：F-67 / F-99

## G. 音频管线
- **事实**：`tools/convert_media.ps1` 已就位并实测过（三个源→两个 ogg + 一张 png）；但 **`sounds.json` 还不存在**，两个 ogg 目前是死文件。
- **危险**：① 忘建 `sounds.json` → 音效静默失败且**不报错**；② 1.78 MB 循环音会让 jar 从 336 KB 涨到 ~2 MB；③ 客户端 `SoundInstance` 生命周期若与效果不同步，会出现"效果结束音还在"或重入叠播。
- **缓解**：`sounds.json` 与 `SoundEvent` 注册放在同一任务内完成，并当场用 `/playsound farmstorm:...` 验证；jar 体积写进验收（预期约 2.1 MB）。
- **归属**：F-94 / F-76

## H. 素材版权与许可（转公开前必须处理）
- **事实**：两个音频来自第三方（SF6 片段、非原创 `Animals.mp3`），图标来自桌面 JPG。
- **危险**：现在仓库私有，没问题。你已说明「以后可能转公开、可能不止自用」——**非商业 ≠ 无风险**，第三方游戏音频的再分发在公开仓库里仍可能被投诉。另外**代码许可仍是「未定」**，转公开等于保留所有权利。
- **缓解**：已在 `README.md` 新增「素材来源与非商业声明」节（含来源表、四条使用条件、转公开前的二选一建议）。转公开时还需要：补 `LICENSE`、把该节内容复制进 Release 说明。
- **归属**：作者决策；F-99 发布前检查

## I. 从 v0.0.1 带来的三条验收纪律（写进本轮）
1. **伤害类验收必须同时给"实测值"和"config 上限"**——0.0.1 曾出现胡罗贝只打 1 点，却因为只确认"掉血了"而放行。
2. **客户端/渲染改动必须截图级证据**，不接受"代码看起来对"。
3. **临时探针删净要查三处**：源码、`build/classes`、jar 内（`*Probe*` = 0）。

## 10. 建议的开工顺序（按"先证伪最贵的假设"排）
1. **F-60 基座 + 升级 `verify_project.py`**——先把验收工具对新数字弄准，否则后面每一步都在噪音里排查。
2. **输入锁最小复现**（A-3 / RT-13）——这是唯一"可能根本走不通"的技术点，越早证伪越省事。
3. **灰度与剪影各自先做 PoC**（A-1 / A-2）——渲染层最耗时间，先拿到能看的画面再谈集成。
4. **相位同步（B / RT-15）**——在效果类落地时就把"先移除再加"的可见副作用测出来。
5. **音频管线（G）与素材替换方案**同推——`sounds.json` 是小事，版权是决策。
