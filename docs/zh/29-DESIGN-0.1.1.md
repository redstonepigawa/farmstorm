## 0. 阅读约定

### 0.1 本文件与 28 号的分工

28 号定**口径**（一句话结论 + 依据 + 落地位置 + 连带），本文写**长什么样**（范围、格式、时序、数值、边界、验收时才看得见的行为）。三条分工纪律：

1. **口径不在这里发明**。本文每一个结论后面都挂决策号（`D-1xx`）；读者若发现某个结论追不到决策号，那就是本文的缺陷，不是可以自行解释的空白。
2. **28 号的正文不复述**。本文引编号，不抄结论句；需要读者「先读 28 号第几条」的地方直接写编号。
3. **哪些东西不在这里**：config 全表（30 号）、类设计 / 网络包 codec / 存档二进制格式（30 号）、任务编号与工时（31 号）。本文只在「依据」一列里点出 config 键名与默认值。

### 0.2 「本文补充」的判定标准

| 类型 | 允许标「本文补充」 | 说明 |
|---|---|---|
| 算术 | 是 | 由两个已给数值算出来的第三个数，必须写出算式（例：`15 − 0 = 15`） |
| 28 号明确授权 | 是 | 28 号写了「由 29 号定」的（行距、字号、内边距、「+N」字形、钳制表达式、配色） |
| 上游没覆盖的读法 | 是 | 必须同时给出「为什么只能这么读」，并登记进 §11 的边界清单 |
| 事实卡已给、作者未拍板 | 标「卡补充（可否决）」 | 例：8 行上限、默认 `(4,4)`、自己绿队友白、维度 path。**不算本文原创**，作者可否决 |
| 与 28 号或事实卡冲突 | **不许** | 冲突只能回报作者，不能自己选一个写进去 |
| 审美偏好 | **不许** | 「我觉得好看」不是理由，必须给可判定的判据（可读性、与既有元素的区分度、像素账） |

本文里一个数只有四种合法来源：28 号写着的、事实卡写着的、带算式的算术、或标了「本文补充」并给了理由的。四种都不是，就是文档缺陷。

### 0.3 标注法

| 标注 | 含义 |
|---|---|
| 【D-1xx】 | 结论来自 28 号的对应决策 |
| 【卡 §1.x】 | 结论来自事实卡的对应小节 |
| 【`路径:行号`】 | 直接来自源码的一行，路径相对 `src/main/java/com/dashpig/farmstorm/`（资源与工具另注） |
| 【本文补充】 | 按 0.2 的六条判定，由本文推导 |
| 【卡补充】 | 事实卡 §2 表下注的「非作者裁定，可否决」项 |

**与 23 号英文版的差异（有意为之）**：29 号的**英文版**把上述标记写成英文方括号（`[author's supplement]` / `[card]` 等），**不**用 `【】`——英文文档里出现中文标点是上一轮遗留的体例瑕疵，本版不复用；中文版继续用 `【】`，两版的标记**一一对应、语义相同**，不是漏译。

### 0.4 单位

## 2. 狂野苹果材质（R1）

**本节依据：D-125、D-126。**

### 2.1 一句话定位

`textures/item/wild_apple.png` 换成 `wild_apple_64x64.png` 的**原样输出**：不降采样、不再走 16 网格众数取色、不再叠绿色「+」。**同时**改生成器的六处回滚点（§2.6），否则下一次重跑就把这张图换回 16 × 16。模型、物品 id、语言键、注册面一律不动。

### 2.2 两张图各自是什么（实测）

| 项 | 现图 `textures/item/wild_apple.png` | 源图 `wild_apple_64x64.png` |
|---|---|---|
| 尺寸 | 16 × 16 | 64 × 64 |
| 文件大小 | **571 B** | **6,946 B** |
| 去重 RGBA | **88** | **1,814** |
| 全透明像素 | **107** / 256 | **1,471** / 4,096 |
| 不透明像素 | **149**（= 256 − 107，【本文补充】算术） | **2,625** |
| 半透明像素 | 0 | 0 |
| alpha 包围盒 | — | x ∈ [2, 60]、y ∈ [0, 63] |
| 绿色「+」 | **有**：33 px 的 `#3FA34D`，落在 x ∈ [9, 15] × y ∈ [9, 15] 的 7 × 7 十字 | 无 |
| 是否 4 × 最近邻放大 | — | **不是**：256 个 4 × 4 块里 **204** 块不均匀 |

【卡 §1.1】给全部像素统计；「现图不透明 149」是 256 − 107 的算术，【本文补充】。

那个 33 px 的十字是**自洽的**：`7 × 3 + 3 × 7 − 3 × 3 = 21 + 21 − 9 = 33`，也就是说它是一枚 **3 px 宽**的十字，正好落在右下角 `left = 9 / top = 9`【`tools/gen_textures.py:612-623`】【本文补充：算式】。这解释了为什么「现贴图本来就带 `+`」——它不是画师画的，是生成器贴上去的。

### 2.3 「直接原图」意味着什么（三件事）

| # | 含义 | 反例（本版不做的） |
|---|---|---|
| 1 | 入库 PNG 就是源图的逐字节副本：不改尺寸、不量化、不动 alpha | 0.1.0 的「缩到 16 × 16 + 众数取色」 |
| 2 | 生成器对 `wild_apple` **不再进** `wild_apple_grid()` 的 16 网格取色【`tools/gen_textures.py:849-881`、`:884-895`】 | 保留取色、只在取色后「补细节」 |
| 3 | 生成器对 `wild_apple` **不再叠** marker【`tools/gen_textures.py:407`、`:974-975`】 | 保留叠图、只把 marker 改成透明 |

不改的东西清单：`models/item/wild_apple.json` 的 `parent = minecraft:item/generated` 与 `layer0 = farmstorm:item/wild_apple`【`models/item/wild_apple.json:1-6`】、物品 id、语言键、注册面、`ICONS` 表里的条目本身（`zh_name` 等元数据照旧）。也不新增第二张贴图。

### 2.4 渲染事实：看不到 4 倍细节（RT-37）

这一节是给作者的**预期管理**，不是实现细节。

1. `item/generated` 的物品模型是一个 **1 × 1 模型单位的 quad**，在物品栏里被画进一个 **16 × 16 GUI px** 的物品格。所以**显示面积恒为 16 × 16**，与贴图分辨率无关。
2. 64 × 64 的贴图塞进 16 × 16 的显示面积，等于每个显示像素平均 `64² ÷ 16² = **16**` 个源像素（4 × 4 块）【本文补充：算术】。过滤与 mipmap 会把这块面积压成一个颜色。
3. 所以玩家看到的仍然是「一张 16 × 16 的图标」，只是它的每个像素来自原图的真实像素，而不是 88 个离散色档里的众数。**这不是 4 倍锐度，是更准的色调与更自然的过渡。**
4. 反例核对：如果源图只是 16 × 16 的 4 × 放大，那么 256 个 4 × 4 块应该块块均匀；实测 204 块不均匀【卡 §1.1】⇒ 这张图的细节是真的，只是**显示不出来**。
5. 结论一句：换图的价值在「原图的构图与色彩层次」，不在「分辨率」。任何「换成 64 × 64 就能看清细节」的表述都是错的（D-126 补充把这条列进 29 / 30 的必写项）。

### 2.5 「+」号规则作废的范围与落地节奏

| 层面 | 本版做什么 | 依据 |
|---|---|---|
| 规则 | **全局作废**：`NO_PLUS_ICONS` / `add_plus` / `build_marker` / `compose_icon` 与合成分支一并删 | D-125 |
| 图 | **只重生成 `wild_apple` 一张** | D-125 |
| 其余 | 26 条里 25 张带 `+`、只有 `converter` 免叠【`tools/gen_textures.py:274-275`】⇒ 本版处理后**仍有 24 张是旧样**（25 − 1 = 24） | D-125 补充 |
| 下版 | 批量重生成那 24 张，不需要再改任何决策（规则已经不在代码里了） | 28 号 §7 第 1 条 |
| 判定边界 | 「规则作废」≠「本版所有图标都不带 `+`」 | 事实卡 §6 第 7 条 |

### 2.6 生成器会覆盖的陷阱（六处，逐处点名）

**这一节是本条的验收重点**：只换 PNG 一定失败，因为有三条独立的回滚路径。

| # | 承载点 | 只换 PNG 会怎样 | 证据 |
|---|---|---|---|
| 1 | `wild_apple_grid()` 的 16 网格众数取色 | 重跑时按 16 网格重新取色，输出回 16 × 16 | `tools/gen_textures.py:849-881`、`:884-895` |
| 2 | `TEXTURE_SIZE = 16` 与 `compose()` 的归一化分支 | 即使直通分支返回 64 × 64，也会被 resize 回 16 × 16 | `:59`、`:976-978` |
| 3 | `expected_size()` 与 `main()` 里的尺寸断言 | 直通改了 `compose()`、没改这里 ⇒ 构建直接 `SystemExit`（`尺寸断言失败`） | `:982-983`、`:1153-1154` |
| 4 | `WILD_APPLE_SOURCE` 默认指向桌面旧图 | 重跑取错素材（旧图 → 众数 → 16 × 16） | `:154`、`:155`（环境变量可覆盖） |
| 5 | `build_marker()` 的调用点与 dry-run 文案 | 删了函数不删调用点 ⇒ 运行时名字不存在；不删文案 ⇒ dry-run 仍打印「+ 绿色「+」」 | `:1127`、`:1141-1142` |
| 6 | `compose_icon()` | 删了叠图机制不删调用点 ⇒ `:975` 引用的函数不存在 | `:612-623`、`:974-975` |

三条判据（验收时逐条过）：

1. 删掉入库的 `wild_apple.png`、重跑生成器，产出的文件必须是 **64 × 64** 且与源图逐字节相同。
2. 同一次重跑里，其余 24 张带 `+` 的旧图**不得**被改动（本版不重跑其余张）。
3. 重跑两次的产物逐字节相同（生成器没有随机数与时间戳依赖）。

## 3. 耕地-核心绑定制（R2 / R3）

**本节依据：D-134、D-135、D-136、D-137、D-138、D-139、D-140。**

这是本版最大的设计变化，也是唯一一处「换掉了一整套数据关系」的改动。R2 与 R3 两个 bug 都由这个结构变化根治，**不是各修一个判据**。

### 3.1 一句话定位

耕地与核的关系从「**范围内即受管**」换成「**显式绑定**」：一块地同一时刻只归 **1 个**核，一个核最多管 **16 块**；「这块地归谁」从此是一个**存储的事实**，不再是一次运行时计算。两个 bug 的症状分别是「拆核连带铲」与「下线即失保护」，它们共同的成因是 0.1.0 用「范围 + 在线玩家」来回答「这块地归谁」——答案换了载体，两个症状的成因同时消失。

### 3.2 实体关系（文字版）

```
玩家（UUID，可离线）
  │  放置：写 ownerUuid + ownerName + placedGameTime
  ▼
据点核心（维度 + 坐标，一个方块实体一核）
  │  ── 容量 16 块（outpost_core.farmlandBonus）
  │  ── 1 个核 : 0..16 块耕地
  ▼
耕地（维度 + 坐标）
  · 绑定：同一时刻只绑 0 或 1 个核（不存在 2 个，这是与 0.1.0 范围覆盖的根本差别）
  · 归属者：锄地的那个人（UUID），可以离线
  · 无绑定 ≠ 不存在：照样能种，只是不受保护
```

| 关系 | 基数 | 存什么 | 判定边界 |
|---|---|---|---|
| 玩家 → 核 | 1 : 0..2 | 核的 `ownerUuid` + `ownerName` | 每人最多 `outpost_core.maxPerPlayer`（默认 2），0.1.0 的 D-122 继续有效【28 号 §5】 |
| 核 → 耕地 | 1 : 0..16 | 绑定表 | 容量即 `outpost_core.farmlandBonus`（默认 16），**不新增 config 键**（D-134） |
| 耕地 → 核 | 1 : 0..1 | 绑定表（反查） | 不存在 2 个（D-134） |
| 耕地 → 耕地主 | 1 : 1 | 账本 `byOwner` | `byOwner` 不再单独落盘，是绑定表的派生视图（D-134 补充） |
| 核 → 维度 | 1 : 1 | 坐标自带维度 | 主世界的 `(0,0)` 与下界的 `(0,0)` 是两个核，互不覆盖（D-143 同向） |

### 3.3 绑定何时发生（锄地那一刻，四步）

| 步 | 判据 | 不满足时 | 依据 |
|---|---|---|---|
| 1 | 目标格能变成耕地（草方块 / 土径 / 土 + 上方空气） | 不动作（0.1.0 既有，本版不改） | `farmland/FarmlandGuard.java:55-63` |
| 2 | 目标格落在某个**己方**核的 3 × 3 影响范围内（范围闸保留） | `NO_CORE` 提示，**不扣耐久** | 0.1.0 的 D-118 未被作废；D-135 补充 |
| 3 | 候选集 = 「覆盖这一格的核」∩「己方」∩「仍有空位」；在候选集里取**最近**；平手按 `placedGameTime` **升序** → **维度 id** → 核坐标 `(x, y, z)` 的**字典序**（三级比较键） | `QUOTA_FULL` 提示（含义已变，见 §3.4） | D-135；平手半句按**裁决 A-39** 修订（三级键） |
| 4 | 写绑定 + 记账 + 放耕地（同一 tick 内完成） | — | D-135 落地位置 |

**候选集是先过滤、再取最近**（【本文补充】，读法说明）：D-135 把「必须覆盖」「必须有容量」写成候选核的前提条件，把「最近」写成排序规则；若先取最近再判它有没有空位，「最近的核满了、但另一个覆盖这一格的核还有空位」会被误拒——那与 D-139 的 `16 × 核数` 总额度直接矛盾（额度允许 32 块，实际只放出 16 块）。D-136 的迁移用的是「三个条件同时成立才迁移 + 多个候选最近优先」，与这里同构。

**平手判据（裁决 A-39 修订 D-135 的「平手按先放置」半句；比较键为三级，28 号原文不改，以 A-39 为准）**：按 `placedGameTime` 升序 → **维度 id**（`minecraft:overworld` / `minecraft:the_nether` / `minecraft:the_end` 的字符串序）→ 核坐标 `(x, y, z)` 字典序，依次比较。**必须三级的原因**：两个不同维度的核可能同一刻放置、坐标也完全相同（主世界 `(0, 64, 0)` 与下界 `(0, 64, 0)`），两级键会在这一格并列；加上维度 id 之后，任意两个不同的核都能分出先后，比较键成为**全序**，「平手」在实现里不会退化成「随便挑一个」。**不得依赖任何 Map / 列表的插入顺序**——`OutpostCoreIndex.byOwner` 是 `HashMap`（`outpost/OutpostCoreIndex.java:53`），跨 owner 的迭代顺序不稳定，拿它当次序会让「同样两个核、两次判定绑给不同的核」。三级键对同一份存档的任意两次运行给出同一个答案，**这是可复现性的前提**：老档补建、核被毁时的迁移、以及复现测试都要求「同样的世界状态 ⇒ 同样的绑定结果」，否则同一个存档在两次启动后可能得到两套归属。`placedGameTime` 已落盘可复核；**不为比较去加载候选核所在的区块**（D-135 补充）。

### 3.4 容量 16 的语义

**容量与额度是两个词，同一个源头，不同含义**（D-134 补充、RT-33）：

| 词 | 是什么 | 不是什么 | 依据 |
|---|---|---|---|
| 核心容量 | 一个核能管的耕地块数上限，单位是「块地」，是**绑定名额** | 不是玩家额度、不是影响力半径、不是「+16 额度」的旧语义 | D-134 |
| 额度 | `16 × 己方核数` | 不是 `base + 16 × 核数`（base 概念已整体删除） | D-139 |
| 已用 | 绑定表里己方名下的块数 | 不是「范围内所有耕地」 | D-139 补充 |
| 两者关系 | 额度恒等于各核容量之和 | **不是两道独立的闸** | 【本文补充：算术 + 推理】 |

**为什么不是两道闸**（【本文补充】）：每块地必须绑到**一个**核，每个核至多 16 块 ⇒ 任意时刻「己方名下已绑定的块数」≤ Σ 容量 = 额度。所以「总额度」永远不会先于「单核容量」触发；玩家实际撞上的那道墙永远是「覆盖这一格的己方核都满了」。D-139 的算式仍然必须写进文档，因为它是额度的**定义**、也是浮窗与提示文案的取数口径，但它不构成第二道运行时判据。

五个算例（把语义钉死）：

| 场景 | 核数 | 额度 | 单核容量 | 实际能开垦 | 算式 / 说明 |
|---|---|---|---|---|---|
| 单人、没有核 | 0 | **0** | — | **0** | 16 × 0；开局谁都耕不了地，但原因不再是 base = 0（D-139 补充） |
| 单人、1 个核 | 1 | **16** | 16 | **16** | 16 × 1 |
| 单人、2 个核且两核范围不重叠 | 2 | **32** | 每核 16 | **32** | 16 × 2 |
| 单人、2 个核但地全在 A 的 3 × 3 里 | 2 | **32** | A 16 / B 16 | **16** | 第 17 块时 B 不覆盖它 ⇒ 无候选 ⇒ 被拒 |
| 同一格同时被 A、B 覆盖且 A 已满 | 2 | 32 | — | 仍可开垦 | 绑到 B（§3.3 第 3 步的过滤后取最近） |

### 3.5 迁移时序（核被毁 → 找接替 → 找不到变泥土）

| 步 | 条件 / 时刻 | 做什么 | 世界是否变 |
|---|---|---|---|
| 1 | 核方块**真的**被移除（不是区块卸载、不是停服） | 取出该核名下的绑定记录集合 | 否 |
| 2 | 对每条记录 | 判方块是否仍是耕地（读不到时按 §3.10 降级，不是「跳过」） | 否 |
| 3 | 搜索接替者 | 三条同时成立：影响范围覆盖该耕地 ∧ 与**耕地主**同盟 ∧ 仍有空位；多个候选**最近优先**、平手按 `placedGameTime` 升序 → 维度 id → 坐标字典序（三级键，裁决 A-39） | 否 |
| 4a | 有接替者 | **改绑**：写新核，方块不动、不掉落、不通知耕地主 | 否 |
| 4b | 没有接替者且能读到方块 | `setBlock(DIRT)` + 摘绑定 | **是**（唯一会动世界的分支） |
| 4c | （不可达，见 A-60）没有接替者且读不到方块 | 实际走「变泥土」（同 4b）；「只摘绑定」保留为票缺失等异常下的防御分支（见 §3.10） | **是**（同 4b） |
| 5 | 全部处理完 | 释放该核的区块 ticket（D-145）、摘索引条目、更新浮窗列表 | 否 |

三条纪律：

1. **先算完集合、再动世界**：沿用 0.1.0 的既有理由（避免边遍历边改账本），D-136 补充明确保留。
2. **只处理本核名下的耕地**，不再遍历在线玩家——0.1.0 的那趟遍历正是 bug 2 的另一半（§3.7.2）。
3. **「变泥土」是唯一的世界写入**：不新增掉落、不给补偿、不通知。迁移成功时玩家看到的是「田换了主人」，不是「田没了」。

### 3.6 老存档补建时序（启动时跑一次）

| 步 | 时刻 | 做什么 |
|---|---|---|
| 1 | 服务端启动 | 读 `world/data/farmstorm_farmland.dat`；旧格式（只有 `byOwner`）走兼容读入 |
| 2 | 加载完成 | 每条旧记录变成「有主、**无绑定**」的耕地 ⇒ 语义上就是「待补建」 |
| 3 | 补建 | 对每条无绑定记录跑**与 §3.5 第 3 步完全相同**的谓词（覆盖 + 同盟 + 有空位，最近优先） |
| 4 | 绑上了 | 写绑定；世界不动 |
| 5 | 绑不上 | **保持耕地、保持无绑定**（不受保护）——绝不铲老存档 |
| 6 | 补建结束 | 本次启动不再补；运行期新开垦的耕地走 §3.3 |

两条必须写明的读法：

1. **谓词复用是本文补充**：裁定 #15 只说「按新规则补建」，而新规则里给出完整谓词的只有 #14（D-136）。复用它是唯一不发明第三套判据的做法；若作者希望补建更宽松（例如只按同盟 + 就近、不看范围），改的是 D-137，不是本文（28 号写作期回报第 3 条已登记）。
2. **补建的遍历顺序决定老档结果，因此必须是确定序**（【本文补充】，按裁决 A-39 的禁则收紧；排序键按 **A-47 rev.2** 取 `BlockPos` 单级全序）：容量 16 是硬顶，所以「哪些老田能绑上」由遍历顺序决定。不得用账本的 `HashMap` 迭代顺序（跨 owner 不稳定，见 §3.3）：改为**先把全部无绑定耕地按 `BlockPos` 全序（y → z → x）排序，再逐条处理**——账本条目只有 `pos`、没有维度字段（`farmland/FarmlandLedger.java:46-48`），同一 `pos` 在账本里只有一条，故单级即全序（A-47 rev.2）。**这与 §3.3 的候选核三级键不是同一套，两处写法不同是有意的、不是笔误**：核的索引条目带维度（`outpost/OutpostCoreIndex.java:50` 的 `record Entry(ResourceLocation dimension, BlockPos pos)`），两个不同维度的核可以同坐标，所以核之间要先按维度 id 分先后；耕地在账本里只有 `pos`，硬加一级维度与存档事实不符。同一份存档任意两次启动都给出同一套绑定；而这个顺序看起来像细节，实际决定老档里哪些田在升级后**看起来**没变、哪些变成不受保护。账本无维度字段还带来一个既有边界：**跨维度同 `BlockPos` 的耕地无法区分**，本版**不修**（A-49），理由是 plan 未要求、老档无法回溯维度、且耕地侧已叠一次存档升版；落点见 30 号 §9 已知限制与 32 号陷阱章。

### 3.7 两个 bug 为什么被根治

#### 3.7.1 bug 1（多核重叠误清算）的因果链

0.1.0 的清算判据是三条：① 目标格在该核的 3 × 3 区块内；② 方块仍是 `minecraft:farmland`；③ 归属者是核主本人**或其在线队友**（`blockentity/OutpostCoreBlockEntity.java:353-366`、`:369-379`）。

1. 三条里**没有一条**问「这块地是不是**只**归这个核」。
2. 于是一块地同时落在 A、B 两个核的 3 × 3 里时，A 和 B **各自**都满足这三条。
3. 拆 A 时，A 按自己的 3 × 3 把这块地算进待处理集合，`setBlock(DIRT)` 落一次——在 0.1.0 的判据下这不是「越权」，A 的每一步都合法。
4. 症状：拆任意一个核，都会连带铲掉重叠区里**属于另一个核**的田。

绑定制下，清算对象 = **绑定表里本核名下的记录**：

1. 一块地只有 0 或 1 条记录，记录里写着「这个核」。
2. 拆 A 时读出的集合里只有真绑给 A 的地；绑给 B 的地**根本不在 A 的记录里**。
3. 于是 A 没有任何合法路径去动 B 的地。**不是「加了一条检查别的核的 if」，而是「清算对象的来源从范围查询换成了归属查询」** —— 那个缺口不是被补上，是不存在了。
4. 症状消失。

#### 3.7.2 bug 2（所有者下线失保护）的因果链

0.1.0 的保护判据入口是「**遍历在线玩家**」：对 `getPlayerList().getPlayers()` 里的每个在线者问「这块地在你（或你队）的核心范围内、且在你账上吗」（`farmland/FarmlandGuard.java:120-134` 的 `:125`；`inOwnRange` 的 `:92-107` 同样从在线玩家出发）。

1. 遍历的集合**只有在线玩家**。
2. 归属者全员离线时，集合里没有他，于是谁也答不上「这是己方的田」。
3. 返回「不受保护」——类注释 `:114-115` 自己写明了这个已知边界。
4. 症状：主人下线，他家的田被踩坏；拆核时他那几块也没有主人来认领。

绑定制下，**踩踏保护面**（A-45）的入口换成「**这块耕地有没有绑定**」：

1. 耕地 → 绑定表：**有绑定 ⇒ 受保护**，没有绑定 ⇒ 不受保护。这条判定链上**没有玩家这一环**——`farmland/FarmlandGuard.java:120-134` 的签名 `protectsFromTrample(level, pos)` 里本来就没有查询者，踩踏事件也不带「谁的地」这一信息。
2. 于是它既不需要在线玩家，也不需要同盟解析：归属者离线、核主离线、两人都换了队伍，这块田照样踩不坏。
3. **另外两面**（额度闸、浮窗）仍走「核主 UUID + **实时**同盟」（D-138、C-9）：它们有查询者（谁在锄地、这是谁的客户端），换队会立刻改变它们的答案。三面从此不再共用同一条判据，A-45 就是对 D-138「三面共用」这半句的收窄。
4. 症状消失。

**这条因果链的两个边界**（必须一起写，否则读者会以为「离线也全都能判」）：

- **踩踏保护没有「动作方」要求**：踩踏的人是谁都不改变「这块地有绑定」这个事实，所以他是不是己方、在不在线都不影响判定；额度闸与浮窗则有动作方——锄地的人、客户端的主人。
- 队伍解析要名字，而账本里只有 UUID。这一点**只影响额度闸与浮窗**：耕地主这一侧的名字从哪个离线来源取，D-138 没点名，本文不发明（取法由 30 号在技术层点死）；本文只规定那两面的判据：**不需要归属者在线**。

#### 3.7.3 为什么不是「各修一个 if」

| 对比项 | 各打一个补丁 | 本版的绑定制 |
|---|---|---|
| bug 1 的修法 | 拆核时遍历其它核，判「这块地是否还被别人覆盖」 | 不需要：清算对象不含别人的地 |
| bug 2 的修法 | 缓存离线玩家 + 队伍快照 | 不需要：判定从一个存储的事实出发 |
| 代价 | 每次拆核 O(核数 × 地数)；队伍快照与 C-9 的实时解析冲突 | 一次反查 |
| 「这块地归谁」的答案份数 | 两份（范围算一次、账本算一次） | 一份（绑定表） |
| 结果 | 两个补丁互不相干，任何一个漏写就复发 | 两个症状同时失去成因 |

结论一句：本版换的是**答案的载体**，不是**判据的条数**。

## 4. 据点核心亮度 15（R4）

**本节依据：D-141。**

### 4.1 一句话定位

`outpost_core` 注册时加 `.lightLevel(state -> 15)`。这是本版唯一的纯方块属性改动，不动任何数值表、不带 config 键、不改方块实体。

### 4.2 改动本身

| 属性 | 改前 | 改后 | 依据 |
|---|---|---|---|
| 方块光 | 无 `lightLevel`（取值 0） | **15** | D-141 |
| `MapColor` / 硬度 / 抗爆 / 音效 / `pushReaction` / `requiresCorrectToolForDrops` | `MapColor.STONE` / 30.0F / 1200.0F / `STONE` / `BLOCK` / 有 | **一字不动** | `registry/FarmstormBlocks.java:82-89` |

### 4.3 连带影响清单

| # | 影响 | 具体表现 | 依据 |
|---|---|---|---|
| 1 | 该位置**永不刷怪** | 核所在格及其光强未衰减到 0 的邻域不满足敌对生物的暗度条件 | RT-36；D-141 补充 |
| 2 | **光强传播 15 格** | 光强每格衰减 1，从 15 到 0 需要 **15** 格（15 − 0 = 15，【本文补充】算术），水平与垂直同距；穿过不透明方块会被阻断（原版光照规则，本版不改） | 本文补充 |
| 3 | 边界粒子的**观感** | 边界粒子是 `minecraft:dust`，颜色即最终颜色、不参与方块光照明；核心周围地表被照亮后，粒子与地表的亮度对比下降 ⇒ 白天或亮处边界线更淡 | 【本文补充：观感推断】；不改粒子参数（D-141 明确只改亮度） |
| 4 | 农场照明 | 核心周围地表的亮度被拉满 ⇒ 本模组作物生长所需的亮度门槛（0.1.0 既有判据，本版不改）在半径内自动满足，核心旁的地夜里也能长 | D-141 补充 |
| 5 | 雪层与冰 | 按原版规则，高亮度地点的雪层与冰会融化。这是原版方块对光源的既有反应，**不是本模组新增的规则** | 【本文补充】 |
| 6 | 不影响 | 方块实体行为、边界粒子的数量 / 间隔 / 颜色、耕地判定、浮窗数据、挖掘耗时 | D-141 补充 |

第 1 条和第 2 条是同一件事的两面：永不刷怪来自「光强高」，传播 15 格来自「光强按格衰减」。两条都写，是因为玩家会分别遇到（「核旁边不刷怪」与「核能把山洞照亮 15 格」）。

### 4.4 为什么不做成 config

作者给的是一条**固定的方块属性**，不是可调玩法值。做成 config 等于发明需求，还会让「同一个核在别人服务器上是 15、在这里是 0」变成一张需要解释的表（D-141 补充已否决该方案）。同理也不做「红石可关灯」这种状态机——那要改方块状态与光照更新，与「一行属性」的改动量差两个数量级。

### 4.5 边界与异常

| 场景 | 规则 | 依据 / 补充 |
|---|---|---|
| 两个核相邻（间距 < 15 格） | 光照取最大值、**不叠加**：两处都是 15，中间区域仍是「每格衰减 1」的那条曲线 | 【本文补充：原版光照按最大光强传播】 |
| 核心紧贴一个天然洞穴 | 洞穴在 15 格内变亮，怪物改到 15 格外的暗处生成——这是玩家会看到的空间变化，不是缺陷 | D-141 补充；【本文补充】 |
| 核心被拆 | 光照随方块消失一起回落（原版光照更新），不留残余 | 原版光照更新行为 |
| 核心所在区块卸载 | 光照数据随区块数据保存，重新加载不需要重算（原版光照系统行为） | 原版光照系统行为 |

## 5. 左上角浮窗（R5）

**本节依据：D-142、D-143、D-144。**

这是本版第二大件，也是**唯一一条促成破红线的需求**：要显示「自己 + 队友的全部核心，含未加载区块与其它维度」，客户端手里没有这份数据，因此必须新增 1 个服务端 → 客户端的只读网络包（D-142、D-146）。

### 5.1 一句话定位

屏幕**左上角**一块自绘的列表，一行一个核，按放置顺序排，最多 8 行核心 + 1 行溢出提示；可开关、可拖拽定位、位置写进 CLIENT config 并且重进游戏仍在；显示范围是**自己 + 队友的全部核心**——含未加载区块、含其它维度。

### 5.2 显示范围

| 项 | 结论 | 依据 |
|---|---|---|
| 显示谁 | 自己 + 队友的全部核 | D-143 第 1 条 |
| 同盟判定 | **实时己方**（核主本人 + 同队队友，按 UUID / 名字判，不看是否在线）——与额度闸同一套；**踩踏保护面不看队伍**（A-45） | D-143 第 1 条；D-138；A-45 |
| 含未加载区块 | **是**：列表来自服务端全量快照，与区块是否加载无关 | D-143 |
| 含其它维度 | **是**：跨维度全量，不做维度过滤 | D-143 |
| 不显示什么 | 敌对核、核心物品、已拆掉的核 | D-143 补充 |

「跨维度」这条不是「顺便」：它正是 D-142 那条包存在的理由。若只显示当前维度，客户端靠已加载区块就能凑出来，就不需要包；正因为要显示**视距外、跨维度**的核，才必须由服务端推一份全量列表（墓碑 §6 第 3、4 条）。

### 5.3 内容格式

一行一个核，格式固定为：

```
#n [维度路径] (x, y, z) 归谁
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `#n` | 十进制序号，从 1 起 | n = 该核在**排序结果**里的位置（§5.4）；玩家之间可以拿它报点（「#2 那个核」）【本文补充】 |
| `[维度路径]` | 维度 id 的 **path**：`overworld` / `the_nether` / `the_end` | **不新增语言键**（卡补充）；同一组坐标在不同维度各有一个核时靠它区分（D-143 补充） |
| `(x, y, z)` | 方块坐标整数，负数带负号 | 原样显示，不做缩写、不换算区块 |
| `归谁` | 自己 → 一条语言键（显示为「自己」）；队友 → `ownerNames` 里的真实名字 | 队友离线也有名字（D-142 补充） |

示例行（三种归属三种维度）：

```
#1 [overworld] (-128, 64, 1024) 自己
#2 [the_nether] (32, 70, -8) 阿麦
#3 [the_end] (0, 65, 0) 阿麦
```

### 5.4 排序

| 项 | 结论 | 依据 |
|---|---|---|
| 主键 | `placedGameTime` **升序**（放得早的在上） | D-143 第 3 条 |
| 跨维度 | **统一排序**：主世界与下界的核在同一条轴上比时间，不分组、不按维度分段 | D-143 第 3 条 |
| 平手（同一刻放置） | 在主键之后再加两级：**维度 id** → 核坐标 `(x, y, z)` 的字典序（合计三级键）——与 §3.3 的候选平手判据同一条 | 裁决 A-39 |
| 玩家所在维度 | **不影响排序**，也与行的显示顺序无关 | D-143 |

排序由**列表顺序**承载：服务端推来的列表本身就是排好序的，客户端不再排序（D-142 补充）。这样「排序规则」只有一处实现，客户端只负责画。

### 5.5 8 行上限与「+N」

| 项 | 结论 | 依据 |
|---|---|---|
| 核心行上限 | **8 行** | 【卡补充】（事实卡 §2 表下注，可否决） |
| 溢出提示 | 第 9 行画 `+N`，N = 总数 − 8 | 【卡补充】 |
| `+N` 的文本 | 字面量 `+` 紧跟十进制数（例 `+3`），不带单位、不加「个」 | 【本文补充：28 号的字面量就是「+N」，加字等于新增语言键，与 D-143 的「不新增语言键」同向】 |
| `+N` 算不算在 8 行里 | **不算**，它是加在 8 行核心行之外的溢出提示行 ⇒ 浮窗最高 **9** 行 | 【本文补充：D-143 第 4 条的「最多显示 8 行」与第 2 条的「每核一行」在同一句里，8 是核心行的上限；否则 9 个核时恰好看不到 `+N`】 |
| `+N` 的颜色 | 灰色（与「自己」绿、「队友」白区分） | 【本文补充】 |
| 交互 | 不可点击、不可滚动、不可翻页、不可展开 | 【本文补充：D-143 没有给任何交互，浮窗是只读列表】 |

### 5.6 几何与配色

| 项 | 值 | 依据 |
|---|---|---|
| 默认坐标 | 左上角 `(4, 4)`（`hud.x` = 4、`hud.y` = 4） | 【卡补充】；D-144 第 3 条 |
| 行高 | **9** GUI px（原版字体行高） | 【本文补充：D-143 补充把字号 / 行距交给 29 号】 |
| 行距 | **1** GUI px（只画在行与行之间） | 【本文补充】 |
| 内边距 | 上下左右各 **2** GUI px | 【本文补充】 |
| 总高（满 9 行） | **93** GUI px = `9 × 9 + 8 × 1 + 2 × 2` | 【本文补充：算术】 |
| 总高（只有 1 行） | **13** GUI px = `9 + 2 × 2` | 【本文补充：算术】 |
| 宽度 | 最长那一行的 `font.width` 实测值 + `2 × 2` 内边距；不写死常数 | 【本文补充】 |
| 宽度量级 | 一行常见内容（例 `#1 [overworld] (-128, 64, 1024) 自己`）约 **214** px（按 ASCII 6 px、汉字 9 px 估算：32 个 ASCII × 6 + 2 个汉字 × 9 = 192 + 18 = 210，加内边距 4 = 214） | 【本文补充：估算，只用于说明宽度可控；位置钳制用实测值】 |
| 文字色（自己） | **绿色**，`0xFF55FF55` | 【卡补充：自己绿、队友白】+ 【本文补充：具体 ARGB，与 `WildHunterHud` 的 `fill` 自绘同一手法】 |
| 文字色（队友） | **白色**，`0xFFFFFFFF` | 同上 |
| 文字色（`+N`） | 灰色，`0xFFAAAAAA` | 【本文补充】 |
| 背景 | 半透明黑 `0x80000000`（保证在草地、天空、水面上都读得清） | 【本文补充】 |
| 边框 | 1 px 黑 `0xFF000000` | 【本文补充：与蓄力条的描边同一手法】 |

**唯一口径（裁决 A-41）**：本节的**行高 9 / 行距 1 / 内边距 2** 是唯一口径；30 号技术规格里的面板高 `10n + 3`（n = 行数，8 行 83 px、9 行 93 px）是它的**等价推论**，不是第二套参数。下游若同时看到两种写法，以本节的三个数分解为准——9 是原版字体行高、1 是行距、2 是内边距，三者可以各自单独查证；`10n + 3` 只是把它们并成一个式子：`9n + (n − 1) + 4 = 10n + 3`。

三条说明：① 半透明底不是审美，是**可读性判据**——白字直接压在雪地或云上会消失；② 绿 / 白两色的语义是「自己 / 队友」，与顺序无关，与维度无关；③ 宽度按实测值算，所以不同玩家屏幕上同一行的宽度可以不同（名字长度不同），**钳制必须用当前实测宽度**。

### 5.7 开关与位置的交互时序

| 步 | 玩家动作 | 客户端状态 | 持久化 | 依据 |
|---|---|---|---|---|
| 1 | 按「开关浮窗」键 | `hud.enabled` 取反，下一次绘制立即生效 | 写 `farmstorm-client.toml` | D-144 第 1、3 条 |
| 2 | 按「拖拽」键 | 进入拖拽模式：打开一个 Screen（单人会自动暂停），浮窗按**编辑态**继续绘制 | 不写 | D-144 第 4 条；D-143 补充 |
| 3 | 按下左键 | 记录抓取偏移 = 光标 − (`hud.x`, `hud.y`)，进入拖动 | 不写 | 【本文补充】 |
| 4 | 拖动 | 预览坐标 = 钳制(光标 − 偏移)；钳制式见下 | 不写（只在内存预览） | 【本文补充：D-144 补充把表达式交给 29 号】 |

两条钳制与例外的细节：

1. **钳制表达式**（【本文补充】）：`x ∈ [0, guiWidth − 宽]`、`y ∈ [0, guiHeight − 高]`，其中「宽 / 高」是当前实测的浮窗尺寸。不允许部分出屏，也不允许出现负坐标（`hud.x` / `hud.y` 的 int 值域放得下负数，但预览与保存都要压在屏幕内）。
2. **拖拽模式下 `ESC` 只做保存与退出**：保存挂在 Screen 的关闭流程上，所以「保存」与「退出拖拽模式」是同一个动作；Screen 开着时原版本来就不会弹暂停菜单（暂停菜单只在没有 Screen 时打开），因此不需要额外拦截。否则保存与别的动作会抢同一次按键，玩家会以为保存失败了。

**拖拽时浮窗必须仍然可见**（D-144 补充）：`WildHunterHud.java:46` 那套前置条件里有 `screen != null` 就整体不画，而拖拽模式本身就是一个 Screen。所以**拖拽模式是唯一例外**：`options.hideGui` 与 `screen != null` 两条早退在编辑态都不生效，否则玩家看不到自己在拖什么。这是技术必然，不是设计偏好。

客户端指令与按键并存（D-144 第 1、2 条）：

| 入口 | 作用 | 依据 |
|---|---|---|
| 「开关浮窗」键 | 等价于 `/farmstorm hud on` / `off` | D-144 第 1、2 条 |
| 「拖拽」键 | 等价于「进入拖拽模式」 | D-144 第 1、4 条 |
| `/farmstorm hud on` / `off` | 同开关 | D-144 第 2 条 |
| `/farmstorm hud reset` | 位置回默认 `(4, 4)`；**开关状态不变** | 【本文补充：D-144 只给了三个子命令，没写 reset 是否也改 enabled；若 reset 顺便打开浮窗，「我关了它、reset 一下又出来了」会变成意外行为】 |

### 5.8 与既有 HUD 的关系

| 元素 | 位置 | 会不会撞 | 依据 |
|---|---|---|---|
| 浮窗 | 从 `(4, 4)` 起向下展开，满行时底边在 y = 97 | — | 【本文补充：4 + 93】 |
| `WildHunterHud` 蓄力条 | 底端锚定：`y = screenHeight − 52`，占距底 **[48, 52)** 的 4 px 带，含描边 **[47, 53)**；横向居中、总宽 44 | **不会**：纵向净空 = `(guiHeight − 53) − 97 = guiHeight − 150`；`guiHeight` = 240 时净空 **90** px | `client/WildHunterHud.java:27`、`:55`；【本文补充：算术】 |
| 原版快捷栏 / 生命 / 饥饿 / 经验 | 距底 0 ~ 39（`client/WildHunterHud.java:14-16` 的类注释逐条记着这三条行带） | 不会（浮窗在顶端） | `client/WildHunterHud.java:14-16` |

## 6. 压缩干草块音效（R6）

### 6.1 一句话定位

`compressed_hay_block` 的 `SoundType` 从 `GRASS` 改成 **`STONE`**。一行属性，但五类声音一起变，且它是 plan 第 3 条需求唯一的落点。

### 6.2 改什么

| 项 | 改前 | 改后 | 依据 |

### 6.3 连带：五类声音一起变

`SoundType` 是**方块属性**，一次替换改的是这一整套：

| # | 声音 | 什么时候响 | 改后 |

| 抗爆 6 | 独立属性 |

## 7. man瓜 数值与追踪（R7 / R8）

**本节依据：D-127、D-128、D-129。**

文档里 `man瓜` 一律指 **`farmstorm:pumpkin_turret`**（物品 / 方块 / 方块实体同 id）。含「瓜」的另外三个对象——`melon_grenade`（瓜！）、`melon_slice_bomb`（瓜片子）、`melon_grenade_stem`（瓜！茎）——都不是 man瓜（D-127）。

### 7.1 一句话定位

三行数值一起改：开火间隔 **60 → 40 刻**、每发伤害 **1 → 3**、炮弹速度 **0.6 → 0.45**（并提成 config 键）。R8 的「追踪」不新增任何追踪机制——**0.1.0 的炮弹本来就每刻重设方向**，要修的是它在贴脸时的过冲抖动。

### 7.2 数值表

| # | 键 / 位置 | 改前 | 改后 | 依据 |
|---|---|---|---|---|
| 1 | `pumpkin_turret.fireIntervalTicks` | 60 刻（3 秒） | **40 刻（2 秒）** | D-127；`config/FarmstormConfig.java:431-433` |
| 2 | `pumpkin_turret.projectileDamage` | 1 点 | **3 点** | D-128；`:425-427` |
| 3 | `pumpkin_turret.bulletSpeed`（**新键**，double） | 0.6（硬编码常量 `TurretBullet.SPEED`） | **0.45**（= 每秒 9 格） | D-129；`entity/TurretBullet.java:28` |
| 4 | `pumpkin_turret.knockbackLevel` | 1 | **不动** | D-128；`:428-430` |
| 5 | `pumpkin_turret.targetRadius` | 15（切比雪夫） | **不动** | `:422-424` |
| 6 | 伤害类型 | `farmstorm:void_bolt` | **不动** | `registry/FarmstormDamageTypes.java:20` |

三个数一起看才是正确的读法（D-128 补充）：按刻折算的理论输出是 **4.5 倍**（`(3 ÷ 40) ÷ (1 ÷ 60) = 4.5`）。只改伤害会让人以为加强了 3 倍，只改间隔会让人以为加强了 1.5 倍。

### 7.3 近距离绕圈 / 抖动的成因

0.1.0 的追踪实现是「每刻直接把速度矢量重设为指向目标中心 × 固定步长」（`entity/TurretBullet.java:73-87`、`:90-96`）：

1. **每刻直视**：`steerTowards()` 每 tick 用 `目标碰撞箱中心 − 自身位置` 重新算方向，没有转向角上限、没有最大追击时长。
2. **固定步长**：速度大小恒为 `SPEED`（0.6 格/刻），与剩余距离无关。
3. **过冲**：当 `dist < 步长`（0.6 格）时，一步跨过的距离**大于**剩余距离 ⇒ 炮弹落到目标另一侧。
4. **反复掉头**：下一 tick 目标在身后 ⇒ 方向反转 ⇒ 再跨过头 ⇒ 每刻往返，画面就是「贴脸绕圈 / 抖动」。
5. **打不中**：命中判定交给原版 `move` 流程（本类不做射线检测），逐刻位移如果跨过目标碰撞箱而两次采样都落在箱外，`onHitEntity` 就不会触发 ⇒ 越近越打不中。

这也是为什么「降速」和「收敛」必须一起做：只降速会把过冲阈值从 0.6 挪到 0.45，问题还在；只修收敛不改速，正常距离上仍是原来那个步长。

**顺带说明一件事**（附录 A 会展开）：`plan0.1.1.txt:27` 要求「增加追踪功能」，而这项能力在 0.1.0 的代码里**已经存在**——`PumpkinTurret` 在发射时把目标交给炮弹（`behavior/impl/PumpkinTurret.java:74`），炮弹此后每刻朝目标重设方向。真正缺的不是追踪，是「接近时收敛」。

### 7.4 修复后的行为

| 情形 | 改后行为 |
|---|---|
| `dist ≥ 步长` | 与现状完全一致：每刻重设方向、速度大小恒定 |
| `dist < 步长` | **按剩余距离收敛**：这一步的位移就是剩余距离（或等价地直接判中），不再跨过目标 |
| 目标死亡 / 消失 | 与现状一致：`target` 置空，炮弹按最后的速度直线飞出，撞方块消失 |
| 撞方块 | 与现状一致：直接 `discard()`，不炸方块 |

三条「没有变」必须写清楚，否则会被读成「加了新机制」：

1. **仍是每刻修正方向**——不是软追踪（没有转向角上限、没有最大追击时长、没有制导参数、没有换实体父类，D-129 第 3 条）。
2. **仍是服务端权威**——追踪只在服务端做，客户端靠实体同步位置（HC-03）。
3. **仍是直线飞行**——收敛只发生在最后一小段（`dist < 步长`），中远距离的弹道形状不变。

### 7.5 手感对照

| 项 | 0.1.0 | v0.1.1 | 算式 / 依据 |
|---|---|---|---|
| 开火间隔 | 60 刻（3 秒） | **40 刻（2 秒）** | D-127；40 ÷ 20 = 2 秒（【本文补充】算术） |
| 每发伤害 | 1 点 | **3 点** | D-128 |
| 弹速 | 0.6 格/刻（12 格/秒） | **0.45 格/刻（9 格/秒）** | D-129；0.45 × 20 = 9（D-129 已给） |
| 最远锁定距离下的最短飞行时间 | 25 刻（15 ÷ 0.6） | **33.3 刻**（15 ÷ 0.45） | 【本文补充】算术；15 出自 `targetRadius` 默认值 |
| 理论输出 | 1 ÷ 60 点/刻 | 3 ÷ 40 点/刻 | **4.5 倍**（D-128 补充） |
| 贴脸命中 | 过冲、抖动、常打不中 | 收敛，命中 | D-129 |

「飞行时间变长」不是副作用而是需求：作者要的是**降低炮弹速度**，玩家看得见炮弹飞过来。33.3 刻是理想直线的最短路（实际每刻修正方向、路径略长），量级意义是「从 1.25 秒变成 1.7 秒」。

### 7.6 是否仍必中

**不是必中，但命中率只会升高，不会降低。** 四个反例仍然成立：

| 反例 | 为什么还是打不中 |
|---|---|
| 目标在炮弹飞行途中死亡 / 消失 | `target` 置空，炮弹沿最后方向直线飞出 |
| 目标与炮弹之间隔着方块 | 撞方块即 `discard()` |
| 目标瞬移（末影人、传送、`/tp`） | 方向每刻重算，但位移一步只有 0.45 格，追不上瞬移 |
| 炮弹所在区块卸载 | 实体不 tick |

反过来，**贴脸这一类「本该命中却打不中」的情况被消除了**——它不是靠提高命中率，而是靠取消过冲。所以本版对「必中」这件事的态度是：**不承诺必中，只承诺不再因为过冲而必不中**（D-129 补充）。

## 8. 朋友的韭 持续场（R9 / R10）

**本节依据：D-131、D-132、D-133。**

### 8.1 一句话定位

投掷物落地后不再是「一次性结算即消失」，而是变成一个**持续 200 刻的场**：每刻扫一次落点半径 6 格的球体，对球内每个 `LivingEntity` 施加 **`200 − x`** 刻 Q弹（x = 落地后经过的刻数）；第 200 刻自己 `discard()`。音效**仍然只在落地那一刻判一次**（R10）。

### 8.2 场的时间轴

「场长」= `friend_chives.effectTicks`（默认 **200**，值域 20 ~ 1200）；`x` 从落地那一瞬算起，落地那刻 **x = 0**。

| x（落地后刻数） | 场在做什么 | 这一批新中招者拿多久 | 已在场者身上剩余 |
|---|---|---|---|
| **0** | 落地：判音效（球内 ≥ 1 只播一次）、对球内每个 `LivingEntity` 施 `200 − 0` 刻 | **200 刻** | 200 |
| 1 | 第 1 次 `tick()` 重扫球体 | 199 刻 | 199 |
| k | 第 k 次扫描（1 ≤ k ≤ 199） | `200 − k` 刻 | `200 − k` |
| **199** | 最后一次扫描 | **1 刻** | 1 |
| **200** | 不再施加，实体 `discard()` | 不施加 | **0：全部到期，同一刻** |

四条读表要点：

1. **到期时刻统一**：每个中招者拿到的是「整段窗口减去已经过去的部分」，所以无论他在第几刻进场，**都在 x = 200 到期**。这就是 `200 − x` 这个写法的全部意义。
2. **幂等**：已在场者每刻被重写为 `200 − k`，而他身上正好剩 `200 − k` ⇒ 值不变，既不续期也不缩短（原版效果每刻递减 1）。
3. **一次都不漏**：x = 0 那一批由落地回调完成，`tick()` 从 x = 1 起接手；两者不重叠、不重复施加。
4. **第 200 刻不施加**：施加 0 刻没有意义（原版会拒绝）。所以场的施加窗口是 **[0, 199]**，共 200 刻，第 200 刻只负责自毁。

若服主把 `effectTicks` 调成 100，则场长 100 刻、每刻施加 `100 − x`（【本文补充】：场长与施加量同源，`200` 是默认值而不是新常量；否则配置改成 100 时会出现「场持续 200 刻、但每人都只拿 100 − x 刻」的自相矛盾）。

### 8.3 为什么是 `200 − x`

| 若写成 | 会发生什么 |
|---|---|
| 固定 200 刻 | 第 2 刻起每次施加都把剩余时长顶回 200 ⇒ **永久续期**，人站在球里永远跳 |
| 固定 200 刻但只在落地施加一次 | 回到 0.1.0 的行为，中途进场的人不受影响 |
| 每次 `200 − 累计次数` | 与 `200 − x` 等价（累计次数就是 x） |
| `200 − x` | 每人的剩余时长不同，**到期时刻相同** |

### 8.4 音效判定（R10）

| 项 | 结论 | 依据 |
|---|---|---|
| 判定时刻 | **落地那一刻**（x = 0），此后不再判 | D-132 |
| 播几次 | **一次** | D-132 |
| 什么条件播 | 那一刻球内 ≥ 1 个生物 | D-132 |
| 空投 | **永不播** | D-132 |
| 后续进场 | **不补播** | D-132 |
| 声音 | `farmstorm:friend_chives`，`SoundSource.PLAYERS`，音量 **2.0**、音高 1.0 | `entity/thrown/FriendChivesProjectile.java:74-76` |
| 可闻半径 | 32 格（= `friend_chives.soundRange` 默认 32.0，音量 = 32.0 ÷ 16 = 2.0） | 事实卡 §1.8 |
| 音频素材 | 现 ogg 就是原素材的前 **10.000 秒**（与 200 刻 = 10 秒对齐，但不是同一个计时器） | 事实卡 §1.8 |

一条移交：`sounds.json` 是否再补 `"attenuation_distance": 32` 属技术面（该键现未设、走原版默认 16；同文件 `wild_hunter_loop` 已有 32 的先例），由 30 号核，**不改变本节结论**（D-132 补充、28 号 §7 第 5 条）。

### 8.5 与旧行为（落地一次性）的对照

| 维度 | 0.1.0 | v0.1.1 |
|---|---|---|
| 施加次数 | **1 次**（落地那一瞬） | **每刻 1 次 × 最多 200 刻** |
| 谁中招 | 落地那一瞬球内的生物 | 落地那一瞬 + 之后 200 刻内进入球内的生物 |
| 每人时长 | 200 刻（同一刻起算） | `200 − x` 刻（x 为进场时刻） |
| 到期时刻 | 落地后 200 刻 | **落地后 200 刻（同一个时刻）** |
| 后续进场 | 不受影响 | 中招，剩余时长就是 `200 − x` |
| 离开球 | 与效果无关（效果已在身上） | 效果随人走完，**不提前结束** |
| 音效 | 落地时球内 ≥ 1 才播 1 次 | **完全相同** |
| 实体 | 落地即消失 | 存活 200 刻、保持可见、第 200 刻自毁 |
| 再投一次 | 两次投掷各自独立 | 两个场各自独立计时（重叠见 §8.6） |

「控场时长」的净效果：**同一个位置从「闪一下」变成「10 秒不能站」**。这正是 R9 要的东西，也是 RT-34 要盯的开销来源。

### 8.6 边界与异常

| 场景 | 规则 |
|---|---|
| 球内 0 个生物（空投） | 不播任何声音；**场照样持续 200 刻**（D-131 的场不以命中为前提）⇒ 之后走进球里的生物会中招，但全程没有声音提示 |
| 中途进入（x = k） | 拿 `200 − k` 刻；仍在 x = 200 到期 |
| 中途离开 | 效果已在身上，按剩余刻数走完 ⇒ 仍然在 x = 200 到期（他在场外跳完最后几秒） |
| 投掷者本人站在球内 | **同样中招**：效果端不筛敌我（既有注释已写明，本版不改） |
| 旁观者 / 创造玩家 | 谓词只有「球内 `LivingEntity` + 存活」⇒ **不筛游戏模式**。创造玩家会被弹起但不受伤，旁观者没有碰撞、观感无变化——判定一致，观感不同 |
| 区块卸载 | **场结束**：不写 NBT 续命、不跨维度恢复（D-133）。走远再回来不会续上剩余刻数 |
| 第 200 刻忘了 `discard()` | **实体泄漏**：落地后寿命上限不再生效（基类的寿命检查带「未落定」条件），没有任何机制会回收它（RT-35） |
| 两个场重叠 | 各场独立结算；同一个效果按原版规则取「更强的那一个」（同 amplifier 比时长）⇒ 后到的短时长**不会**缩短已有的长时长，到期时刻由最后那个更长的场决定【本文补充】 |
| 投掷物没落地就被销毁（超寿命） | 没有落定就没有场（基类在落定前仍受寿命上限约束） |
| 同时存在的场数量 | 受投掷物寿命与投掷频率限制（RT-34），本版不额外加上限 |
