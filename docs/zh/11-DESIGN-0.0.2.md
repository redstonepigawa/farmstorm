## 0. 阅读约定

### 0.1 本文与 01-DESIGN.md 的关系

本文是**增量**，不是重写。v0.0.1 的设计（`01-DESIGN.md`）已随 D-49 冻结，本文不重复定义其中任何既有规则；凡本文写「沿用」，一律指回 `01-DESIGN.md` 的对应小节，阅读时两篇并排看。

v0.0.2 只做两件事：① 给转换器补上唯一缺失的那条合成配方（§2）；② 追加 §3–§8 的 7 个新功能。既有 21 条转换配方、12 个进度、15 条 `CropProfile` 的任何字段、117 个既有 config 键的默认值，一律不动。

### 0.2 标注法

| 标注 | 含义 |
|---|---|
| 【D-xx】 | 结论直接来自 `.work/v002-BRIEF.md` §2 的决策表（D-49 ~ D-79） |
| 【P-x】 | 结论直接来自 `plan0.0.2.txt` 的第 x 条追加要求 |
| 【本文补充】 | BRIEF 与 plan 都没有给出、由本文按既有惯例或原版行为推导的值或口径。实现阶段照此执行，不在别处另立一版 |

凡出现数字，只有两种合法来源：BRIEF / plan 里写着的，或者标了【本文补充】的。二者都不是的数字，视为文档缺陷。

### 0.3 单位与取整

1. 时间：秒 / 游戏刻（tick），1 秒 = 20 刻。
2. 长度：格（block）。
3. 生命与伤害：点。原版 2 点 = 半颗心，因此「回复 10 点生命」= 5 颗心。
4. 等级与 amplifier：等级 N 落库时 `amplifier = N − 1`（`01-DESIGN.md` §0 条款 3）。
5. 角度：度（°）。转速单位写作「度/刻」。
6. 百分比：一律写带 `%` 的整数或一位小数，不做隐式四舍五入。

### 0.4 距离度量

沿用 `01-DESIGN.md` §3.7 条款 4：「半径 N 格」= 欧氏半径；「切比雪夫距离 N」= 方形邻域。新增判定默认切比雪夫，凡本文改用欧氏的（§5 的作用半径 4、§6 的触发半径 1.5、§7 的索敌半径 5），都在该节写明理由。

### 0.5 权威与同步

1. **服务端权威**：落点结算、方块写入、效果施加、伤害、击退、状态迁移全部在服务端（D-23 口径不变）。
2. **0 个自定义网络包**（C-6、D-50）：三项侵入性效果（灰度、红色剪影、输入锁）所需的「服务端告诉客户端状态」，一律借道隐藏 `MobEffect`，用「效果是否存在 + amplifier + 剩余时长」表达完整状态，走原版 `ClientboundUpdateMobEffectPacket` 免费同步。禁止为此新增 `CustomPacketPayload`。
3. **渲染层不写回**：所有相机角度（§6.8）只在渲染层改，不写 `player.getYRot()` / `player.getXRot()`。

## 2. 农产品转换器的合成配方

### 2.1 一句话定位

给 v0.0.1 那个「没有任何配方、只能靠创造模式拿到」的转换器，补上**第一条**合成配方，让「种田 → 转换」这条链在生存模式下真正跑得起来。

### 2.2 类型与类别

| 项 | 值 |
|---|---|
| 对象 | 一个工作方块（`farmstorm:converter`），不是作物 |
| 是否 `CropProfile` | 否。它不进 19 条档案表，不挂任何 `CropCategory` |
| 配方类型 | 原版有序合成 `minecraft:crafting`，3×3 围合 |
| 归类 | 「配方增量」而非「注册对象增量」：blocks / items 计数不变 |

### 2.3 获取方式

唯一途径是工作台合成（D-52）。合成得到的是**方块物品**，放置后才是 v0.0.1 的三槽位 GUI 工作方块（`01-DESIGN.md` §3.1.2）。

### 2.4 数值表

| 参数 | 数值 | 单位 | 依据 |
|---|---|---|---|
| 配方网格 | 3×3，有序 | 格 | D-52 |
| 中心格 | `minecraft:crafting_table` × 1 | 个 | D-52 |
| 外围八格 | 物品标签 `farmstorm:converter_fuel`，每格 1 个 | 格 | D-52 |
| 产出 | `farmstorm:converter` × 1 | 个 | D-52 |
| 经验成本 | 合成不扣经验 | 点 | 【P-1】与 D-52 均未给合成成本；D-12 的每次 3 点只作用于「转换器内的转换」，与合成无关 |
| 燃料标签条目 | 36（18 原版 + 18 改良） | 种 | 【本文补充】，拆分见 §2.5 |

### 2.5 燃料标签 `farmstorm:converter_fuel` 的内容

BRIEF 只给了口径「原版农作物 + 本模组全部改良作物（19 条档案里凡是能被当作「农作物」的物品）」，没给逐条清单。本文把口径落成一条可执行的规则：

> **标签 = 19 条档案中除 `compressed_puffed_wheat` 之外的 18 条改良作物物品，加上它们各自的原版参照物品（18 项）。**

排除 `compressed_puffed_wheat` 的依据是 D-56：它是「二级合成物」，不是「改良农作物」。原版一侧同样按「一一对应」取 18 项：`01-DESIGN.md` §5 的 15 个原版参照，加上 §5–§8 新增三条的原版参照（绯红菌、甘蔗、金苹果）。

**原版一侧（18 项）**

| 分组 | 物品 |
|---|---|
| `01-DESIGN.md` §5 的 15 个原版参照 | `minecraft:wheat`、`minecraft:carrot`、`minecraft:potato`、`minecraft:poisonous_potato`、`minecraft:beetroot`、`minecraft:melon_slice`、`minecraft:melon`、`minecraft:pumpkin`、`minecraft:torchflower`、`minecraft:pitcher_plant`、`minecraft:cactus`、`minecraft:bamboo`、`minecraft:red_mushroom`、`minecraft:brown_mushroom`、`minecraft:sweet_berries` |
| 新增三条的原版参照 | `minecraft:crimson_fungus`（莫洛托夫，【P-2】）、`minecraft:sugar_cane`（桑吉尔蔗，【P-3】）、`minecraft:golden_apple`（狂野苹果，D-54） |

**改良一侧（18 项）**

| 分组 | 物品 |
|---|---|
| v0.0.1 的 15 条档案 | `puffed_wheat`、`blast_carrot`、`ubi_server`、`toxic_ubi_server`、`power_beet`、`melon_slice_bomb`、`melon_grenade`、`pumpkin_turret`、`awakened_torchflower`、`awakened_pitcher_plant`、`fang_trap_cactus`、`bamboo_firecracker`、`red_mushroom_puff`、`brown_mushroom_puff`、`lucky_berry` |
| v0.0.2 新增的 3 条 | `molotov`、`zangief_cane`、`wild_apple` |

改良一侧的物品全部带 `farmstorm:` 前缀。**不进标签的三类**（【本文补充】，理由随条）：① 播种物品（`puffed_wheat_seeds` 这类），它们是种子不是农作物；② `compressed_puffed_wheat`（D-56）；③ `compressed_hay_block`，它是方块不是农作物。

### 2.6 行为规格

1. 中心放 `minecraft:crafting_table`、八格各放一个燃料标签内的物品，产出 1 个转换器。
2. 八格**可以混搭**：不必是同一种作物，只要每格都命中 `farmstorm:converter_fuel` 标签即成立（【本文补充】：D-52 只说「周围八格收这个标签」，逐格独立判定，不加「八格同物」约束）。
3. 中心必须是原版工作台，不是转换器自身；把转换器放进八格不成立（它不在标签内）。
4. 合成不消耗经验、不消耗下界之星；下界之星只在转换器的正向转换时消耗（D-12、`01-DESIGN.md` §3.1.2）。
5. 合成与转换是两件事：合成属于 `minecraft:crafting`，转换属于 `farmstorm:conversion` 的 GUI 内结算。新增这条合成**不触碰**任何一条既有转换配方。

### 2.7 边界与异常

| 场景 | 规则 |
|---|---|
| 已在 v0.0.1 存档里靠创造模式放好转换器 | 正常工作，行为与新合成的完全相同；本配方不改方块任何字段 |
| 另一个数据包也定义了同样形状的合成 | 原版合成表按首个匹配裁决，本模组不介入 |
| 燃料标签被数据包清空 | 配方不可达成，转换器在生存模式无法获得。这是数据包层面的后果，本模组不改配方逻辑、不加兜底 |
| 把新作物当燃料烧掉 | 合法。`wild_apple` 等既是燃料也是转换产物，误当燃料是玩家自己的损失，不做拦截 |
| 合成产出堆叠 | 产出 1 个，不额外掉落经验、不触发任何进度 |

## 3. 压缩干草块

### 3.1 一句话定位

一个「硬到炸不动、只能拿钻石镐慢慢砸」的建材方块，作为压缩膨胀麦的落点产物存在。

### 3.2 类型与类别

| 项 | 值 |
|---|---|
| 注册名 | `farmstorm:compressed_hay_block` |
| 方块父类 | 普通方块（`Block`），不是 `DeployedCropBlock` |
| 是否 `CropProfile` | 否。它是方块，不进 19 条档案表 |
| 类别 | 不挂 `CropCategory`。【本文补充】：建造类的判定要求「效果写入**原版**有实质用途的方块」（`01-DESIGN.md` §2.3.5），本方块是本模组方块，因此它只能作为建造类产物的载体被提及，自身不被标类 |
| 物品形态 | `BlockItem` `farmstorm:compressed_hay_block` |

### 3.3 获取方式

| 途径 | 说明 | 依据 |
|---|---|---|
| 压缩膨胀麦投掷落点 | 把落点范围内的方块整片写成本方块，是主要量产方式 | D-77 |
| 挖回去 | 需要钻石镐及以上，且需正确工具才掉落（见 §3.4） | BRIEF §3.2 的工具标签 |
| 合成 | **没有**。BRIEF §3.2 的配方增量只有 5 条（转换器合成 1 + 压缩膨胀麦 1 + 转换 3），不含本方块 | BRIEF §3.2 |

### 3.4 数值表

| 参数 | 数值 | 单位 | 依据 |
|---|---|---|---|
| 硬度 | 30.0 | 原版 `strength` 第一位 | D-57 |
| 爆炸抗性 | 6.0 | 原版 `strength` 第二位 | D-57 |
| 掉落前提 | `requiresCorrectToolForDrops()` 为真，即必须用正确工具 | — | D-57 |
| 挖掘工具标签 | `minecraft:mineable/pickaxe` | — | BRIEF §3.2 |
| 最低工具等级 | `minecraft:needs_diamond_tool`（钻石镐及以上） | — | BRIEF §3.2 |
| 朝向 | 六面同材质，不可旋转（不用 pillar / axis） | — | D-57 |
| 材质 | 原版干草块侧面的灰度版 | — | D-57 |
| 物品堆叠 | 64 | 个 | 【本文补充】：方块物品沿用原版 64 上限，不纳入 `stack.throwable` |
| 破坏掉落 | 本体 1 个 | 个 | 【本文补充】：原版方块破坏规则，无额外战利品表字段 |

**这两个数字是照抄远古残骸的一对数，不是平衡出来的**（D-57 的实测依据）：

| 原版方块 | `strength` 实测 | 说明 |
|---|---|---|
| `minecraft:ancient_debris` | 30.0 / 1200.0 | 本方块取它的**硬度** 30.0，不取 1200.0 的抗性 |
| `minecraft:hay_block` | 0.5 | 无参 `strength(0.5F)` 同时管硬度与抗性；本方块不用它的抗性 |
| `minecraft:cobblestone` | 2.0 / 6.0 | 本方块取它的**抗性** 6.0——这就是 D-19 里「圆石 6.0」的那个 6.0（`Blocks.COBBLESTONE` 为 `strength(2.0F, 6.0F)`） |

一句话对齐：**30.0 来自远古残骸的硬度，6.0 来自圆石的爆炸抗性**，两者凑成 D-57 的那一对数；§3.5 与 §11.2 里说的「6.0 抗性挡不住的东西」指的都是这个圆石口径。

### 3.5 行为规格

**抗爆矩阵**——这是本节最需要说清的一张表。判定表达式是 `resistance < maxResistance`（BRIEF §3.4 明令不许改），所以「等于」一律算**破不动**：

| 破坏来源 | 生效阈值 / 规则 | 对本方块 | 依据 |
|---|---|---|---|
| 瓜！ | `BlastRule.grenade()`，阈值 6.0 | **破不动**（6.0 不小于 6.0） | D-57、D-78 |
| 瓜片子 | `BlastRule.sliceBomb()`，阈值 6.0 | **破不动**（同上） | D-57、D-78 |
| 育碧服务器 | `BlastRule.UNBREAKABLE_SKIP`，底线 3.6e6 | **破得动** | D-78 |
| 毒育碧服务器 | `BlastRule.VANILLA`，底线 3.6e6 | **破得动** | D-78 |
| 原版爆炸（含 TNT） | 原版 `Explosion` 的逐格累积公式 | **破得动**：逐格 `f -= (resistance + 0.3) * 0.3`，`f > 0` 即破；6.0 抗性挡不住圆石级别的方块 | D-57 |
| 玩家挖掘 | 钻石镐及以上 | 正常破坏，掉落本体 | BRIEF §3.2 |

其余行为：普通方块的一切默认行为（可被活塞推动、可被流体推动、参与光照遮挡、被爆炸破坏时按原版掉落规则结算）。

### 3.6 边界与异常

| 场景 | 规则 |
|---|---|
| 被另一发压缩膨胀麦覆盖 | 幂等：写入的仍是本方块，不产生额外现象 |
| 被膨胀麦覆盖 | 变成 `minecraft:hay_block`。写入优先于爆炸抗性（`01-DESIGN.md` §7.11 优先级表第 4 条），抗性不参与 |
| 被活塞推动 | 可以推动。它不是部署方块，没有归属者与依附坐标需要维护 |
| 工具不对（木镐 / 徒手） | 挖得动但**不掉落**，且耗时按 30.0 硬度算，极长 |
| 创造模式 | 秒破，不受硬度与工具标签约束（原版规则） |

2. **湿态判定**：先按干态边长 3 的立方体探一次水源——口径是流体标签 `FluidTags.WATER` 且 `fluidState.isSource()` 为真（`01-DESIGN.md` §4.1）；命中即整段改用湿态边长 5，**不再二次判定**。

5. **没有爆炸段**：膨胀麦的落点结算只做两件事——把立方体写成干草块、跳过抗性 ≥ 3.6e6 的方块（`01-DESIGN.md` §4.1、上一条那个源码文件），它不触发任何 `Explosion`。因此本方块**同样没有**「爆炸威力」与「伤害上限」这两个参数。D-77 已把这一点写成硬要求：任何 v0.0.2 文档都不许写「爆炸威力与伤害上限沿用膨胀麦」。
6. **不触发破障语义**：类别只有 `CONSTRUCTION`、没有 `DEMOLITION`，因此它既不破坏方块，也不推进「未授权拆墙」这条既有进度（`01-DESIGN.md` §6 第 8 条）。

### 5.5 落点算法（六步）

触发由投掷物落点发起，落点本身先走 `01-DESIGN.md` §3.4 的既有优先级。

    落点结算(level, landingVec, pos):
        1. 触发器      —— 在落点生成一次「威力 0」的爆炸，只为拿到落点语义；不结算伤害、不动方块
        2. 枚举候选    —— 以 landingVec 所在方块坐标为中心，切比雪夫半径 4 的立方体
        3. 欧氏筛      —— 以 landingVec 所在的**整数格**为球心，保留整数格偏移满足 dx²+dy²+dz² ≤ r² 的方块
        4. 上表面判据  —— 逐块判断「上表面接触空气」（§5.7），不满足的丢弃
        5. 掷骰        —— 每个通过的方块独立掷一次（§5.8），按结果写入它上方的空气位（§5.9）
        6. 收尾        —— 投掷物实体 discard，settled 置真，同一实体不再结算

六步之间的两条硬约束：① 第 1 步的爆炸在默认威力 0 时**零副作用**，它只是「落点触发器」（D-58）；威力被人为调大后**只增加对实体的伤害，永远不破坏方块**——莫洛托夫没有破障标签，`BlastRule.forCrop` 对它恒返回 `NEVER_BREAK`，破坏权限与威力无关（裁决 A-10）；② 第 5 步只写「原本是空气」的位置，原方块一格都不动（D-58）。

### 5.6 半径 4 格怎么数

1. **候选集**：以落点所在方块坐标为原点，取 `dx, dy, dz ∈ [−4, +4]` 的全部方块位置。这是 9×9×9 = 729 个候选（【本文补充】：729 是枚举上界，不是实际作用数量）。
2. **筛选**：把候选集按**欧氏距离**裁成球——判定原点取**落点所在的整数格**（§3.4 落点结算出的那个 `BlockPos`），被判定点取候选格相对它的**整数格偏移**（`dx, dy, dz`），条件写 `dx² + dy² + dz² ≤ r²`。不取 `landingVec` 的精确坐标：球心落在方块内部时「球内有多少格」没有唯一答案（裁决 V-20）。
3. **为什么用欧氏**：【P-2】写的是「半径 4 格」。按 `01-DESIGN.md` §3.7 条款 4，「半径 N 格」一律解释为欧氏半径；条款 1 规定原点默认是方块中心或部署点坐标，投掷型沿用 §3.4 落点结算出的**整数格**。两条合起来就是上面第 2 条。
4. **为什么不用切比雪夫**：切比雪夫半径 4 是个 9×9×9 的方块盒子，对角处距离 6.93 格（【本文补充】：√(4²+4²+4²) 的几何推算值），与「半径 4 格」的直觉差太远；欧氏球的最远点正好 4.0 格。
5. **不计入的方块**：空气、水、以及上表面不是实心面的方块都在第 4 步被淘汰，所以「4 格内有多少方块」并不等于「掷了多少次骰」。半径 4.0 时整数球（`d² ≤ 16`）共 **257** 格，这是单发写入的上界（`12-TECH-0.0.2.md` §3.7 判据 1 / 判据 6）。

### 5.7 「上表面接触空气」怎么判

判定只有两条，全在服务端按方块坐标逐块判：

| 条件 | 判定 | 说明 |
|---|---|---|
| A · 上方是空气 | `level.getBlockState(pos.above()).isAir()` 为真 | 只认原版 `isAir`，覆盖空气、洞穴空气、虚空空气三种。上方是水、雪层、草、火把都不算空气 |
| B · 自身是完整实心方块 | `level.getBlockState(pos).isSolidRender(level, pos)` 为真 | 这一条自然排除空气方块、水、树叶、台阶、雪层。没有它，向水面「点火」会得到立刻消失的火。**为什么不用 `isFaceSturdy(level, pos, Direction.UP)`**：它会让「顶面完整的有向方块」也通过，语义比设计意图宽；两者对台阶 / 雪层的结论一致，`isSolidRender` 更窄（裁决 V-21） |

补充口径（【本文补充】）：

1. 条件 A、B 是**与**关系，缺一不掷。
2. 只看紧邻上方一格，**不递归**。「上方是空气、再上方也是空气」不会额外多掷一次。
3. 判定与掷骰发生在同一刻，中间不做方块更新；因此写火不影响同一批其它方块的判据（见 §5.9 第 1 条）。
4. 不做「是否可燃」的筛选。下方是石头也照写火——这类火按原版规则自然熄灭，那是预期结果，不是漏判（见 §11.3）。

### 5.8 85 / 15 怎么掷

1. **粒度**：每个通过 §5.7 的方块**独立掷一次**，不是整个球掷一次，也不是每层掷一次。
2. **随机源**：服务端世界随机（`RandomSource`），与投掷者的运气无关，可被世界种子复现。
3. **掷法**：取一个 [0, 100) 的实数 `r`；`r < fireChance` → 火，否则 → 岩浆块。**只有 `molotov.fireChance` 一个键**（§10.2），岩浆块的概率是它的余数，不设第二个键（BRIEF §8.1 裁决 A-01）。
4. **互斥**：一次掷骰只产出一个结果，同一个空气位不会同时得到火和岩浆块。
5. **不再有「两项之和必须为 100」这条校验**：只剩一个概率键，余数自动归岩浆块，因此不存在两个百分比加起来不等于 100 的非法配置（BRIEF §8.1 裁决 A-01）。`molotov.fireChance` 取值 0.0–100.0：取 100 时全火，取 0 时全岩浆块。
6. **无保底**：不做「至少出一个火」这类补偿。极端情况下全出岩浆块是合法结果。

### 5.9 火焰与岩浆块落在哪个坐标

| 项 | 坐标 | 说明 |
|---|---|---|
| 火焰 | `pos.above()` | 即「那个合格方块正上方的空气位」，精确到方块坐标，不取中心偏移 |
| 岩浆块 | `pos.above()` | 与火焰**同一个位置**，二者互斥 |
| 原方块 `pos` | 保持原状 | 不替换、不破坏、不产生掉落 |

三条推论（【本文补充】）：

1. **对号入座是双射**：不同方块的上方位置必然不同，所以同一发莫洛托夫不会出现「两个方块抢同一个空气位」的冲突，也就不需要去重。
2. **写入前不必再查一次空气**：条件 A 已在同一刻确认它是空气。若实现阶段改为异步或多线程写入，则必须在写之前补一次 `isAir` 检查，写不成即放弃该格，不重试、不转移。
3. **落点本身是空气时**（例如命中实体后结算），落点方块在筛选中自然被淘汰，它下面那层照常参与——表现为「在落点下方起一片火 / 岩浆」。

### 5.10 为什么不做方块破坏

这一条是本节最重要的设计约束，依据是 D-48、D-19 与 D-58：

1. **破坏权限只有一处判据**：方块破坏权限只由 `CropCategory.DEMOLITION` 决定，全仓没有第二处判据（D-48 铁律；D-58 的依据段再次点名了这条，并明确「不是 D-19」）。D-19 管的是**抗性阈值**——它决定「炸得动什么」，不决定「谁有资格炸」，两者不是一回事：阈值写在 `BlastRule` 里，不写在具体爆炸调用点。
2. **莫洛托夫没有破障标签**：它的类别是「伤害类、建造类」（BRIEF §3.1）。既然不挂 `DEMOLITION`，它在规则层就不具备破坏方块的资格——效果看起来再像爆炸也不行。
3. **D-58 把爆炸降级成触发器**：落点那次爆炸的威力是 0。原版 `Explosion` 在半径 0 时伤害公式得 Infinity，天然无伤；方块破坏同理不发生。于是这次爆炸只剩「落点在哪儿」这一个信息量。
4. **真正的效果是「写」不是「删」**：火焰与岩浆块被写到**空气位**上，属于建造类语义（写新方块），与原方块零交互。
5. **反证**：若让莫洛托夫破方块，立刻出现第二处判据——「同样的爆炸，莫洛托夫按什么阈值破、瓜！按 6.0 阈值不破」——既违反 D-19，也把 `01-DESIGN.md` §7.11 的破坏优先级表撕成两半。
6. **连带影响**：因为它不破坏、不伤害，damage_types 增量为 0（BRIEF §3.2），也不需要伤害上限这类裁剪逻辑。

### 5.11 边界与异常

| 场景 | 规则 |
|---|---|
| 落点在未加载区块 | 直接作废，不结算（`01-DESIGN.md` §7.10） |
| 落点在水中 | 水面不满足条件 B，不参与掷骰；水体内部不存在空气位，因此水下不会凭空生出岩浆块。水面上方的合格方块照常掷骰 |
| 落点在雨区 | 照常写火。火随后按原版规则被雨浇灭，这是预期表现，不做补偿（§11.3） |
| 落点范围内没有任何合格方块 | 结算完成、什么都不写，不报错、不做粒子补偿 |
| 命中方块侧面 | 落点取命中面内侧坐标（`01-DESIGN.md` §3.4），球心落在方块堆中，结果是「球心周围那一圈上表面被点火」 |
| 范围内方块被同一刻的其它效果改动 | 本次结算不重试、不二次扫描，按当前读到的状态裁完即止 |
| 创造模式玩家投掷 | 正常结算，不消耗物品（D-16 的对称处理） |

### 6.5 触发判定

1. **扫描时机**：部署方块的 BlockEntity 每 10 刻扫一次（`DeployedKind.ZANGIEF_CANE(10)`）。
2. **度量**：以**部署点方块中心**为球心，取**玩家碰撞箱中心**到球心的欧氏距离 ≤ 1.5 格（D-73 的球形口径 +【本文补充】的判定点取碰撞箱中心）。
3. **对象筛选**：只认非己方玩家（`TeamResolver.isFriendly` 判否，`01-DESIGN.md` §3.6）；创造模式与旁观者不触发（D-71）；生物不触发（D-71）。这与 v0.0.1 三处陷阱的豁免一致。
4. **同刻多个候选**：取距离最近者结算，其余不受影响——方块在结算的第一刻就被静默移除（D-72），不存在第二个触发者。
5. **触发即结算**：`triggered` 置真 → 方块静默移除 → 对触发者施加 `amplifier 0` 的 `farmstorm:zangief_piledriver`（14 刻）→ 播放音效。整个过程在同一刻完成，不排队。

### 6.6 相位状态机（amplifier 0 / 1 / 2）

隐藏效果 `farmstorm:zangief_piledriver` 的 **amplifier 就是阶段号**（D-50）。客户端读到什么阶段就演什么，不需要任何自定义包（BRIEF §7.5）。

| amplifier | 阶段 | 效果时长 | 服务端在这个阶段做什么 | 客户端据这个阶段做什么 | 何时离开本阶段 |
|---|---|---|---|---|---|
| 0 | 已倒转、等待漂浮 | 14 刻 | 记住触发者与触发刻；不干预位置；到第 14 刻重发同 id 的 `amplifier 1` | 相机 `roll = 180` + pitch 取反（D-59）；键鼠锁定（D-60）；播放触发音一次 | 效果剩余时长归零 |
| 1 | 漂浮中 | 20 刻 | 不额外给速度（上升由原版 `MobEffects.LEVITATION` 自己决定，D-69 只定等级与时长）；到第 20 刻重发 `amplifier 2` 并给首个向下速度 | 保持倒转与锁定；不自转；视角随身体自然抬升 | 效果剩余时长归零 |
| 2 | 下坠自转 | 40 刻 | 每刻按「剩余高度 ÷ 剩余刻数」重设向下速度（§6.10）；检测到落地立刻清效果 | 保持倒转；每刻 `yaw += 72°`（D-70）；落地或效果消失时把相机角度复位为 0 | 落地 / 效果到期 / 玩家死亡 / 效果被外部清除 |

三条状态机约束（【本文补充】）：① 阶段只能单向走 0 → 1 → 2，不回头；② 任一阶段效果被外部清除（`/effect clear`、其它模组的清理逻辑）时，客户端直接复位到「无效果」，不再补发下一阶段；③ 相位切换靠**重发同 id 不同 amplifier 的效果**实现，一次重发同时刷新 amplifier 与剩余时长。

### 6.8 相机

1. **叠加方式**：`roll = 180°` **并且** pitch 取反（D-59）。只做其中一个是错的，必须两条一起。
2. **yaw 自转**：相位 2 期间每刻 `yaw += 72°`，逆时针（D-70），在客户端按 tick 累加，不依赖服务端逐刻同步（BRIEF §7.4）。
3. **只改渲染层**：通过 `ViewportEvent.ComputeCameraAngles` 改角度，**不写回** `player.getYRot()` / `player.getXRot()`。玩家真实朝向从头到尾不变，服务端权威不破（BRIEF §7.4）。
4. **复位时机**：效果消失、相位回到「无」、玩家死亡、切换任何会重建相机的视角，都要把累加值归零。漏归零的后果是相机永久歪掉，这是本节最容易出的 bug。
5. **GUI 不受影响**：roll / pitch 作用于相机矩阵，不作用于 HUD 与容器界面。
6. **转速已裁定**：按 BRIEF §8.1 裁决 A-05，`zangief_cane.spinDegreesPerTick` 默认 **72.0 度/刻**（72 × 20 = 1440 度/秒），`plan0.0.2.txt` 第 29 行的「1440 度每秒」由此得到满足；40 刻累计 2880° = 8 整圈，方向逆时针（yaw 递增，D-70 已同步修订）。旧版事实卡把「1440 ÷ 20」写成 24，是它自己的算式笔误，本条随之改正，不再保留「两种落地口径」的说法。

### 6.9 输入锁

锁定范围照抄 D-60，**只留 ESC**：

| 要锁的 | 锁到什么程度 |
|---|---|
| 移动键（前后左右） | 全部清零，相位 0 / 1 期间原地不动 |
| 跳跃、潜行 | 同上 |
| 攻击、使用 / 放置 | 取消触发，不出手、不放方块 |
| 快捷栏切换（1–9 与滚轮） | 取消，切不了栏 |
| 打开背包（E）、聊天（T / 斜杠） | 取消，界面不打开 |
| ESC | **放行**。锁死 ESC 会让玩家以为游戏卡死（D-60） |

实现落在五个客户端事件上（BRIEF §7.3 的表格）。本节只锁时间段：**从触发刻到相位 2 结束**。效果一消失立刻解锁，不加「落地才算」的额外判据——否则玩家掉进虚空会被永久锁死（§11.5）。

### 6.10 下坠

1. **为什么不能只给一次速度**：原版重力每刻把 y 速度再减 0.08 并乘 0.98（【本文补充】：原版重力参数 −0.08 格/刻²、阻力 0.98）。一次性给初速会让下坠越来越快，落地时间随高度漂移，无法保证「1.7–2.0 秒」。
2. **伺服口径**（【本文补充】）：每刻重算一次向下速度

    速度 = 剩余高度 ÷ 剩余刻数      // 剩余刻数 = 40 − 已用时，分母最小取 1

   于是无论玩家被抬到多高，都在第 40 刻落到地面；被方块挡住提前落地则提前结束。
3. **剩余高度怎么取**：从玩家脚部往下找第一个可站立面或世界最低 y，取较近者。
4. **结束条件**：玩家 `onGround()` 为真 / 脚下被方块挡住 / 40 刻用完 / 玩家死亡 / 效果被清除。五种任一发生即清效果、解锁、复位相机。
5. **不补位、不穿透**：下坠是速度不是传送，撞到方块就停在方块上（与 D-65 的冲刺同一口径）。

### 7.5 三项属性加成

三项加成全部以**属性修饰符**实现，因此走原版 `ClientboundUpdateAttributesPacket` 免费同步，不需要任何自定义包（D-50 的口径）。

| 属性 | 加成 | 修饰符 Operation | 效果示例 | 依据 |
|---|---|---|---|---|
| `minecraft:generic.movement_speed` | +30% | `ADD_MULTIPLIED_TOTAL` | 原版基础 0.1 格/刻 → 0.13 格/刻（【本文补充】：原版基础值 0.1） | 【P-6】定百分比；Operation 选择为【本文补充】 |
| `minecraft:generic.attack_speed` | +30% | `ADD_MULTIPLIED_TOTAL` | 原版基础 4.0 次/秒 → 5.2 次/秒（【本文补充】：原版基础值 4.0） | 同上 |
| `minecraft:generic.attack_damage` | +40% | `ADD_MULTIPLIED_TOTAL` | 空手 1.0 点 → 1.4 点；持武器时按总伤害同比放大（【本文补充】：原版空手基础值 1.0） | 同上 |

表中 0.13 格/刻、5.2 次/秒、1.4 点三个数是由「原版基础值 ×（1 + 加成）」算出的示意值（【本文补充】），用来表明量级，不是新的数值来源。

**为什么是乘法修饰符而不是加法**（【本文补充】）：

1. 原文说的是「提升百分之三十 / 四十」，即**相对当前数值**的百分比。加法修饰符（`ADD_VALUE`）只能表达固定点数，一旦玩家的基础值变化（换武器、吃药水），「提升四成」这个语义就失效了。
2. 为什么不用 `ADD_MULTIPLIED_BASE`：它只乘**基础值**。攻击伤害的基础值只有 1.0 点，+40% = +0.4 点，与「伤害提升四成」的实际体感差一个量级；`ADD_MULTIPLIED_TOTAL` 乘的是「基础值 + 全部加法修饰符 + 武器伤害」的总量，才符合原文。
3. **叠加语义**（关键）：同一属性上多个 `ADD_MULTIPLIED_TOTAL` 修饰符的 amount 会先**求和**再对总量乘一次，不是逐次相乘。因此速度 II（+40%）与狂野猎人（+30%）同时存在时是 ×1.70（= 1 + 0.40 + 0.30），不是 ×1.82（= 1.4 × 1.3）——两个乘数是【本文补充】的算式示意，用来区分「求和」与「逐次相乘」两种语义。这条在 §11.7 展开。
4. **精确移除**：三个修饰符各带固定的标识（名称 + UUID）。效果到期、被清除、玩家死亡时按标识逐个移除，不误删其它来源（药水、装备、其它模组）加在同一属性上的修饰符。

### 7.8 索敌算法

候选集合与排序规则全部照抄 D-64：

1. **范围**：以玩家为球心、**半径 5.0 格**的球（欧氏）。【P-6】写「5 格内」，按 `01-DESIGN.md` §3.7 条款 4 解释为欧氏半径。
2. **夹角**：候选与玩家**视线方向**的夹角 **≤ 30°**。
3. **类型**：只认 `LivingEntity`。
4. **排除**：自己、同队伍玩家（`TeamResolver.isFriendly`）、旁观者。
5. **排序**：夹角最小者优先；夹角相同则取距离近者。
6. **可算性**：「画面中最靠近准星」等价于「与视线夹角最小」，服务端算得出来，**不需要读客户端鼠标位置**（D-64 的原文口径）。

    选目标(player):
        look = player.getLookAngle()                      // 视线单位向量
        eye  = player.getEyePosition()                    // 判定原点取眼睛
        best = null
        for e in level.getEntitiesOfClass(LivingEntity, 以 player 为心、半径 5.0 的包围盒):
            if e == player                       → skip   // 自己
            if e 是旁观者                        → skip   // D-64
            if TeamResolver.isFriendly(player, e) → skip   // 同队
            v = e.getEyePosition() - eye                  // 眼到眼
            d = |v|
            if d > 5.0                           → skip   // 欧氏球
            if v·look / d > cos(30°) 不成立       → skip   // 夹角 > 30°
            angle = acos(v·look / d)
            best = 比 best 更优先者（angle 小者优先；angle 相等取 d 小者）
        return best

两条补充（【本文补充】）：① 夹角用**眼睛到眼睛**的向量算，不用脚点——高个子生物在小夹角下才不会被误排除；② 夹角比较用余弦值比大小即可，不必真的算 `acos`，两者单调对应。

### 7.9 冲刺（吸附的实现方式）

「吸附到目标身边」**不做瞬移**，做 3 刻的冲刺（D-65）：

| 项 | 规格 | 依据 |
|---|---|---|
| 位移时长 | 3 刻 | D-65 |
| 位移速度 | 按当前距离算出初速，使玩家在 3 刻内跨到位（【本文补充】：每刻位移 = 距离 ÷ 3） | D-65 |
| 下发方式 | `setDeltaMovement`，客户端照常模拟移动与碰撞 | D-65 |
| 撞墙 | 即停，**不补位、不穿透** | D-65 |
| 落点被方块占据 | 该次冲刺直接失败，本次不吸附 | D-65 |
| 准星对准目标 | 由**客户端**在冲刺启动时本地把视角转向目标，随客户端常规旋转包同步；服务端不写 `setYRot` / `setXRot` | 【本文补充】，与 BRIEF §7.4 的「渲染层不写回」精神一致 |
| 驱动方 | 客户端预测位移 + 服务端判定（服务端在收到挥击包时用 §7.8 的同一算法独立再算一次） | BRIEF §7.6 |
| 新增网络包 | **0**。不许为这个功能新增 `CustomPacketPayload` | D-50 |

**三条红线**（照抄 BRIEF §7.6）：① 首选方案不许换成「服务端逐刻传送」，除非首选实测手感不可接受；② 真要换，必须在 `12-TECH-0.0.2.md` 留决策记录；③ 无论选哪条，都不许为它新增网络包。

**为什么不用瞬移**：瞬移会穿过墙、会跳过碰撞、会让被撞的一方毫无反应时间；冲刺走的是原版移动与碰撞，撞墙即停，手感与公平性都对得上（D-65）。

### 7.13 近战攻击的完整流程

【P-6】给了一张流程草图，本文把它落成状态机——每一格都能指回一条决策：

    按下攻击键（客户端）
      ├─ 本地没有 wild_hunter 效果
      │     └─ 原版攻击，什么都不改
      ├─ 本地有效果，但 §7.8 算不出合法目标
      │     └─ 原版攻击（不吸附、不额外击退）           // D-64 的空集分支
      └─ 本地有合法目标
            ├─ 本地起 3 刻冲刺，本地视角转向目标          // D-65，客户端预测
            └─ 服务端收到挥击包
                  ├─ 用同一算法重算目标                   // D-64，确定性
                  ├─ 目标已不存在 / 落点被方块占据
                  │     └─ 本次不吸附，按普通攻击结算       // D-65
                  └─ 目标存在
                        ├─ 结算伤害
                        ├─ 掉血 > 0 → 原版默认强度击退       // D-75
                        └─ 造成击杀 → +160 刻 / +10 点      // D-74

三条与流程绑定的事实：① 客户端算一遍是为了手感（不等回包），服务端算一遍是为了权威——两边用**同一个确定性算法**，因此结论一致（BRIEF §7.6）；② 流程里没有任何一步需要新增包（D-50）；③ 「准星对准目标」落在客户端本地转向，服务端不碰朝向（§7.9 的表）。

### 7.14 边界与异常

| 场景 | 规则 |
|---|---|
| 效果期间玩家下线 | 效果随存档保留，回线按剩余时长继续；循环音由客户端重建（§11.6） |
| 与速度 / 力量类效果叠加 | 同 Operation 的修饰符先求和再乘，不叠乘（§11.7） |
| 目标在冲刺途中死亡 | 位移已发生，伤害与击退不结算；不换目标（§11.9） |
| 目标隐身 | 高亮照样画（隐身不影响 `hasLineOfSight`），索敌也照样能锁定（§11.8） |
| 目标为创造模式玩家 | 可被锁定、可被吸附，但原版对创造模式不结算伤害，因此不会有击退，也不会续时（【本文补充】） |
| 玩家骑乘中攻击 | 冲刺不生效（原版骑乘时速度由载具决定），退化为普通攻击（【本文补充】） |
| 效果被 `/effect clear` 清掉 | 三项属性修饰符立刻移除、灰度与剪影立刻消失、循环音立刻停；正在进行的冲刺不打断（3 刻内自然结束） |
| 同一刻多次按下攻击 | 以服务端收到的第一个挥击包为准，其余按普通攻击处理（【本文补充】） |
| 玩家在冲刺中撞到另一名玩家 | 原版碰撞处理，不额外结算伤害、不额外击退（【本文补充】） |

## 11. 异常与边界处理清单

编号沿用 `01-DESIGN.md` §7 的风格，本节改为 11.1、11.2……共 13 条。每条只写规则与依据，不再重复各节已给的数值。

### 11.1 转换器配方与既有 21 条转换配方的共存

- **两类配方不是一回事**：合成属 `minecraft:crafting`（产出一台转换器方块），转换属 `farmstorm:conversion`（在转换器 GUI 内结算）。新增合成配方**不触碰**任何一条转换配方（§2.6 第 5 条）。
- **计数**：既有 21 条转换配方一条不动；追加 3 条（莫洛托夫、桑吉尔蔗、狂野苹果）→ 24 条（BRIEF §4）。
- **燃料标签 ≠ 输入槽白名单**：前者决定「什么能合成转换器」，后者由转换配方表决定「什么能放进输入槽」（`01-DESIGN.md` §3.1.2）。某物品在标签里但不在配方表里，仍然放不进输入槽；反过来，某物品在配方表里但不在标签里，也合法——这两套判据互不推导。
- **附魔金苹果不能用**：`minecraft:enchanted_golden_apple` 与 `minecraft:golden_apple` 是两个物品 ID，前者不在 `farmstorm:converter_fuel` 标签内，八格放它不成立（【本文补充】：标签按物品 ID 判定）。
- **烧掉自己的产物是合法的**：`wild_apple` 等既是燃料也是转换产物，玩家误当燃料是玩家自己的损失，不做 UI 拦截、不加二次确认（§2.7）。

### 11.2 压缩干草块被瓜！炸不掉的分歧

- **判定表达式钉死**：`resistance < maxResistance`（BRIEF §3.4 明令不许改 `BlastRule.canBreak()` 的比较逻辑）。所以「相等」判为**不破**。
- **分歧点**：本方块抗性 6.0，瓜！与瓜片子的阈值也是 6.0，6.0 不小于 6.0 → **破不动**（D-57）。这与「玩家直觉里爆炸能炸掉干草类方块」相反，是刻意的设计结果。
- **反面**：育碧服务器（`UNBREAKABLE_SKIP`）与毒育碧服务器（`VANILLA`）只受 3.6e6 的底线与两个标签约束，它们**破得动**本方块（D-78）。原版爆炸（含 TNT）**也破得动**：原版 `Explosion` 逐格累积 `f -= (resistance + 0.3) * 0.3`、`f > 0` 即破，6.0 抗性挡不住圆石级别的方块（D-57）。
- **不许为了「手感」改阈值**：任何改动都会同时改到瓜！、瓜片子与既有 4 条破障类的手感，属于 BRIEF §3.4 的禁改区。
- **玩家想拆自己造的地基**：用钻石镐正常挖，或用育碧服务器炸。两条路都在规则内，不需要为它加新配方或新工具。
- **与「建造类写入」不冲突**：压缩膨胀麦是**写**方块（§4.5），瓜！是**炸**方块（阈值判定），两条路径在不同层，同时存在不产生矛盾（`01-DESIGN.md` §7.11 的优先级表第 2、4 条）。

### 11.3 莫洛托夫在雨里 / 水里

- **雨**：写下去的火按原版规则被雨浇灭，本模组**不做防雨处理、不做补偿**。D-58 只规定「放火」，没有规定「火必须烧起来」。
- **水面上**：水面不满足 §5.7 的条件 B（`isSolidRender` 为假），因此水面那一格**不掷骰**；水中也没有「上方的空气位」，所以水下不会凭空出现岩浆块。
- **落点在水里**：投掷物照常走 `01-DESIGN.md` §3.4 的落点流程并结算，只是筛出来的合格方块更少，甚至为零（§5.11）。
- **落在水边的陆地**：陆地那一侧照常烧起来；同一发莫洛托夫在不同方块上是两个结果，这是预期。
- **不做「雨天禁用」分支**：加了它就要读天气状态，会把一条纯方块判定的逻辑变成三条（雨 / 雷雨 / 晴），收益为零。

### 11.4 桑吉尔蔗触发时玩家死亡或退出

- **玩家死亡**：效果挂在玩家实体上，实体移除时效果一并消失 → 输入锁解除、相机累加值复位（§6.8 第 4 条）。方块已在触发刻静默移除（D-72），不会二次触发。重生后的新实体不继承任何阶段。
- **退出游戏**：服务端不再 tick 该玩家，相位停在原地。整条链上限 74 刻（3.7 秒），远短于常规的断线重连时间，因此**通常**回线时效果已经过期，客户端什么都不做。
- **快速重连（【本文补充】）**：若在 74 刻内回线，玩家可能带着 `amplifier 1` 或 `2` 回来。服务端按剩余时长继续推进相位；相位 2 的「剩余高度」按回线后的新位置现算（§6.10 第 2 条）。客户端每刻自检阶段效果是否还在，不在就自己复位（RT-15）。
- **归属者离线**：桑吉尔蔗是陷阱，归属者只影响敌我判定（按最后已知队伍，`01-DESIGN.md` §7.2），与其是否在线无关。
- **玩家死亡时视角卡在倒转**：不会。相机角度只在渲染层（§6.8），死亡界面走另一条渲染路径。

### 11.5 桑吉尔蔗把玩家抛到基岩层或虚空

- **上升段**：漂浮由原版 `MobEffects.LEVITATION` 自己抬升，本模组不给速度（§6.6 相位 1）。头顶有方块时位移被碰撞吃掉，实际上升高度可能为 0。
- **落回基岩层**：基岩上表面是可站立面，伺服速度在第 40 刻之前就把它按到面上，相位 2 提前结束，一切正常。
- **落进虚空（玩家自己挖穿了基岩）**：伺服速度按「剩余高度 ÷ 剩余刻数」推进，剩余高度取到世界最低 y 为止。40 刻走完后相位结束、解锁、交还原版重力，玩家可以自救（末影珍珠、水桶、飞行）。**不做「到 y 坐标强行结束」的补丁**——那会引入一条与生命值无关的第二种终止条件。
- **在相位 2 期间死亡**（坠落伤害或其它来源）：走 §11.4 的死亡路径。
- **锁不能无限期**：输入锁的终点是「相位 2 结束」，不是「真到落地」。反过来锁会让掉进虚空的玩家永远动不了，这是必须避免的。

### 11.6 狂野猎人期间玩家下线

- **效果本体**：`MobEffectInstance` 随玩家存档保存，回线后按剩余时长继续计时（原版行为）。计数不因离线而暂停或加速。
- **循环音频**：客户端 `SoundInstance`，会话结束即随之销毁；回线时由客户端按「效果还在不在」重建（D-76，服务端不补发）。
- **灰度与红色剪影**：派生渲染，不持久化任何状态；回线后由效果存在与否自动恢复（D-50）。
- **冲刺中断**：冲刺只有 3 刻（D-65），不会跨越登录；断线时未完成的冲刺随会话作废，不做补偿。
- **不因离线续时**：续时只由**击杀**触发（D-74），离线期间没有战斗，效果不会因此延长。
- **属性修饰符**：随玩家数据保存，回线后由原版属性同步自动恢复；若因异常丢失，效果到期的清理逻辑仍会尝试按标识移除（移除一个不存在的修饰符是空操作，不报错）。

### 11.7 狂野猎人与其它速度类效果叠加

- **同 Operation 先求和再乘**：同一属性上多个 `ADD_MULTIPLIED_TOTAL` 修饰符的 amount 先相加，再对总量乘一次。因此速度 II（+40%）与狂野猎人（+30%）同时存在时是 **×1.70**，不是 ×1.82（§7.5 第 3 条）。
- **跨 Operation 的顺序**：`ADD_VALUE` 的固定点数先进「基础值」一侧求和，`ADD_MULTIPLIED_TOTAL` 最后统一乘。所以其它模组给固定 +0.05 格/刻时，先加后乘，结果与纯百分比叠加不同。
- **急迫不冲突**：急迫（haste）作用于挖掘速度，不是攻击速度，与本节三项加成没有交集。
- **精确移除**：三个修饰符带固定标识（名称 + UUID），效果到期 / 被清除 / 玩家死亡时按标识移除，**不误删**药水、装备或其它模组加在同一属性上的修饰符（§7.5 第 4 条）。
- **清理路径只有一条**：三种结束方式（时长耗尽、`/effect clear`、死亡）都调用同一段清理，不允许出现「死亡后属性还在」的残留——那是最难排查的一类 bug。
- **与食物 / 药水的时序**：先吃的那一份先结算，后吃的那一份后结算，但结果只与「同一刻有哪些修饰符」有关，与顺序无关。

### 11.8 红色高亮对隐身玩家

- **会画**：隐身（`MobEffects.INVISIBILITY`）只影响渲染，不影响 `hasLineOfSight`，因此隐身的敌方玩家**照样**被画成红色剪影。
- **理由**：D-62 只给了两个筛选条件——「视线内可见（无方块遮挡）」与「距离 ≤ 64 格」，外加排除自己与同队伍玩家。没有隐身豁免这一条，不擅自加（BRIEF §6 的「不许自己加条件」口径）。
- **不算透视**：高亮仍然要求无方块遮挡，躲到墙后就不画（D-62 明写「不穿墙」）。因此它给的是「看见才标红」，不是「全图雷达」。
- **旁观者不画**：旁观玩家不进入高亮集合（与 D-64 索敌排除旁观者对齐），避免旁观视角被刷屏。
- **同队不画**：己方判定走 `TeamResolver`（`01-DESIGN.md` §3.6），队伍在战斗中变更时，下一次渲染立刻按新队伍决定画或不画——不做缓存。
- **与索敌集合不同**：索敌是 5 格球 + 30° 锥（§7.8），高亮是 64 格全向。两者只有「排除自己与同队」这一条共享，不要合并成一个集合。

### 11.9 冲刺目标在冲刺途中死亡

- **位移不回收**：3 刻的冲刺已经发生，玩家该到哪就到哪。位移是速度不是传送，回收会瞬移，违反 D-65。
- **结算时重解析目标**：服务端在结算刻用 §7.8 的算法重新算一次目标；目标已不存在（死亡 / 被移除 / 离开范围）→ 本次**不结算伤害、不结算击退**，也不追击。
- **不换目标**：排序在触发刻算一次，途中不重排。因此「原本排第二的敌人」不会因为第一死了就被打中——这会让「谁挨打」变得不可预测。
- **落点被死者占用不算失败**：D-65 的失败条件是「落点被**方块**占据」，尸体不阻塞方块，因此不影响判定。
- **击杀续时只认真正击杀**：只有击杀者确实是本玩家时才 +160 刻 / +10 点（D-74）；目标死于其它来源（摔死、队友补刀）不续时。

### 11.10 循环音频与唱片机 / 其它模组音效打架

- **分类隔离**：循环音走 `SoundSource.PLAYERS`（D-76），唱片机走 `SoundSource.RECORDS`，二者在设置里的音量滑块彼此独立，互不压低。
- **不占用 MUSIC**：因此**不打断**原版背景音乐（D-76 的明写要求）。这是选 `PLAYERS` 而不是 `MUSIC` 的唯一理由。
- **多实例共存**：两名玩家同时持有狂野猎人时，两条循环音同时存在，各自跟随各自的主人，不互斥、不合并、不降噪。【本文补充】
- **16 格衰减**：超出 16 格按原版线性衰减到不可闻。1.21.1 上究竟压 `getVolume` 还是走可听距离钩子，属实现阶段实测项（BRIEF §7.7 的待验证点），文档只锁「16 格」这个数字。
- **停播只有三种触发**：效果消失、玩家死亡、退出世界。服务端不逐刻重发播放/停止指令（D-76），因此不存在「服务端与客户端各管一半」的状态分裂。
- **与音频类模组冲突**：不做运行时检测、不做降级（与 RT-16 的同类处理一致）；若第三方模组接管了音源分类，以它为准，本模组不争夺。

### 11.11 幸运浆果池与狂野苹果的排除口径

- **池的规模**：19 条档案减去 3 条 = **16**（BRIEF §4）。三条是 `lucky_berry`（D-55）、`wild_apple`（D-55）、`compressed_puffed_wheat`（D-56）。
- **要合读两条决策**：D-55 只点名排除了两条，D-56 单独规定压缩膨胀麦不进池。两条合起来才是 16；只读 D-55 会得到 17。
- **排除狂野苹果的理由**：它是本版最强道具，不该由 1 颗浆果随机产出（D-55 的原文依据）。这一条决定了「随到狂野苹果」不可能发生，§8.6 已登记。
- **实现口径**：池必须是**显式列举**的常量列表，不许写成「全部档案 − 幸运浆果」的运行时推导——那样每加一条档案就会悄悄扩大池（D-55 明写把自动推导改成显式排除）。
- **对既有 14 的影响**：v0.0.1 的 14 条全部保留，一条不少；新增的是 2 条（莫洛托夫、桑吉尔蔗），因此 14 → 16。

### 11.12 转换器燃料标签与 19 条档案的联动

- **标签是数据**：`farmstorm:converter_fuel` 落在 item tags 里，内容见 §2.5 的 36 项。它是**唯一**一处「什么算农作物」的可执行定义。
- **与档案表的关系**：新增一条 `CropProfile` 时，除非它像压缩膨胀麦那样被明确判为「二级合成物」，否则必须同步进标签。漏加的表现是「玩家拿不到转换器」，不报错、不崩溃，最难发现。
- **不进标签的三类**：播种物品、`compressed_puffed_wheat`、`compressed_hay_block`（§2.5 末段）。
- **与转换配方表是两张表**：进标签 ≠ 能转换。标签管合成，配方表管转换（§11.1 第 3 条）。
- **与幸运浆果池不同步**：池排除 3 条、标签排除 3 条，但排除的对象不同（池排除幸运浆果本身，标签排除压缩膨胀麦与播种物）。两张表不要互相引用推导。

### 11.13 世界灰度与光影类模组（RT-16）

- **不检测**：本模组**不做**光影（Oculus / Iris 等）的运行时检测，也不给「检测到就关闭灰度」的分支。
- **登记为已知不兼容**：世界灰度走原版 `PostChain`，在渲染管线末端再跑一次全屏 pass，光影模组也占着同一段管线，二者互相覆盖的可能是真实存在的。按 RT-16 的口径，这条写进发布的兼容性说明，不作为运行时问题处理。
- **降级路径**：RT-10 的退化方案是「世界一次 pass + GUI 一次 pass」；再不可用时按 RT-10 再降一档（只灰世界）并在 Release 说明里登记降级。三种情形都不新增网络包。
- **不因兼容问题改动 D-61 的载体**：即使某个光影包不支持，也不换成「雾色 / 贴图替换」这类冒充方案（V-56 只改了作用范围：HUD 不灰，世界必须真灰）。
