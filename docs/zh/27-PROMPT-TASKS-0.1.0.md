## 0. 使用说明

### 0.1 与 26 号的分工

| 文件 | 管什么 | 投喂频率 |
|---|---|---|
| `26-PROMPT-MAIN-0.1.0.md` | 全局纪律与硬约束（工程红线、代码规范、执行纪律、完成定义、回报格式、禁止行为、已知陷阱；编号以它自己的章节为准，本文件不重抄、不新编号） | 每个阶段都常驻 |
| `27-PROMPT-TASKS-0.1.0.md`（本文件） | 这一轮做哪些任务、做到什么算过、交付后怎么开下一阶段 | 一次只取一节 |

三条规矩：

1. 本文件不重写硬约束，只引用编号。看到 `D-xxx`（决策）回 `22`、`RT-xx`（风险）与 `§11 #n`（验收自检）回 `24`、`§11.x`（异常与边界）与 48 × 48 / 3 × 3 这类几何量回 `23`、`A-19 ~ A-28`（裁决）与 `F-xxx`（任务）回 `25`，不要凭记忆理解。
2. 冲突时的裁决顺序：`22-DECISIONS-0.1.0.md`（v0.1.0 唯一真相源）> `23` / `24` > `25` > 本文件。`25` §0.4 已把本轮的口径分歧裁完（A-19 ~ A-28），本文件按裁决写，不重开讨论。
3. 本文件的验收判据只在 `26` 的完成定义之内收紧，不额外发明交付物；`25` 里没有的任务、编号、人日与数值，本文件一个都不加。

### 0.2 怎么投喂

1. 打开本文件，找到当前 Phase 的小节（标题形如 `## 2. Phase 21 · 基线与工具链（F-136 ~ F-142）`），从标题开始整段复制。
2. 与 `26-PROMPT-MAIN-0.1.0.md` **全文**一起投给编码代理，**一次只投一个 Phase**。
3. 等它按 `26` 的回报格式交回，再对照本节 §x.4 的出口判据逐条验收。
4. 验收通过后，用 §7 的交接语开下一阶段。

四条禁令：

- 不要把 §1 总览表一起投——代理会试图一次做完五个阶段。
- 不要跳过 Phase 21 的 F-136 / F-137 直接做 F-138：**90 / 155 / 299** 是 F-136 复算出来的实测值，跳过去就回到「拿 +3 宣布 93」的老路（RT-27；A-21）。
- 不要打乱 F-140 → F-141 → F-142 的顺序，也不要把它们塞进同一个提交：先加 ID 清单、再改计数与分母、最后加第四个 config 来源，这是 24 号 §1.4 的 G1 / G2 / G3（A-21）。
- 不要按编号顺序硬排：Phase 22 / 23 / 24 三者互不依赖、都只等 Phase 21，可以分别派给三个人；Phase 21 内部 F-139 **可并行，但不先于 F-141**，建议排法 `F-138 → F-140 → F-141 → F-139 → F-142`（见 §2.5 第 1 条）。

### 0.3 怎么判断一个阶段完成

三道闸全绿才算过，缺一条都按「未完成」处理：

1. **出口判据**：§x.4 的每一条都能指到 `logs/latest.log` 的断言输出；游戏内 `/execute` `/data get` `/setblock` `/loot` `/clear` 的返回值；F3 / F3+B 的界面读数；`config/farmstorm-server.toml` 或 `src/generated/resources` 的文件内容；`build/libs` 与 `dist` 的产物（含 `jar tf` 的条目清单）。结构性证据（`grep` 命中 0、`git diff` 为空、PNG 逐字节比对、`jar tf` 的条目列表）只在 `25` §0.3 第 4 条允许的场合使用。说「实现了但没验」不算过。
2. **任务覆盖**：§x.3 的每个 F-xx 都有一份可指认的证据；代理漏做时按 `26` 的完成定义要求回补，不要自己补。
3. **仓库状态**：`.tools\gw.cmd build` 退出码 0；`git status` 只出现本阶段边界内的文件；`docs/zh` 的 00 – 26 与 `docs/en/` 全部、既有 22 条 `CropProfile` 档案的字段、既有 155 个 config 键的默认值（除 F-139 授权的 1 条）、既有 18 条进度、既有转换配方未被触碰。

阶段失败时的处理顺序：先让它按 `26` 的自查节自查 → 仍不过就把未通过的验收项抄回任务书重派一次 → 两次不过才换新会话重做，并在交接语里点名卡在哪一条。

一条本版特有的判定（`25` §0.1 末段）：**F-140 提交后工具转红是预期中间态**。验收时把这条红写成「预期中间态 · 唯一一处类型红」，不要因为红就判阶段失败，也不要让它被 F-141 吸收进同一个提交。

### 3.5 常见翻车点

1. **只删 `.randomTicks()` 而不写 `isRandomlyTicking → false`**（RT-24；`24` §4.4 的三件套）：删掉 Properties 上的开关后，原版 `CropBlock` 是否仍随机刻取决于反编译结果。翻成什么样：双源推进——同一株的推进日志出现 6 次或 30 次，`age` 直接冲过 3，成熟时长缩到几秒。提前发现：三件套必须**同时**成立（`.randomTicks()` 只有删除行、`grep -c "randomTick"` 为 0、`isRandomlyTicking` 有一行 `return false`）；实测同一株推进恰好 3 次。
2. **按 23 号 §6.3 的旧写法随机抽 T ∈ [400, 900]**（A-26 已作废）：无方块实体时第三段的余数无处可存，落成「三段各取 T/3」后总时长不再是 402 – 900 刻。翻成什么样：四株里有株的总时长掉到 399 刻以下，或三株完全相等（哈希没参与）。提前发现：段长必须由 `d = 134 + floorMod(pos.hashCode(), 167)` 决定、`T = 3d`；四株的值不全相同。
3. **把免疫闸写成「consume 了但不施效果」**（D-112；`24` §5.1）：闸的位置放在 `findTrigger` 之后、`trigger` 之前，但漏了「被闸住时不 `consume`」。翻成什么样：2 秒内第二次踩刺球，刺球方块消失了——玩家既没挨打也没了陷阱。提前发现：F-146 第 1 条断言直接看「刺球方块仍在原地」。
4. **免疫记进存档或记到生物身上**（D-112 第 3、4 条）：用 `SavedData` 存免疫窗口，或把 `Monster` 也写进 `UNTIL`。翻成什么样：重连后免疫仍生效（玩家以为自己卡了）；或一只僵尸踩过之后，第二枚陷阱对另一只僵尸不触发。提前发现：`grep -c "SavedData" trap/TrapImmunity.java` 为 0；僵尸连踩两枚都触发。
5. **dust 放在免疫闸之后发**（D-113；`24` §5.2）：dust 与有没有人踩无关，闸在它前面就会把粒子一起拦住。翻成什么样：玩家站在陷阱边上时 10 秒内 0 个粒子，站远了才有。提前发现：验收时**人不靠近**，10 秒内必须恰好 2 次；再连续数 60 秒为 12 次（相位对齐：`dustInterval` 100 是 `scanInterval` 10 的整数倍）。
6. **dust 用了狂野猎人的红烟**（A-25；`24` §5.2 的旧取值）：`DustParticleOptions(1.0F, 0.15F, 0.15F)` + 偏移 `(0.2, 0.1, 0.2)` + `Vec3.atCenterOf`。翻成什么样：陷阱落地处的粒子与狂野猎人的红烟分不出来，且位置偏高 0.1 格、横向散布偏小。提前发现：读常量三元组必须是 `(0.62, 0.56, 0.44)`、位置 `y + 0.15`、散布 `0.25 / 0.10 / 0.25`。
7. **生物遍历自己写一个半径数字**（D-114；`24` §5.3）：四个 `findTrigger` 的第二遍遍历另取一个半径或另读一个 config 键。翻成什么样：同一个陷阱对玩家与生物的触发边界不一致，`22` §8 #56 / #57 的度量约定被破坏。提前发现：两遍遍历必须用同一个 `AABB` 与同一个 config 键（代码里只出现一处半径）；炮台集合也不许因为这次改动被扩到生物。
8. **FIFO 先放行后挤出，或挤出用 `breakBlock`**（D-115；`24` §5.4）：先写入新方块再挤出会短暂出现 17 个；用 `breakBlock` 会掉落物品。翻成什么样：放完后数陷阱是 17，或地上出现一堆掉落物把背包填满。提前发现：放完后数**必须是 16**、最早坐标变空气、**地上没有掉落物**；挤出必须复用既有 `consume()` 且排在写入之前。
9. **`getGameProfile` 只改一处**（F-145 的编译期硬阻塞）：`ZangiefCaneTrap` 或 `VibrationBeanTrap` 里还有第二处。翻成什么样：编译 `incompatible types`，或退回用 `Player` 强转，运行期 `ClassCastException`。提前发现：`grep -c "getGameProfile" behavior/impl/VibrationBeanTrap.java` 为 0，且 build 日志无 `incompatible types`。

### 4.5 常见翻车点

1. **试注册 `GameRule` 或写「gamerule」**（A-19；RT-25）：`GameRules.register` 是 `private static`，无 Mixin 红线内注册不了；走反射或 `Unsafe` 会崩服。翻成什么样：编译不过，或起服时 `IllegalAccessException`；更糟的是文档里留下「`/gamerule farmstorm:...`」这种不存在的指令名。提前发现：`grep -rn "GameRules.register" src/main/java` 为 0；交付物里不出现「gamerule」这个词。
2. **指令字面量写成 `farmland_limit` 或 `farmlandLimit`**（D-116；`24` §7.2）：Brigadier 的字面量区分大小写与下划线，写错就是补全不出来。翻成什么样：`/farmstorm` 补全里没有这一项，而反馈文案里却引用了它。提前发现：`/farmstorm` 补全逐字是 **farmlandlimit**；语言键 `command.farmstorm.farmlandlimit.set` 里的名字与代码里的字面量必须逐字相同。
3. **判定顺序写成「先额度后范围」**（D-116 第 4 项；`24` §6.3）：无核心时额度也是 0，先判额度就会给「额度已满」的提示。翻成什么样：默认额度 0 且无核心时提示「已用 0/0」，玩家以为是额度问题而不是没有核心；`24` #10 的验收（要求出现「附近没有己方据点核心」）直接红。提前发现：两个拒绝文案各出现一次的对照实验（`23` §11.9），并检查 `canTill` 的短路顺序。
4. **拦截点选 `HoeItem` 覆写而不是 `RightClickBlock` 事件**（`24` §6.3 的首要方案；待验证 ⑥）：覆写物品层时取消已经发生在产出之后。翻成什么样：「视觉上能耕、规则上无效」——耕地没产生但耐久掉了，或耕地产生了却没入账。提前发现：默认额度 0 时读 `ItemDamage`，必须**不变**；做不到就按 RT-28 兜底 ① 退化并写进验收记录。
5. **拆核做全范围扫描**（D-120 第 4 项；`24` §6.5）：按 3 × 3 区块遍历所有方块而不是只遍历账本。翻成什么样：范围内他人开垦的田也被铲成泥土，玩家在别人据点边上耕的地被无端毁掉。提前发现：F-159 的「范围内但不在账上的耕地不被铲」这条断言。
6. **账本只在内存或只存计数**（RT-28 第 4 条风险；D-117 第 4 条）：用 `int` 计数而不是坐标集合。翻成什么样：重启后 `used` 归零、玩家白赚一轮额度；或自己挖掉一块耕地后 `used` 不减。提前发现：重启前后 `used` 一致；挖掉一块后立刻 −1；同一块耕地在两核心并集里只算一块。
7. **边界粒子用 `sendParticles` 广播**（A-24；`24` §6.6）：`ServerLevel#sendParticles` 发给半径内所有人而不筛己方。翻成什么样：非己方也看得见你的据点边界，`24` §11 #14 直接红；包量还随人数线性放大（RT-30）。提前发现：两个客户端各截一帧（己方看见、非己方看不见）；按玩家发包要先跑通待验证 ⑧ 的最小用例。
8. **粒子按 4 个包 / 圈、三档衰减实现**（A-24；`24` §6.6 的旧写法）：翻成什么样：包量是 23 号 §8.7 的 4 倍，与 RT-30 的方向相反；非己方判定也没了（广播）。提前发现：单圈 **48** 点、每轮 **1 个包**、两档衰减（满点 / 16 格余量带每 4 轮 1 次），三个数逐个对。
9. **额度按「队伍的核心数」求和**（D-117；`23` §11.4）：把队伍口径实现成「队伍共享一个核心计数」。翻成什么样：换队后额度不跟着变，或一个人退队把全队额度带走。提前发现：换队后新队友立刻算己方、额度按新队求和（§11.4）；下线不回收已开垦的耕地（§11.3）。
10. **`countOwned` 不做惰性校验**（D-122 补充；`23` §11.2）：`/setblock air` 清掉的核心仍被计入。翻成什么样：被清掉的核心继续给 `+16`，玩家可以无限刷额度。提前发现：清掉核心后额度必须掉回 `base`；重启后的 `countOwned` 与重启前一致。

### 5.5 常见翻车点

1. **只改图不改生成器**（D-104 补充项；`24` §9.3）：手绘或一次性脚本产出后不把改动写回 `tools/gen_textures.py`。翻成什么样：下次任何人重跑生成器，7 张图被覆盖回占位 / 灰阶，`git diff` 里冒出一批「莫名其妙的还原」。提前发现：删图重跑后与入库**逐字节比对**；`src/main/resources/assets` 的 `git diff --stat` 为空。
2. **压缩麦只改物品模型的父、不改方块模型**（A-23）：`cube_all` 不认 `top` / `bottom` 三键，改一个键等于两个面还是同一张图。翻成什么样：物品栏看得出是小方块，落地后顶 / 侧 / 底一模一样。提前发现：读 block 模型 json 的 `parent` 必须是 `minecraft:block/cube_bottom_top` 且 `textures` 三键齐；落地截三面。

### 6.5 常见翻车点

1. **语言键只凑总数不凑分项**（`24` §9.4 的三处核对式）：总键数做到 315，但 `farmstorm.configuration.*` 是 165 或 `command.*` 少一条。翻成什么样：总数对、结构错，`configuration` 与 config 键数 166 不再相等。提前发现：六项合计 `26 + 32 + 166 + 1 + 2 + 88 = 315` 与增量 `1 + 1 + 11 + 1 + 2 + 0 = 16` 两个式都要成立，再单数 `configuration` 与 166 比一次。
2. **战利品表照抄无 BlockItem 的写法，或干脆漏掉这一个 JSON**（A-27；`24` §2.3）：漏项来自 `23` §1.3 / §10.3 的「4 个」。翻成什么样：挖掉核心什么都不掉，而 DataGen 不报错；JSON 只有 4 个，与 5 的账对不上。提前发现：`loot_table/blocks/outpost_core.json` 必须存在且这一行显式指出该方块有 `BlockItem`；`/loot give` 与直接挖两条路径产物一致。
